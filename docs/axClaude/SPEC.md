# axClaude — Project Specification

Describes axClaude, one app of the axKit bundle (`docs/axKit/SPEC.md`). Every feature is built; this document is kept in step with the code (a behaviour change updates it in the same commit), and what each release brought is section 12.

---

## 1. Summary

An **access layer** for Claude Code (bundle AX-11, 2026-10-29): titled "axClaude, access layer for Claude Code" wherever its name appears; before it first starts Claude Code, the consent notice (AX-11.4, in StartClaude; Not now leaves the line "Not connected to Claude Code. Press Ctrl+Shift+R to connect."); sending /login adds the sign-in line (AX-11.6).

axClaude is a small, self-contained Windows desktop application for a blind developer who uses the NVDA screen reader. It runs the Claude Code CLI (`claude --ax-screen-reader`) inside a Windows pseudo console (ConPTY), sends what the user types in a plain message field to that console, and turns everything the console prints into a **line-by-line transcript** in a read-only text view. The transcript is navigable with NVDA-style single-key commands (`h` headings, `i` the user's own inputs, `o` the start of each reply) and carries marker lines that the app inserts around every exchange. The app starts against a project folder, like `claude` itself, and the folder can be changed from a menu.

The app is **not** a terminal emulator. It relies on Claude Code's screen reader mode, which prints flat, labelled, linear text, and it only understands the small set of control sequences that ConPTY emits for that output.

## 2. Goals and non-goals

Goals:

- **G1 Screen reader first.** Everything works with NVDA and the keyboard only. Focus, names, roles and announcements are designed, not left to defaults.
- **G2 Lightweight.** One WinForms executable, no third-party runtime dependencies, starts in well under a second, idles at negligible CPU.
- **G3 Faithful.** Everything Claude Code prints in screen reader mode ends up in the transcript, in order, once.
- **G4 Structured.** The transcript is navigable by structure (inputs, replies, headings, tool activity, prompts), not only by line.
- **G5 Project aware.** Claude runs in a chosen folder, and the app always shows which.
- **G6 Robust.** Startup dialogs, crashes, exit and restarts are handled; the UI never freezes on console I/O.

Non-goals: a general terminal emulator (colours, the alternate screen, mouse reporting are ignored; only Claude Code in screen reader mode is supported); the Claude API, the Agent SDK or `-p --output-format stream-json` (D3); other platforms (Windows 10 1809 or later only); a mouse-first UI.

## 3. Users and scenarios

Primary user: a blind software developer on Windows 11 with NVDA, keyboard only, who already uses Claude Code and wants a calmer, navigable way to read its output than a terminal window.

| Id | Scenario | What must be true |
| :-- | :-- | :-- |
| S1 | Start on a project | `axclaude C:\src\myproject` (or the menu) starts Claude there; the title and the status bar name the folder. |
| S2 | Ask and read | Type, Enter, hear that Claude finished, Alt+3 lands on the latest reply, read down with the arrows. |
| S3 | Answer a prompt | A permission prompt or y/n question appears as plain lines; "Claude asks" is spoken; the user types `1` or `y` and presses Enter. |
| S4 | Review a long reply | `h` / Shift+H move between headings; `1`..`6` by level. |
| S5 | Recall what was asked | `i` / Shift+I move between the user's inputs. |
| S6 | Switch project | Session → Open folder… → the standard folder picker → Claude restarts there; a system line and an announcement confirm it. |
| S7 | Resume | `axclaude C:\src\myproject` starts Claude on the last conversation in the folder (`--continue` is the default, FR-9.1); New session (Ctrl+N) offers a fresh one, a resume and plan mode (FR-8.6). |
| S8 | Claude stops | The transcript says so, the app announces it, Force Claude to restart (Ctrl+Shift+R) is one keystroke away. |
| S9 | Interrupt | Ctrl+I. Plain Escape in the message field is guarded (FR-2.3, D20). |

## 4. Background: Claude Code in screen reader mode

Verified on 2026-09-18 against Claude Code **2.1.277** (native build) and https://code.claude.com/docs/en/accessibility.

### 4.1 Documented behaviour

- Enabled with `claude --ax-screen-reader`, `CLAUDE_AX_SCREEN_READER=1`, or the `axScreenReader` setting. The first line printed is `[Screen Reader Mode: on via flag]`.
- Output is flat text: no boxes, no colour cues, no redraws of unchanged content; spinners are static text; tables read as `Header: value` sentences. The `tui` setting is ignored.
- Every message starts with a label: `you:`, `claude:`, `thinking:`, `tool:`, `tool error:`, `error:`, `warning:`, `Permission Required:`, `Cost:` (at exit).
- Menus become numbered lists followed by an `Enter selection` prompt; the user types the number and presses Enter. Yes/no questions take a typed `y` or `n` and Enter.
- Two pauses exist for terminals: `CLAUDE_AX_STARTUP_QUIET_MS` (3 s after the confirmation line) and `CLAUDE_AX_PREPARK_MS` (50 ms with the cursor parked before a changed line). Both are set to `0` (FR-1.3).
- The **terminal bell** rings when a reply finishes, when a prompt needs an answer, and when a tool that ran longer than 5 s finishes: the app's primary "Claude needs you" signal. OSC 133 marks are also emitted at turn boundaries; axClaude listens to them since 2026-11-15 (FR-15; `events-and-grounding.md` sections 4.1 to 4.3 say where the bell stands among the marks, the reply's rows and the session file).
- Shift+Tab cycles permission modes and prints an announcement such as `[plan mode on]` once. Alt+M also cycles on Windows.
- Keys: Enter submits; Escape interrupts or closes a dialog; Ctrl+C interrupts or clears input; Ctrl+D twice exits, as does `/exit`; Up/Down browse history; Tab accepts a completion; Ctrl+U / Ctrl+K / Ctrl+W edit the draft.
- Multi-line pastes collapse to `[Pasted text #N +M lines]`; bracketed paste mode is on (`ESC[?2004h`).

### 4.2 The stream at startup (`probe.vt`, 120×40)

```
ESC[?9001h ESC[?1004h ESC[?25l ESC[2J ESC[m ESC[H ESC]0;claude BEL? ESC[?25h
[Screen Reader Mode: on via flag] CR LF
ESC[?2004h ESC[?2031h ESC[?1004h ESC[>0q ESC[?u ESC[?25l
Permission Required: Accessing workspace: CR LF
<folder path> CR LF ... y. Yes, I trust this folder CR LF n. No, exit CR LF Enter y/n: CR LF
Enter to confirm · Esc to cancel ESC[11;12H ESC[?25h
```

1. The first sequences (win32-input-mode request, focus events, clear, title) come from ConPTY and are tolerated.
2. The client asks for bracketed paste, synchronized output, focus reporting, the terminal version and the kitty keyboard protocol. None needs an answer.
3. The workspace trust dialog is a flat `y/n` prompt shown the first time a folder is used.
4. The cursor is positioned with CUP onto the input line: cursor positioning happens even in screen reader mode, to park the caret and redraw the region below the static transcript.

### 4.3 After the trust prompt (`session.vt`)

- The dialog area was cleared row by row (`ESC[2;1H ESC[K CR LF ESC[K ...`) and replaced by the session header, `auto mode on (shift+tab to cycle)`, `effort: xhigh · /effort` and the prompt.
- A second one-time dialog then overwrote rows 5 and below. Startup dialogs are unpredictable in number; never assume the prompt is ready after a fixed delay.
- A message sent while a y/n dialog was open produced `Please answer y or n.` once; later invalid input was ignored silently. Dialog lines must be shown faithfully.
- Rows are rewritten from column 1 and end with `ESC[K`, so trailing whitespace is not significant.

### 4.4 A conversation (the fixtures under tests/fixtures)

**Frames.** Every redraw is bracketed by `ESC[?25l` and `ESC[?25h`. A frame moves the cursor with CUP to the first row of the *dynamic block*, rewrites that row and the rows below it (each ending with `ESC[K` and `CR LF`), skips unchanged rows with another CUP, erases rows left over from a taller frame, and parks the cursor on the prompt row. Rows above the block are never touched again. A frame taller than the screen scrolls with `CR LF` on the bottom row.

**The dynamic block.** Idle: the mode line and the prompt row `$`. Working: a spinner row (`Forming…`, changing every second), sometimes a `Tip: …` row, the mode line with ` · esc to interrupt`, the prompt row. A multi-line draft adds `ctrl+g to edit in Notepad` above the prompt. The slash-command list and a dialog's `Enter to confirm · Esc to cancel` hint are drawn **below** the cursor row.

**A turn.** `you: What is 2+2?` replaces the mode line; a spinner row is rewritten in place; then `ESC]133;C ESC]133;D BEL`; then the final frame: `claude: 2 + 2 = 4`, the turn summary `Baked for 1s · done 2:47 PM`, the mode line, the prompt.

Facts the design depends on:

1. **Enter must be a separate write.** `text\r` in one write became a pasted two-line draft. `text`, then `\r` later, submits reliably.
2. **The `you:` echo.** After submit, Claude rewrites the first dynamic row as `you: <text>`; a multi-line message continues on unlabelled rows. Dialog answers produce no `you:` line. Slash commands produced none when this was recorded and do since 2.1.281 (`you: /model`, `you: /exit` in the fixtures): a row that repeats no sent text, left as Claude printed it, except `/clear`'s (FR-8.8).
3. **Reply rendering.** `claude: ` starts the reply; markdown is plain text: headings lose their `#`, the first block shares the `claude:` row, a later heading is a short row between blank rows, list items keep `- `. **No SGR styling** except dim around the resume hint at exit. Heading detection is structural (§7.6).
4. **Hard wrapping.** Claude wraps long lines at the console width with `CR LF`; a continuation row can begin with a space. A wide console (D9) avoids most of it.
5. **Tool activity.** `tool: Reading 1 file… (ctrl+o to expand)` with the command on following rows (`$ printf …`); the final frame collapses it to `Read 1 file (ctrl+o to expand)`. A content row can start with `$ `: only the cursor row may be treated as the prompt.
6. **Turn end.** `ESC]133;C`, `ESC]133;D` and `BEL` arrive together, usually immediately **before** the final frame with the reply (once in 16 measured turns the reply's rows came 7 ms before them). Announcements wait for the frame (FR-7.2). A turn starts with `ESC]133;A`; an interrupt ends with C and D and no bell; a tool's question rings the bell alone. Since 2026-11-15 the marks are listened to (`SessionModel.Marked`, FR-15): what each moment of a turn gives in the stream, in Claude Code's hooks and in its session file, and how the ends are told apart, is measured in `events-and-grounding.md` sections 4.1 to 4.3.
7. **Titles.** `ESC]0;…` carries a state glyph and the session name: `◐ Basic arithmetic question` while working, `✳ …` idle.
8. **Bracketed paste marks text as pasted.** Claude answered that an instruction "came from the pasted text rather than from you directly" and did not follow it. The user's words go as typed text (FR-2.5).
9. **Turn summary lines.** `Crunched for 5s · done 2:48 PM`.
10. **Exit.** `/exit` opened the autocomplete list below the prompt, `\r` ran it: marks, `BEL`, mode resets, title cleared, `Resume this session with:` and `claude --resume <id>`, exit.
11. Tip rows appear inside the dynamic block while working and vanish with the final frame; `effort: xhigh · /effort` sits in the block for the first turns.
12. **240 columns behave the same** (`conversation-claude2.1.277-240x50.vt`); a y/n dialog echoes the typed `y` with a backspace-space-`y` sequence before the redraw.
13. **A message sent while Claude works** (`steering-claude2.1.278-240x50.vt`): drawn inside the dynamic block as `you: <text>` over `ctrl+x ctrl+s to send now`, redrawn with the spinner every second on shifting rows (a running Bash tool shows `Running…  (3s · timeout 1m)` and `(ctrl+b to run in background)` above it). When Claude takes it up, the `you:` row stays where it was drawn last, the hint disappears and the reply follows. There is no second echo. FR-4.7 is the rule that came out of it. Since 2.1.326 the hint is one row, `Queued  ·  ctrl+x ctrl+s to send now` (`queued-claude2.1.326-240x50.vt`), read as the same hint; and a reply longer than the screen ends a frame on its own rows after the turn's end mark, with the queued row drawn over, so a held block waits for a frame that shows the mode line before it goes in without an echo.
14. **A lone `\n` write is Ctrl+J**: a two-line draft, a two-row echo, and a reply that treats it as typed text, not a paste.
15. **The draft is printed without a frame bracket** (`long-message-claude2.1.278-240x50.vt`): `$ ` plus the text, wrapped over several rows, no cursor hide/show, so the app sees it only at a quiet-timer frame end. The echo wraps the same way.
16. **Mode cycling** (smoke recording): `ESC[Z` went from `auto mode on (shift+tab to cycle)` to `manual mode on` (no cycle hint) to `accept edits on (shift+tab to cycle)`. Each change prints `[manual mode on]` on the row under the prompt for one frame with the cursor parked on it. These bracketed rows are Claude's own announcements and the app speaks them.
17. **Ctrl+O** (smoke recordings): after a turn, two presses drew nothing: screen reader mode never re-renders printed rows, so a past tool summary cannot be expanded. On an idle prompt, Ctrl+O replaced the mode line and the prompt with `Showing detailed transcript · ctrl+o to toggle · ctrl+e to show all verbose`, and a message typed afterwards was never taken up. Ctrl+O is a mode switch that hides the prompt, not an expander.
18. **`--verbose`** (smoke recording, 2.1.278, 2026-09-19): started with `--ax-screen-reader --verbose`, Claude prints what the tools return in full and no `(ctrl+o to expand)` summary at all: `tool: Bash (echo alpha && echo beta && echo gamma)` followed by the rows `alpha`, `beta`, `gamma`; `tool: Read`, rewritten in place to `tool: Read(C:\…\notes.txt)`, followed by `Read 4 lines`; then `claude: OK DONE`. The output rows are unlabelled rows after the `tool:` row, up to the next labelled row. This is the working form of the "show all verbose" that Ctrl+O's status row advertises, and the material a fold of tool output under its `tool:` line would work on.

### 4.5 Two Windows process gotchas

1. **Standard handle inheritance.** A launcher with redirected stdio hands its pipes to the child even with `bInheritHandles = false`; Claude Code then sees no TTY and silently switches to `--print` mode. Fix: clear the three standard handles with `SetStdHandle` around `CreateProcess` (FR-1.4).
2. **Nested session variables.** A process started from inside Claude Code carries `CLAUDECODE=1` and other `CLAUDE*` variables; the child environment is built without them (FR-1.3).

## 5. Functional requirements

Everything listed is built.

### FR-1 Launch and process hosting

- FR-1.1: Create a ConPTY of a fixed size (default 240×50, settings `ptyColumns` / `ptyRows`) and start `claude.exe --ax-screen-reader` in the project folder with the extra arguments from the command line.
- FR-1.2: Locate `claude`: an explicit path (`--claude <path>`, else the `claudePath` setting) is the only place tried; without one, `claude.exe`/`claude.cmd` in every `PATH` folder, then `%USERPROFILE%\.local\bin\claude.exe`, then `%APPDATA%\npm\claude.cmd` (`AxKit.Core/ClaudeCodeProgram`, the one search, shared with the AI tools registration since 2026-11-09, bundle mcp.md MC-6.8). A `.cmd` shim runs through `cmd.exe /d /s /c` with every argument in quotes, inside which cmd.exe reads `& | < > ^ ( ) , ; =` and spaces as plain text (a folder named `R&D` arrives whole); an argument holding a percent sign, an exclamation mark, a double quote or a line break, which cmd.exe acts on inside quotes too, or a `claude.cmd` whose own path holds one of these or `& | < > ^`, is refused before anything runs: the error notice "Claude Code was not started. claude.cmd is a batch program, which Windows runs through cmd.exe, and "<the argument>" holds a percent sign (%), which cmd.exe would act on even inside quotes: it is not started with it. Rename the folder or change the argument, or install Claude Code with its own installer…", the same line in the conversation, the window open. `claude.exe` takes every character. One rule for every start of Claude Code in the bundle (`AxKit.Core/SystemPrograms.LineFor` through `ClaudeCodeProgram.LineFor`; docs/axKit/repairs.json R-24, 2026-11-14). Nothing found: the notice of FR-1.9, the window stays open.
- FR-1.3: The child environment is the current environment minus every `CLAUDE*` variable but `CLAUDE_CONFIG_DIR`, the user's own choice of Claude Code's folder, which Claude Code and the settings of FR-14 then both follow (the user's decision, 2026-11-15), plus `TERM=xterm-256color`, `CLAUDE_AX_STARTUP_QUIET_MS=0`, `CLAUDE_AX_PREPARK_MS=0`, `CLAUDE_CODE_DISABLE_ALTERNATE_SCREEN=1`.
- FR-1.4: Clear the app's own standard handles around `CreateProcess` (§4.5).
- FR-1.5: Console output is read on a background thread and handed to the UI thread in batches (§7.3); never read on the UI thread. Writes go through one serialized writer.
- FR-1.6: When Claude exits: the system line `Claude stopped (exit code N). Press Ctrl+Shift+R to start it again.`, the announcement `Claude stopped`, status `stopped`. No auto-restart.
- FR-1.7: On close, close the pseudo console (Claude exits), wait up to 2 s, then terminate. No Ctrl+C. Claude Code persists the conversation continuously, so `--continue` recovers it. A close or a restart the user confirmed while Claude was busy (the Close axClaude? and Force Claude to restart? notices, a new session or folder over a working Claude) terminates it at once instead: the user chose it knowing, and a process that ignores its console closing would otherwise hold the window for the whole wait (2026-10-23).
  - A close (Alt+F4, the close button, Session → Exit) while Claude is in the middle of a turn (working, waiting for an answer, or holding a message sent while it worked) first shows the **Close axClaude?** notice (D23): "Claude is still working" (or "Claude is waiting for your answer"; plus " and a message you sent is still waiting for it" when one is), ". If you close now, Claude stops in the middle of its work.", "What is done so far is saved. Start axClaude again to carry on.", and the key line "Enter: Close anyway. Escape: Keep working." (D23) Buttons **Close anyway** (Enter) and **Keep working** (Escape).
  - The same notice comes up while Claude runs work in the background after its turn (a shell started with `run_in_background`), which the mode line counts as `auto mode on  ·  1 shell  ·  ↓ to manage` (`SessionModel.Background`, kept while a screen of Claude's covers the mode line): "Claude has work running in the background (1 shell). If you close now, the background work stops." (appended as ", and it has work running in the background (1 shell)" when Claude is also in a turn). The New session notice warns the same way (FR-8.6), and the status bar shows `1 shell in the background`. An idle Claude with nothing in the background closes at once; a Windows shutdown or Task Manager never asks.
- FR-1.8: **Force Claude to restart** (Ctrl+Shift+R, announced "Restarting") stops and restarts in the same folder with the same arguments. While Claude runs it first shows the **Force Claude to restart?** notice (D23): "Claude is still working." or "Claude is waiting for your answer." while in a turn, "Claude has work running in the background (1 shell)." while background work runs (FR-1.7), then "Restarting immediately quits Claude Code and terminates any processes it runs in the background, then starts it again in the same folder with the same options. The conversation stays in the window." and the key line "Enter: Restart now. Escape: Keep Claude running." (D23); buttons **Restart now** (Enter) and **Keep Claude running** (Escape). A stopped Claude starts at once. The arguments are those after `--` on the command line (FR-9.1) or the ones chosen last in the New session notice (FR-8.6). No resume menu item: `--continue` is the default (FR-9.1); `--resume <id>` and the like go after `--` or through New session, and Restart keeps them. Restart keeps the conversation in the window, and a restart with `--continue` in the same folder shows no replay (FR-4.8); New session and a folder change clear the conversation (FR-8.3, FR-8.6).

### FR-3 Conversation

- FR-3.1: A read-only, multi-line, word-wrapped text view "Conversation" fills the window above the field: a native Win32 EDIT control (WinForms `TextBox`), so NVDA reads it line by line and supports review, selection and copying.
- FR-3.2: Each transcript line is one logical line of Claude's output or one app line. Trailing whitespace is trimmed. Rows the terminal soft-wrapped are not joined: at 240 columns Claude hard-wraps first, see FR-3.2a.
- FR-3.2a: A plain row inside a `claude:` or `you:` block that follows a row within 20 characters of the console width, and starts with a space or a lowercase letter, is `JoinedToPrevious`; the view shows the two as one line joined with a space (none when the row starts with one). Rows under a `tool:` line, labelled rows, blank rows and rows at a marker never join; a joined row is never a heading; `l` counts a joined line once. The model keeps the rows as separate `Line`s; only the mirror's separator changes (D17). Setting `joinWrappedLines` (default true, file only) turns it off.
- FR-3.3: Output that arrives while the user reads never moves the caret or selection, never scrolls the view away from the caret, never makes NVDA speak. Without focus, the caret tracks the end and the view scrolls to it, so Ctrl+Tab lands on the newest line; the view also scrolls to the caret when it gains focus. A notice opened while the view had focus does not count as losing it (`KeepCaret`). The caret stays on its transcript line and column while lines above change, its own line is rewritten, or lines are hidden or trimmed (§7.7). Output within 250 ms of a key press in the focused view is applied once the keys stop. Output within 4 s of a caret move that neither a key nor the view made waits as well, and comes 4 s after the last such move (2026-11-09): NVDA's continuous reading (Say all) moves the caret from sentence to sentence as it reads, and output applied between two of its moves changed the text under the range it was reading and cut the reading off (`docs/axKit/development-environment.md` section 5); so the lines wait while the reading goes on. A key press ends the wait as before. The view tells its own moves (`OwnSelect`) and a key's (within its hold) from the reader's (`WndProc`, the EM_SETSEL message).
- FR-3.3a: **The view's text is the transcript's, and the view checks it** (2026-11-15, after new text stood above older text in a long conversation read with the caret in it). Whatever happened between two updates of the view (one frame, or everything that came while the view held its output back for a key, the reader or a selection), the edits applied in their order give exactly the visible lines, the reading breaks included: two edits that start at the same place are applied the later one in the text first; a reading break counts once in the text's length however many marks fall on its column; and a row with a break is found wherever it stands. The view also checks itself, since every edit is placed by an offset into the text the edits before it made, and one that landed elsewhere would misplace every later one for the rest of the session: with each update it asks the control's length before the first edit and after each, and the caret after each (the control leaves it behind what it put in); as it takes the focus it compares its whole text with the mirror's (`TranscriptMirror.FirstDifference`; one copy of the text, about a millisecond at 20 000 lines). On a difference it writes one ERROR line to the log, numbers only (which edit, the lengths, the positions; never the conversation's words; twenty lines a run at most), puts the whole mirrored text in the control in one message (`Rendering`) and puts the caret back by FR-3.3's rule. Nothing is said: the text is right again before the reader meets it, and the log line goes with the next report (F4). An automated run fails on that line.
- FR-3.4: A screen row keeps its line while it is on screen, so in-place rewrites update the line. A line is committed once its row scrolls off or the screen is reset.
- FR-3.5: Chrome is hidden, decided at frame end (§7.5): (a) every row **below** the cursor row; (b) the cursor row when it is the prompt or the draft, or the mode line (on a full screen Claude can park the cursor on the mode line in the bottom row while it works, and the spinner and mode line above a non-chrome cursor row were spoken with the reply); (c) the contiguous block above the cursor row that matches the chrome patterns in `LineClassifier` (mode line, spinner, `Tip:`, `ctrl+g to edit in Notepad`, `effort: … · /effort`, the queued-message hint, the background hint, a bracketed announcement, and the live progress rows of work in the background (FR-7.10, §4.4 items 21 and 24): a running subagent's status row in both its forms, a dynamic workflow's live row, any other row of the large circle `◯` and two spaces, and the row `Waiting for 2 background agents to finish` or `Waiting for 1 dynamic workflow to finish`). The block is closed by the first row that matches none of them, so one unknown row of Claude Code's own at the bottom leaves every row above it in the conversation; that is kept, since it is also what keeps a reply's last rows from being hidden, and a new row is answered with a pattern in `ClaudeCodeTexts`. In the last frame of `/exit` the cursor stands on a blank row under the two rows Claude Code prints as it ends, `Resume this session with:` over `claude … --resume <id>` (`ClaudeCodeTexts.ResumeLabel`, `ResumeCommand`), with the live block still drawn above them (Claude Code 2.1.319 and 2.1.332, the `clear` and `permissions-search` fixtures); the two rows stay in the conversation, and the row above them is read as the cursor row of (b), so that the prompt, the mode line and the spinner are chrome as in any other frame (2026-11-25; until then they stood in the conversation at the end of the session). Content rows outside that block are never matched, so `$ printf …` in a reply stays. (d) The slash-command completion list, which Claude prints directly above the echoed draft row (`$ /ex`, a dollar sign and a no-break space): the draft row is hidden wherever it sits above the cursor, and list rows (`/name  description`, with their indented continuation rows) only as the run directly above a draft row or ending at the cursor row, since a frame can end with the cursor inside the list before the draft row is printed, and after `/exit` Claude prints its last lines under both. An aligned route or path listing in a reply matches the list pattern too and stays, wherever it is: a row that stood in the conversation at the last frame's end and was not written since is never the list's (2026-11-27, `SessionModel.HideCompletionRows`), since the list is drawn now, on rows that were interface rows or empty. Until then the last rows of a reply shaped like list rows were one run with the list of the next slash command drawn under them, blank rows continuing a run since 2.1.326, and were hidden with it for good. The mode line and the spinner feed the status bar. One option shows hidden rows, the live progress rows alone (Options → Background work → Show Claude Code's live progress rows in the conversation, FR-7.10), and they still count as chrome for the block, so the spinner and the mode line above them stay hidden; Help → Record raw stream captures the stream for diagnosis.
- FR-3.6: At most `maxTranscriptLines` (default 20 000) lines; beyond that the oldest 10 % that are off screen are dropped in one operation and the view keeps the caret on its line.
- FR-3.7: Ctrl+F (anywhere; Navigate → Find…) opens the **Find** notice (D23): a "Text to find" field with the last text selected, **Find next** (Enter) and **Cancel** (Escape); Enter with an empty field keeps the notice open and announces "Type the text to find". F3 / Shift+F3 repeat the search; with no text yet they open the notice. Case-insensitive, line by line from the line after (before) the caret, wrapping, ending with the caret line. A match focuses the conversation, puts the caret at it and announces the line, prefixed "From the top, " or "From the end, " after a wrap; no match announces "Not found: <text>" and leaves the caret.
- FR-3.8: Session → **Export conversation…** (Ctrl+S; Save conversation as… until 2.11.0: the conversation is Claude's own record, and the app has no save, so the item is named for what it does and sits at the bottom of the menu, where the editors have Save and Save as, bundle AX-6) writes the conversation as shown (hidden rows left out, wrapped rows joined, without the reading break of FR-3.10; `TranscriptMirror.Render` over the model's lines, not the view's text) as UTF-8 without a byte order mark, default name `axclaude-<folder>-<yyyyMMdd-HHmm>.txt` in the Documents folder, outside the project (D34); announces "Saved".
- FR-3.9: **Bookmarks.** `m` in the conversation (Navigate → Bookmark this line; Ctrl+K from anywhere, which focuses the conversation first) drops a bookmark in front of the caret's line: an app line `Bookmark n` (`LineKind.Bookmark`, `IsMarker`: never classified or hidden, not a heading; *n* counts bookmarks since the session started), announced "Bookmark n added"; the caret stays. On a bookmarked line, or on the bookmark line itself, `m` removes it ("Bookmark n removed"). `k` / Shift+K jump to the next / previous bookmark line and announce it together with the line it marks ("Bookmark 2, claude: …"); otherwise "No next bookmark". A bookmark on a wrapped line (FR-3.2a) goes in front of its first row and leaves the join and the heading rule around it alone (`JoinWrappedRows` steps over bookmark lines). Bookmarks are conversation lines: they are copied and saved with it (FR-3.8), trimmed with it (FR-3.6), and live as long as the conversation in the window. Nothing is persisted separately.
- FR-3.10: **Reading breaks.** When the view has the focus and the caret is on the last screen row of the text, the reader has heard everything there is, so the view marks the end of the last line as heard when output is applied; what Claude appends to that line (or joins to it) after the mark is rendered on a line of its own, so that Down Arrow reads only what is new (D28). A mark that would cut a word moves in front of the word (never in front of the caret), and a space after the mark stays on the heard side. The breaks are rendering only: `l`, Enter, Find and Ctrl+S see the joined line. They are removed, and the line joined up again, once the caret has left the display line that holds them or the view has lost the focus. Output the view holds back (the moment after a key, the wait while NVDA reads, FR-3.3) is put in at once when Down Arrow is pressed on the last row, before the key moves the caret, so that Down never reads the same line again while the next one waits (the maintainer's report of 2026-11-25).
- FR-3.11: **Selection.** Shift with the arrow keys, Ctrl+Shift+End and Ctrl+A select text natively. While the focused view holds a selection, output waits (as after a key press) until the selection is gone, so the selected text never changes under the reader. Ctrl+C with a selection copies it and announces `Copied` (`Could not copy. Try again` when the clipboard is held). Escape with a selection clears it, puts the caret at its start and announces `Selection cleared`; Escape without a selection focuses the message field as before.
- FR-3.12: **Jump history.** Before every jump the app makes (the quick keys, `k`, Alt+3, find, Page Up / Page Down) the caret's line is remembered, up to the last 100. Backspace goes back to the most recent one and announces `Back to <line>`; each press goes one jump further back. A remembered line that is no longer shown is skipped; with nothing left, `Nothing to go back to`. Arrow keys, Ctrl+Up / Ctrl+Down and Ctrl+Home / Ctrl+End are not remembered; going back is itself not remembered.
- FR-3.13: Options → Text → Font… (the Windows font dialog); Ctrl+Plus / Ctrl+Minus change the size in 1-point steps (6 to 72) and announce it; "Windows text size" returns to the system message font, which follows the text size slider under Settings → Accessibility. Menus and the status bar use the system font. Colours are the system colours, so high contrast themes apply, and the window is light or dark as Windows is (AX-7.7).
- Dropped: a transcript log file (Claude Code keeps every conversation).

### FR-4 Markers

- FR-4.1: When the user sends a message, the app prints an **exchange block** at the end of the conversation, above the trailing chrome block: `# Input n`, the message as sent (one line per line, trailing whitespace trimmed), a blank line, `# Output n Reply from Claude`, a blank line. *n* counts messages since the app started, or since New session cleared the conversation (FR-8.6); a replayed conversation has its own count (FR-4.8). Nothing in the block moves afterwards; the reply follows it (D22). The `#` is literal, so an exported conversation is Markdown. Both markers are level 1 headings; Claude's headings are level 2 and deeper. The message lines and blank lines are app lines (`LineKind.UserMessage`), never classified or hidden. A message sent while Claude works gets its block later (FR-4.7). FR-4.6 adds a time stamp.
- FR-4.2: Claude's `you:` echo is hidden, always. The echo block is found by text: from the `you:` row, rows are taken while the text so far, whitespace removed, is a prefix of the sent text, whitespace removed, until equal. Wrapped rows and blank lines inside the message belong to the echo; the rows after it do not.
- FR-4.3: An echo that does not repeat the sent text (a `[Pasted text #1 +5 lines]` placeholder) stays visible after the block.
- FR-4.4: No block for a bare Enter, special keys, slash commands (their output follows the previous lines; their `you:` echo, printed since 2.1.281, repeats no sent text and stays as Claude's own row, and `/clear`'s empties the window, FR-8.8) or an answer typed while a prompt waits (Claude's cursor sits on a prompt row, FR-7.2).
- FR-4.5: App system lines read `System: <message>`.
- FR-4.6: Options → Text → **Time stamps on Input and Output lines** (setting `markerTimeStamps`, default off): `# Input 3 (14:32)` and `# Output 3 Reply from Claude (14:32)`, 24-hour. Existing markers keep their text.
- FR-4.6a: Options → Text → **Markers in the text** (setting `showMarkers`, default on): off, every heading line is shown without its `#` marker, `Input 1`, `Output 1 Reply from Claude`, Claude's `Summary`; the lines, the jump keys and their announcements (§6.4, which never speak the marker) and the export (FR-3.8, always the Markdown) are unchanged, so the structure stays and the text is lighter. On again, the markers return; the caret keeps its line either way. The view's mirror does it (`TranscriptMirror.ShowMarkers`, `Line.BareText`), so axTerminal has the same item.
- FR-4.7: A message sent while Claude works is drawn by Claude **inside** the working block over the `ctrl+x ctrl+s to send now` hint (§4.4 item 13); those rows are chrome, never the echo. The message is held outside the conversation until the hint disappears and the `you:` block becomes content, which is when Claude takes it up; the block then goes in directly before that echo, and the echo is hidden, so the message and its response arrive together (D16). Meanwhile the status bar shows `1 message waiting`. If Claude becomes idle with nothing waiting and no echo came, the block goes in at the end. A pending send is matched to an echo by its text (an echo that repeats nothing is left alone, since a `you:` row quoted in a tool result, replayed at startup or printed for a slash command is not the message, and a held block whose echo never comes goes in once Claude is idle), and is forgotten 30 minutes after it was sent, counted only while Claude is idle: a message queued behind a long step (a subagent, a slow build) waits as long as the step does. A block once printed is never printed again, however the transcript is trimmed (FR-3.6). Restart (FR-1.8) prints the block of a message still held at the end of the old run, since the Claude that would have echoed it is gone; New session drops it with the conversation (FR-8.6). Whether Claude works is, since 2026-11-17, the core's word and no longer the screen's (FR-15; `events-and-grounding.md` EG-6.4, EG-1.4): a message is held, and said as "Queued", while the core has a turn open or ending. A turn is ending from Claude Code's end mark until its "Done" is due, 600 ms after the bell at most, the time in which the reply's last rows still arrive; a message sent then, with a screen that shows no work, used to be "Sent" and got its block in front of those rows, and now goes after that reply. A turn can be over with no frame behind it, so the window ends one more frame of the screen as it stands when the core's turn is over, and a held block whose echo never came goes in then, as it did with the turn's last frame. In a run without marks the core's turn follows the screen's spinner and hint; with the core in shadow (`eventCore`) or after it failed, the screen decides as before.
- FR-4.8: **Replayed conversation.** With `--continue` or `--resume` Claude prints the earlier exchanges at startup as plain `you:` and `claude:` rows. Once Claude is ready (FR-7.7), the app puts the exchange block around each of them: `# Input n from previous session` before the `you:` rows, which stay as the message with their label, then a blank line, `# Output n from previous session Reply from Claude` and a blank line before the first `claude:`, `thinking:` or `tool:` row that follows. *n* counts from 1 in replay order; the live numbering is separate and starts at 1 for every run of the app (FR-4.1), the label telling the two apart. A slash command (`you: /exit`) gets no block. The last past output marker counts as a response already started, so the replay never announces "Responding" (FR-7.7). Rows of an earlier run in the same window keep the blocks they got then: a restart remembers the last line before it, and only the rows after it are looked at (a text match would be fooled by a quoted `[Screen Reader Mode:` row). `i` does not stop on a `you:` row that has a marker in front of it (§6.4). A restart in the folder Claude was already running in, with `--continue` in effect (Restart), replays the conversation the window already shows: every row Claude prints is hidden until Claude is ready, so the window keeps its conversation and the live numbering goes on with no copy underneath. A question (trust, a prompt) or an exit before Claude is ready shows the hidden rows after all. A folder change (FR-8.3, FR-8.5) and New session (FR-8.6) clear the window first and show the replay with its blocks, as at the first start of the app. The mode and session name of the run that ended are forgotten at every restart: the status says `starting` until the new Claude prints its mode line, which is also what marks it ready (FR-7.7).

### FR-7 Announcements and attention signals

- FR-7.1: Announcements are UI Automation notifications raised on the conversation (`RaiseAutomationNotification`), which NVDA speaks without moving focus; while a notice shows they are raised on the notice's text or field. Jump results use "most recent" processing (a new jump cancels the previous); status announcements use "all".
- FR-7.2: **"Done" and "Claude asks".** Since 2026-11-17 "Done" is the core's (FR-15, `events-and-grounding.md` EG-5.6, EG-6.5 and section 4.2). A turn that closes with its end marks and its bell (§4.4 item 6) has finished, and **"Done"** (setting `announceBell`, default on) is said, with its chime and the taskbar signal (FR-7.3), once its last reply is in the conversation: no reply line still waits, the end is confirmed (the turn's stop event, the session file's turn end, or 300 ms after the bell), and a frame after the bell has added a visible line; 600 ms after the bell at the latest. **FR-7.2a, "Done" is heard first, then the reply** (the maintainer's choice of 2026-11-22; until then the lines the window still held for speech went first, and since NVDA reads a notification to its end before the next, "Done" was heard only when the whole reply had been read, long after the music had stopped: "the delay is way too long and should only be a second"). The bell comes just before the turn's last frame, which brings the last reply's rows (§4.4 item 6). Once the bell has rung, reply lines not yet spoken wait for the Done it may bring, 800 ms at most; "Done" is said with the lines after it, as one notification ("Done. " and the reply's words), since NVDA does not speak both of two notifications raised back to back; with nothing held, the word alone. The lines a frame brings are held before that frame can bring the Done: when the turn's end was confirmed before its last rows were drawn (the stop event comes before the end mark), Done is decided on the frame that draws the reply, and it says that frame's lines after its word (2026-11-26: Haiku answering in a second draws its whole reply in the frame after the bell; replayed with the stop event first, the line was held only after Done had gone, and "Done. green apples" would be "Done" and the line alone a moment later; the fixture `silent-words-claude2.1.332`). He settled the same day that it is the one rule, with no threshold of time ("a setting that speaks done before the result or does not speak done at all"): `announceBell` (Options → When Claude is done → Announce "Done") turns the word off, and the lines then go alone; axTerminal has the same order and a switch of its own (its SPEC AT-5.1). A bell that brings no Done (a question's, a turn that was cut) lets the lines go when the 800 ms have passed, unless a question has dropped them (D33). What was already handed to NVDA before the bell is not taken back: "Done" does not interrupt. A turn whose end marks come without a bell says no "Done": an interrupted reply, and the note Claude Code writes when it hands the prompt back. Neither does a reply cut by Send queued messages now (FR-2.8): the queued message's turn follows at once. A bell with no end mark before it is a question's: it starts or restarts a 400 ms timer, the settle, since a question's rows can be blank for a frame while Claude redraws it. When it fires: **"Claude asks"** if Claude's cursor sits on a prompt row (`Permission Required:`, `Enter selection`, `Enter y/n`, `Select with numbers`) or on the blank row under one, and "Done" is not said. Only the cursor row counts: a tool result or a replay can quote a prompt anywhere else (§4.4). Rows that scroll away inside one frame are classified when they are committed, so a replay's `you:` and `claude:` rows keep their kinds. The settle says "Done" by itself, as it did for every bell until 2026-11-17, only where the core does not: in a run in which Claude Code has written no turn mark, where the bell and the settle are all there is of a turn's end; while the core decides nothing (the file-only setting `eventCore` set to `shadow`, or a core that failed, until Claude is started again); and for a "Done" owed to a window that was put away when its turn ended (FR-9.6), one for however many turns ended meanwhile, said after the bringing up unless a question waits then.
- FR-7.3: **Chimes** (`soundOnBell`, default on; Options → Sounds → Chimes: ready, sent, replying, done, question): a single high ping (C6) with "Ready"; a single low note (A4) with "Sent" and "Queued"; three rising notes ending on a long one (C5, E5, G5) with "Responding"; the same notes falling (G5, E5, C5) with "Done"; two equal notes (E5, E5) with "Claude asks". No chime hangs on the working status: the bell comes once per turn (§4.4 item 6), so the done chime marks the end of the whole turn. With the bell also, when the window is not active, a taskbar flash until it is activated (`flashTaskbar`, default on). NVDA speaks notifications only from the active window, so these reach a user working elsewhere. **Background alert** (`backgroundAlert`, default on in axClaude since 2026-11-21, the maintainer's own option made the default; Options → When Claude is done → Louder alert when the window is in the background): when the turn ends or Claude asks while the window is not active, a longer and louder call (G5, C6 and a held E6, then once more, 1.4 s at nearly twice the chimes' volume) plays in place of the done, question or notice chime, whatever `soundOnBell` says, and never in place of an offered command's chime, which plays as ever (FR-2.12); in the active window nothing changes. The chimes are made to be unobtrusive at the window and were missed from another window with sounds of its own, where NVDA does not speak "Done" either. The sounds are short sine tones generated in code (`WaveTone`) and played through one winmm wave-out device that stays open (`Sounds`, D31); no media file ships.
- FR-7.3a: **Announcements** (2026-11-12, the user's ask to filter what is spoken; Options → Announcements, each a switch, default on): "Ready" (`announceReady`), "Sent" and "Queued" (`announceSent`; the sign-in reminder after /login is said whatever the switch), "Responding" (`announceResponding`), "Question closed" (`announceQuestionClosed`), and Claude's own notices, its bracketed rows such as "[accept edits on]" and "Conversation cleared" (`announceClaudeNotices`). "Done" keeps its switch under When Claude is done (`announceBell`). A switch silences the words only: the chimes are the sounds' switch, and what a key of the user's asks for is always said. The line of FR-7.3b has its switch here too.
- FR-7.3b: **A turn Claude Code begins by itself says so** (2026-11-17, the user's decision of that day, after he took such a turn for axClaude restarting by itself). Claude Code starts a turn by itself when work in the background ends (a shell, an agent: the task's notification), and until then the music played, the reply was spoken and "Done" was said with no word of why. When such a turn begins, the window says **"Claude goes on by itself"** (`announceSelfStarted`, default on; Options → Announcements → "Claude goes on by itself" when a turn starts that you did not send), once for the turn, never interrupting, with no sound of its own and nothing in the status bar; a turn of a message the user sent or queued never says it. The core decides it (FR-15, `events-and-grounding.md` EG-4.6): the turn's prompt in the session file, which Claude Code writes with the source system, read while the turn is open or, in a run without turn marks, as what opens it. So the line needs the session file followed (`groundInSessionFile`; without hooks the file is found by the first message sent in the run) and the core in charge of the state: with no record, or with `eventCore` set to `shadow`, nothing is said. It comes when the entry is read, 73 to 228 ms after the turn's start mark as measured (the timelines `background-shell` and `background-agents`): after the music has started, before the reply. While the window is put away it is dropped, as every announcement is (FR-9.6).
- FR-7.4: **Speak replies as they arrive** (`replySpeech`: `none`, `firstLines`, `all` (the default since 2026-11-21, the maintainer's word: "we must speak claude results on by default"; D10); Options → Speech → **Speak replies: none** | **Speak replies: first lines** | **Speak replies: all lines**, shown checked like a radio group; a choice announces its text (`Speak replies: all lines`) and takes effect with what arrives next). Reply lines after the newest output marker are spoken once final: committed, followed by another visible line, or Claude idle. A line whose text was already spoken since that marker is not spoken again: in a long turn Claude can print lines it printed before as new rows, and the first reply of the turn was read out again as the turn ended, over "Done"; such reprints are Claude repainting from the top (§4.4 item 20), and this rule is the second line of defence. *Speak replies: all lines* speaks the `claude:` line and its unlabelled continuation lines; *Speak replies: first lines* speaks the `claude:` line of each message, where Claude says what it is doing or what it found, and leaves the rest for reading, which gives the major moments of a long turn without its detail. **Speak each tool call** (`speakToolCalls`, default off; Options → Speech → Speak each tool call, a check item) adds the `tool:` row of each call, as printed (`tool: Bash (sleep 20)`, `tool: Reading 1 file…`) less a trailing `(ctrl+o to expand)` hint, whatever the reply mode, None included; it is spoken as soon as it arrives, since the row is printed whole and the tool's running status is drawn under it, and it joins the utterance of any reply line that became final in the same frame. A collapsed row that Claude rewrites in place for the next call (`tool: Reading 2 files…`) is spoken again with its new text; its summary once the calls are done (`Read 2 files (ctrl+o to expand)`) is not. An `error:` row, Claude's own error (`error: API Error: 401 Invalid API key · Please run /login` when the login has lapsed), is spoken like a `claude:` row in both modes, with its continuation lines in *all lines*: it can be Claude's whole answer, and a turn that says only Sent, Responding and Done leaves the user without a word of why; `warning:` and `tool error:` rows are not spoken, since Claude goes on after them. Tool output, thinking and the `you:` rows are never auto-spoken, nor is the conversation replayed at startup: speech starts once Claude is ready (FR-7.7). The lines that become final in one frame go out as **one** notification (D32): a wrapped continuation joins with a space, other lines with a full stop unless they end with punctuation of their own, so a heading or a list item is heard as a unit. A line counts as spoken by identity and text: Claude redraws rows in place, and the row that held the prompt a moment ago holds the first reply line next. The pass behind this is shared with the tick (FR-7.8): `Arrivals` in Core, one walk over the transcript per frame.
- FR-7.4a: **Words that keep a reply line silent** (`silentWords`, a list, empty by default; Options → Speech → Words that keep a reply line silent..., one field with the words between semicolons, 2026-11-12): a reply or tool call line that would be spoken and holds one of the words, case not minded, stays in the conversation and is not spoken (`SpeechFilter`). Saving says how many words there are, or "Every reply line is spoken" for none.
- FR-7.4b: **The record of an answered question is never reply speech, and a question cuts leftover reply speech** (2026-11-14). When the user has answered a question Claude asked through Claude Code's question interface, Claude Code prints a record in the question's place: `●  User answered Claude's questions:` and under it one row for each question answered, `· Which colour do you prefer? → Green` (the whole question, an arrow, the answer's name, the names of several, or the words typed after Other). Those rows are Claude Code's words, not Claude's reply: they have a kind of their own (`LineKind.AnswerRecord`; the label by `ClaudeCodeTexts.AnsweredLabel`, the rows under it while they start with `· ` or are the wrapped rest of such a row, `LineClassifier.ContinuesAnswerRecord`), they stay in the conversation and in its export as printed, right under the app's own `Question:` line that q finds (D33, Record), no quick key stops at them as a kind of their own, and `Arrivals` skips them as it skips a marker, so no reply mode speaks them; the user heard "Sent" with the answer. A reply's own lines before and after the record are spoken as ever; the record does not end the reply. Until this rule the rows were reply lines in *all lines*: the label was spoken at once, and the row with the old question, the last visible line while Claude worked, seconds later with the next reply, into the next question. Second, a question of Claude's that opens in the control area while NVDA may still be reading reply text the window spoke interrupts it, whatever Go to them at once says (D33, Arrival), and reply text still held for speech is dropped; the option keeps deciding only whether the focus moves at once. **The question is said once** (the maintainer's rule of 2026-11-26): by the focus when it moves, by an announcement only when it does not. The interruption is the word `Question`, raised just before the focus moves to the list (at once from the bottom of the window, a second later from the conversation), and NVDA's reading of the focus says the question, the role and the answer after it. Until 2026-11-26 the interruption was `<question>. <the answer the focus is on>` itself, raised 300 ms after the focus moved, in the screen and the stream alike (one code, `MainForm.ShowInArea`): when NVDA had already begun reading the focused list, whose name is the question, the question was heard twice, the announcement and the list ("Claude asks to use Write: <path>. Asked by Claude, an AI: … 1. No", then the list read again). The stream met it most, since its reply is spoken whole just before Claude Code asks about the tool, so that leftover speech was nearly always counted as running. Whether NVDA is still reading is an estimate, since the window cannot ask it (`LeftoverSpeech` in Core: 60 ms for each character spoken, an utterance queued behind the one before, 30 s at most). Not a feedback survey, which comes after the turn and leaves the reply's end be (R-19), and not an offered command (FR-2.12).
- FR-7.5: System events are announced: folder changed, Restart, Claude stopped, copy confirmations, recording started and stopped, text size changes, "No next …", find results, "Exported" (FR-3.8).
- FR-7.6: If notifications are unavailable (the call returns false), the target line is selected so NVDA reads "selected …".
- FR-7.7: Sending announces "Sent", or "Queued" while Claude works. "Responding" is announced once per output marker when the first reply, thinking or tool line appears after it. Claude's own bracketed announcements (`[accept edits on]`, §4.4 item 16) are spoken as they appear; that confirms a mode change (Ctrl+P). "Ready" once per start, with its ping (FR-7.3), when the first mode line appears with Claude idle; the replayed conversation is marked at that moment (FR-4.8) and announces nothing else.
- FR-7.8: **Tick** (`clickOnNewLine`, default on; Options → Sounds → Ticks for new lines and tool calls, one item for both ticks): a 10 ms typewriter-like strike (a burst of noise over a 1.5 kHz tone that dies away, with a short attack so it is one tick and not a click) whenever a frame adds a visible line from Claude to the conversation (any line that is not one of the app's own: the markers, the message, system lines, bookmarks). A frame that brings a tool call row (a `tool:` row that is new, or a collapsed one rewritten for the next call, as the tool call speech of FR-7.4 sees it) plays the **tool sound** in its place, so that a tool starting is told from a line arriving without a word: a tiny mouth pop, 30 ms, a round tone (a sine with 0.08 of its second harmonic) whose pitch falls from 700 Hz towards 300 Hz as 300 + 400 exp(-t / 6 ms), rising over 1.5 ms, dying away as exp(-t / 7.5 ms) and brought to nothing over its last 4 ms, the loudest sample 0.3 of full scale (`WaveTone.Pop`; chosen by the user by ear on 2026-11-15, the first of three pops played to him three times each: "I like the current click for tools, but I think it is creating some jarring audio ducking. Can we try something more like a tiny mouth pop so it is not elongated"; until then two lower knocks of noise over a tone, 650 and 850 Hz, 12 ms each, at 0.5 of full scale; `WaveToneTests` holds it to the samples of the script he heard). A frame that adds several lines ticks once. The ticks play whatever the speech mode (FR-7.4) and whether or not NVDA is speaking. A tick never cuts a chime short: it is queued behind the chime, and a tick is dropped while the previous one has not played yet, so ticks never pile up (D31); a chime replaces a tick. The line tick is the 1.3.0 sound (D31). The "jarring audio ducking" the user heard with the knocks was looked for in the code on 2026-11-15 and not found there: the tool sound is queued on the chimes' device, which stays open for the process's life, with no reset of its own (only a chime resets, and only that device); the working music and the background chords are on devices of their own, which no chime or tick touches; winmm's wave-out plays in the default (console) role, which never triggers Windows' communications ducking. What remains is outside axKit: NVDA's own audio ducking (NVDA+Shift+D), which lowers other programs' sound while NVDA speaks, and a laptop's sound enhancements (loudness equalisation, a maker's "audio" suite), whose compressor can pull every sound down for a moment after a loud broadband click such as the knocks' noise burst; the pop has no noise, is softer (0.3 for 0.5) and is a single round tone, which gives a compressor less to react to.
- FR-7.9: **Working music** (`workingMusic`, default on in axClaude since 2026-11-21, the maintainer's own option made the default; off in axTerminal; Options → Sounds → Background music while Claude works): a quiet, slow pad, calm lift music in a building of the future (since 2026-11-15, the user's wish for something gentler, heard by him and settled the same day: "the standard background music is ok"; until then sixteen soft plucked notes, an arpeggio of 8 s): four sustained chords of soft sine tones, C major seventh, A minor ninth, F major seventh and G sixth, 3.5 s each, 14 s that repeat without a seam; each chord swells from nothing over 3.5 s while the one before fades, so nothing is struck; every voice is two sines a fraction of a hertz apart, a slow shimmer, between 175 and 500 Hz; one soft high ping (G5, E6, A5, D6) rings away in each chord. ### FR-9 Command line

```
AxKit.exe claude [<folder>] [--project <folder>] [--claude <path>] [--cols N] [--rows N]
                [--no-ax] [--record <file.vt>] [--message <text>] [--title <text>] [--model <name>]
                [--hide-on-close [--hidden]] [--source screen|stream] [--] [claude arguments…]
```

`--source` (being built, `stream-mode.md` SM-9.1) names what feeds this window for this one start, in place of the
setting `claudeSource`: `screen`, Claude Code in its pseudo console as always, or `stream`, Claude Code as one
process read line by line. Any other word is refused. A window keeps the source it was made for.

axClaude is one app of the axKit bundle (`docs/axKit/SPEC.md` AX-1): `AxKit.exe` reads the verb `claude`, or a folder alone, or an option alone, and hands the arguments to `AxClaudeApp.Run`; the installed console command `axClaude` stands for `AxKit claude`. Everything below is what the app does with those arguments.

- FR-9.1: Everything after `--` goes to `claude` verbatim (`--resume <id>`, `--model opus`, `--permission-mode plan`). Without `--`, Claude gets `--continue`: the last conversation in the folder carries on. In a folder without one Claude prints `No conversation found to continue` and exits; the app then announces "Nothing to continue, new conversation", adds that as a system line and starts Claude again without the flag, and leaves the flag off for that folder until the folder changes. New session's preset Continue the last conversation is this default and gets the same rescue (it is the preset selected at first, so a new session in a folder never used before would otherwise stop; until 3.5.0 it did). An explicit `--continue` (after `--`, or in New session's Custom field) gets no such rescue: Claude's own line and "Claude stopped" follow. A bare `--` gives no arguments: a new conversation.
- FR-9.2: `--no-ax` omits `--ax-screen-reader` (testing only). `--record` writes the raw stream to a file (the PtyCapture format with the `.chunks.txt` index); Options → Developer → Record raw stream for a bug report… does the same at run time. In a window Claude Code's stream feeds (docs/axClaude/stream-mode.md SM-6.5) the file holds the stream's lines as Claude Code wrote them, one a line (`.jsonl`), with the same index of times. `--cols`, `--rows`, `--claude` override the settings file. `--message <text>` (2026-11-07) puts the text into the message field as the window opens, with the caret at its start, unsent: axHelp's screenshot starts axClaude this way (axTask's Open in axClaude on an issue did until 2026-11-14, when axTask's GitHub lists were removed, docs/axTask/SPEC.md TK-7a.2). For axHelp's conversation (5.7.0, docs/axHelp/SPEC.md HE-2): `--title <text>` titles the window with the text alone in place of the folder's name (the status bar keeps the folder); `--model <name>` adds `--model` to every start of Claude in the window, the default `--continue` and its retry as a new conversation included; and a start may hand an open window a "message" (`AppMessage.Message`, one line), which goes into the message field on a line of its own, not sent, the caret at its end and the window in front; the window says "Text added to your message from another window, not sent", since any program of the user's can send one and text that arrived without a word could be sent unread (`docs/axKit/repairs.json` R-07). `--message` too leaves the caret at the end of its text.
- FR-9.3: A GUI executable started from a console returns at once. Publishing and installing are the bundle's (bundle spec AX-2, AX-4.2).
- FR-9.4: In development: `dotnet run --project src/AxKit -- claude <folder>`, `scripts to run-individual-apps\run-axClaude.ps1 <folder>` or `run.ps1`.
- FR-9.5: `--help` (`-h`, `-?`, `/?`) shows the usage in a message box; `--version` the version; a bad command line its error. These are the only message boxes: no window exists yet (D23). `AxKit.exe --help` alone is the bundle's usage (AX-1.4); `AxKit.exe claude --help` is this one.
- FR-9.6: **A window that hides on closing** (2026-11-15, for axHelp's conversation, docs/axHelp/SPEC.md HE-1.3, HE-2.1, HE-2.7; axClaude knows nothing of axHelp, only these two options and three hand-overs).
  - `--hide-on-close`: Alt+F4, the close command (Session, Hide this window, in Exit's place) and Close all windows put the window away: hidden, Claude Code running on, the conversation, the message field's text, the focus and the caret as they were. No question is asked, also while Claude works (FR-1.7 guards an end, and nothing ends). Windows' own end, Update and restart and the commands below close it for real.
  - Put away, the window is silent and unseen (`AxKitForm.PutAway`): it announces nothing and keeps nothing to say later (a reply that arrives is in the conversation, to be read), plays no chime, tick or music (`Sounds.Muted`; the music starts again on showing while Claude still works), is in no Window menu, not in Alt+Tab and not reached by Close all windows (they list visible windows), and the AI tools do not list or read it (its pipe answers that it is hidden). What Claude comes to wait on is not acted on: the settle (D33) is put off until the window is shown and then runs as for a question that has just arrived, with its chime, its focus and its words; a bell that rang meanwhile is "Done" then. The hidden process never keeps the foreground (`ForegroundReturn`, the hotkey windows' rule, shared).
  - Brought up by a hand-over from a start of this very program file (`AppMessage`, FR-9.2): "show" makes the same window visible, in front, with the focus in the message field, or in the control area while it stands in the field's place; a notice on view keeps the focus. When the message field holds a message typed and not sent, "show" also plays the recall chime and says "Unsent message in the field" after NVDA has read the field (the user, 2026-11-15: the message is kept, and said so that it is no surprise); a "message" hand-over says what it added instead. A window already on view comes to the front the same way, the focus put in the message field wherever it was. "message" adds its line and does the same. Nothing is rebuilt, replayed or announced by the showing itself. Activating the window any other way (Alt+Tab, the taskbar) moves nothing.
  - **What happened while it was put away is said and asked on the bringing up**, nothing of it lost and nothing of it heard before, in this order: a notice raised meanwhile (an error) is shown again as on its arrival, with its chime and the focus where a notice puts it; "Claude stopped. Ctrl+Shift+R starts it again" when Claude stopped; then, after the settle, what Claude waits on, or "Done" with its chime when a turn ended; then a command an AI tool offered (FR-2.12), which never shows in a hidden window and is asked now with its own chime and its caution in the list's name (bundle AX-11.12). Whether the Done chime alone also sounds at the moment a turn ends in a hidden window is one switch in the code, `DoneChimeWhilePutAway`, off: the user's decision still to take.
  - Ended for real: Session, End Claude and close this window, which asks FR-1.7's question while Claude is in the middle of something. The hand-over "end" (axHelp's Quit) is a request, never a forced close: a window with nothing to lose (Claude idle, nothing running in the background, the message field empty, no offered command waiting, no notice) closes at once; any other is brought up and asks, FR-1.7's question while Claude works, waits for an answer or runs something in the background, and for a message typed and not sent or an offered command not answered a question of its own, "Close this conversation?", which says what would be lost and whose default, Enter, is Keep it open. A window kept after an "end" has lost its keeper: from then on it closes on Alt+F4 as any axClaude window, with FR-1.7's question, until a "show" or a "message" says the keeper is back.
  - Who may hand over: the sender names a window of its own in the message, and the receiving window takes a hand-over, whatever its verb, only when that window belongs to a process of this very program file (`AppMessage.SenderRefusal`; the sender checks its target the same way, S-13). This stops a program that only knows the message's shape. It is not proof of the sender, since a program running as the user can name a window that is not its own; which is why a "message" is still said aloud (repairs R-07), an "end" never loses anything without a question, and a "show" only shows.
  - `--hidden`, only with `--hide-on-close` and a folder: the window starts put away, Claude started as in any start. It is shown once without activation and without a pixel (opacity 0, at its normal size, since Windows activates a window shown maximized; as a tool window and no app window, which Windows keeps out of the taskbar and out of Alt+Tab) and hidden in the same moment, so that every control exists and the conversation fills as in a window on view; its own frame and its saved state are put back before it is first seen. It takes neither the focus nor the foreground and says nothing; a trust question waits as above. A window never brought up saves no window place as it closes, since the user never placed it (it would write "not maximized" into the settings every axClaude window reads); one that was brought up saves as any window.
  - Owed, by ear and eye on a real desktop (the test desktop shows none of it): that the hidden start's one moment as a real window leaves no entry in the taskbar or Alt+Tab and no flicker; that its frame is right at the first showing after the style is put back; and the foreground on hiding and on a hidden start (nvda-test-plan section 20). Not tried: making the handles of the form and its controls without showing the window at all; a form never shown has no child controls made (`src/AxClaude/CLAUDE.md`), and forcing them one by one was judged more fragile than a showing nobody can see.
  - The cost: Claude Code and the window's process stay in memory while hidden.
- FR-9.7: **axKit's AI tools for every window's Claude** (2026-11-15 for axHelp's conversation, with the option `--ai-tools`, docs/axHelp/SPEC.md HE-2.8, HE-D10; every window since 2026-11-26, the priorities item "every window gives Claude axKit's AI tools from its start"; docs/axKit/mcp.md MC-6.9). When the user's own Claude Code file already names a server `axkit` in its user scope (MC-6.8, axKit added to Claude Code by the user: the top-level `mcpServers` of `.claude.json` in the profile, or in `CLAUDE_CONFIG_DIR` as Claude Code is started with it; `McpClaudeCode.NamesServer`, read only, a test run's own folder in a run), that entry gives the tools and the window names nothing a second time; the log says only that it was found, never anything of the file. ### FR-14 Claude Code's own settings

Asked by the user on 2026-11-15 ("an option to block Claude feedback requests ... if I want to focus", then widened the same day: "make an inventory of the Claude flags that you can set and then add menu items ... we could edit the Claude settings with code to make changes there that are not slash commands"). Claude Code's settings that a screen reader user would otherwise reach through `/config`'s 44 numbered rows or by editing a JSON file are offered as menu items. Decisions D37.

- FR-14.1: **One table, one place** (root rule 12): `AxClaude.Core/ClaudeCodeSettings` holds every setting offered, each with its id, its menu text, its group, how it reaches Claude Code (a slash command, or a top-level key of Claude Code's user settings file), its values (the first always Claude Code's own default, which is the key's absence), Claude Code's default, and when a change applies; with `CheckedWith`, the Claude Code version it was checked against (2.1.325, against the documentation's settings, settings-reference, env-vars, data-usage and commands pages). When `tools/upstream.ps1` reports a new Claude Code, the table is checked with the program's other places. The window builds its items from the table and knows no key or command of its own.
- FR-14.2: **The user settings file.** Claude Code's `settings.json` in its configuration folder: the folder `CLAUDE_CONFIG_DIR` names in the environment axClaude gives Claude Code, else `.claude` in the user profile (Claude Code's documentation: "On Windows, `~/.claude` means `%USERPROFILE%\.claude`"). Since `ClaudeLauncher.BuildEnvironment` leaves out every `CLAUDE*` variable (§7.4), that is the profile's today, whatever the user's own environment says; the path follows the launcher should that change. In a test run it is the run's own folder (`AutomationEnvironment.Home`), never the user's file. Never a project's `.claude/settings.json` or `settings.local.json`. A choice is written off the UI thread, one at a time: the file is read; one top-level key is set or removed and every other key and value kept (`ClaudeCodeSettings.WithKey`, System.Text.Json; the formatting becomes two-space indentation and the user's characters stay unescaped); a copy of the file as it was goes beside it as `settings.json.axkit-backup`, overwritten at every change; the new text is written beside the file and moved over it, so that Claude Code, which watches the file, never reads half of it. A missing file or folder is created. A file that is not one JSON object (a syntax error, a comment, a trailing comma, a key twice) is never written: the Error notice says why, with the line of a syntax error and the path, and the item's check goes back to what the file holds. The change is said with when it applies: "Claude Code's feedback requests blocked, applies at once" (Claude Code's documentation: "Claude Code watches your settings files and reloads them when they change"). The values are the table's fixed ones: nothing typed, and never a secret. The checks are read from the file each time Options opens (and before the command palette or the AI tools read the menu), since Claude Code's `/config` or the user may change it; a file that cannot be read checks nothing; a value the user set by hand that is none of the table's checks no item.
- FR-14.3: **The menus.** Options, Claude Code settings (C), between Questions and Text, check items and choices only, groups parted by separators: Block Claude Code's feedback requests (B; `feedbackSurveyRate: 0`, off removes the key) | ─ | Claude-drafted feedback: a card for each, Claude Code's default (C; no key) | Claude-drafted feedback: quiet, counted without a card (Q; `feedbackDrafts: "quiet"`) | Claude-drafted feedback: off, Claude drafts none (O; `"off"`; named as `/config` names the setting, so that Claude Code's own list title stays in `ClaudeCodeTexts` alone) | ─ | Hide tips while Claude works (T; `spinnerTipsEnabled: false`) | Hide the turn duration after each reply (D; `showTurnDuration: false`) | Hide the session recap after time away (R; `awaySummaryEnabled: false`) | ─ | No reply from Claude after my ! commands (N; `respondToBashCommands: false`). A check item is checked when the file holds the value that is not Claude Code's default; turning it off removes the key. Options because they are settings; one submenu deep (bundle AX-9.1). Every item is marked act (docs/axKit/app-kit.md AK-2.5): it writes a file outside axKit's settings, so an AI tool asks the user first. Actions: Choose the model… (O) and Choose the effort… (F), after Next permission mode: `/model` and `/effort` sent bare, as the user's own typed command would go, only while Claude is idle ("Not sent: Claude is busy" otherwise); Claude Code's own picker, which marks the current choice, comes up as a question in the control area (D33). Their value cannot be read from a file (`/model` saves to the `model` key, read only at start; `/effort` to `modelSettings`), which is why they are commands and not checks. `/model` saves the choice as the default of new sessions; `max` effort is for the session only (Claude Code's model-config page). Over Claude Code's stream, which has no pickers, the window shows a list of its own made from the answer to its first request and sends the command with the value chosen (docs/axClaude/stream-mode.md SM-5.5).
- FR-14.4: **Never offered**, from the inventory's risks: anything that turns screen reader mode off (`axScreenReader`, `CLAUDE_AX_SCREEN_READER`) or changes how Claude Code draws what axClaude parses (`tui` and `/tui`, the fullscreen and alternate-screen switches, `viewMode`, `/focus`, `statusLine` and `/statusline`, `maxProseWidth`, `syntaxHighlightingDisabled`, `prefersReducedMotion`, which each change rows or escape sequences and would need a recording first), `editorMode: "vim"` (it takes the keys axClaude types into the input), the modes and keys that skip permission checks (`bypassPermissions`, `--dangerously-skip-permissions`, `skipDangerousModePermissionPrompt`), `askUserQuestionTimeout` (no effect in screen reader mode), the parser's timing variables (`CLAUDE_AX_STARTUP_QUIET_MS`, `CLAUDE_AX_PREPARK_MS`), and settings that pour text into the conversation (`verbose`, `showThinkingSummaries`). Left for later, each with a reason: `permissions.defaultMode` (a key inside the object that holds the user's permission rules; it needs a change of a nested key), the output style (`/output-style` writes the project's local file), fast mode (costs more), error reports and telemetry (environment variables read at start, with consequences of their own: a start option with its explanation and the restart offer, a later item), prompt suggestions (whether they reach the hidden prompt row is not recorded).
- FR-14.5: **Beside axClaude's own feedback options** (D33): Options, Questions, Dismiss Claude's feedback surveys unheard answers a survey Claude Code shows; Block Claude Code's feedback requests keeps Claude Code from showing one at all. Both stay; the guide says which does what.

### FR-15 Events and grounding

How axClaude learns what happens in a session, and how the conversation it shows is tied to Claude Code's own record, is specified in `events-and-grounding.md` (asked by the user on 2026-11-15; requirement ids EG-n.m, decisions EG-D-n), which amends this document where its section 9 says so. In short: four sources, each for what it does best (the marks in the console stream, Claude Code's session file, hooks registered for the one session, and the screen as before), all taken as plain records in arrival order by one pure class, the core (`AxClaude.Core/Flow/SessionFlow`), whose decisions the window carries out.

- FR-15.1: **In stages** (EG-D-10). Stage 1 changes nothing the user hears: the core runs beside the window in shadow, and once for each turn the log says in numbers where the two differed (EG-4.11). Stage 2 moves the state, Done, reply speech and the background number to the core, one family for each commit; stage 3 is grounding. Which families the core is in charge of is a constant of the build; the file-only setting `eventCore` set to `shadow` puts all of them back in shadow without a rebuild (EG-9.6).
- FR-15.2: **As built on 2026-11-15**: the marks, the bell, every frame and every action of the user reach the core, which was in charge of nothing then. **Since 2026-11-17** (WP-A16) it is in charge of the state: whether Claude works, for the status bar (FR-10.2), the music (FR-7.9), every idle test of the window, and "Queued" with the held block (FR-4.7, D16); and (WP-A17, the same day) of Done (FR-7.2), with the settle after a bell left for a question and for the three cases FR-7.2 names; Say the event sources says "Core: in charge of state and Done.". With the state it also decides, since the same day, that a turn is one Claude Code began by itself, which the window says (FR-7.3b). Reply speech and the background number are still the window's own code's, compared in shadow. Options → Developer has the two switches and Say the event sources (FR-12.3), and Help → Diagnostics → Copy diagnostics gains the lines of EG-9.4, numbers and fixed words only. Hooks are passed (EG-2): with each start of a Claude Code at least as new as the events' table, the window passes axKit's own settings file and serves the pipe of that start, and each event is one more input of the core; not in the Store's copy, not when the user's own options for Claude Code name a settings file, and not with the switch off, in which cases the start is the start it always was. The session file is read (EG-3): its entries are inputs of the core too. Neither changes anything that is heard while the core is in shadow. What is still to come has its step of the build plan (`events-and-grounding.md` section 10), and this requirement is changed with it.

### FR-16 The stream as a second source (being built)

Claude Code's non-interactive stream as a second way for the window to learn what Claude does is specified in `stream-mode.md` (the maintainer's decision of 2026-11-17; requirement ids SM-n.m), which amends this document where it says so. ### 7.2 Data flow

```
ConPTY output pipe ──(reader thread, one BeginInvoke per burst)──> UI thread: LineStore.Feed (the base of SessionModel) = UTF-8 Decoder ──> VtParser ──> Screen
        ──(frame end: ESC[?25h, or 100 ms quiet)──> SessionModel.EndFrame (row text into lines, chrome, classification, echoes, status)
        ──Changed──> TranscriptView.Sync through TranscriptMirror (edits, caret) + announcements + status bar
Input field / menus ──> ConsoleForm write queue (paced writes, one pump timer) ──> ConPTY input pipe
```

Beside it since 2026-11-15, the core (FR-15; `events-and-grounding.md` EG-4.8, section 7.2):

```
SessionModel.Marked (OSC 133 A, C, D), LineStore.Bell, the pass after Changed (Arrivals.Update)   ─┐  each raised inside Feed, in the stream's order
the user's actions (a message sent, an answer, Escape, Send now, a screen's key, put away, a question shown) ─┤
Claude started, Claude ended                                                                         ─┤
the hooks' pipe and the session file's reader, each from a thread of its own, one post for a burst   ─┘  (MainForm.Hooks.cs, MainForm.Record.cs)
        ──> one queue on the UI thread ──> SessionFlow.Handle(input, time) ──> decisions, carried out in order before the next input is taken
        ──> the timer for the core's wake time, a note in the log, the record to follow or forget; every other decision to FlowShadow while its family is in shadow
```

### 7.3 Threading

- Reader thread (`PtyHost`): blocking `Read`; chunks are collected in an inbox and one `BeginInvoke` per burst drains it on the UI thread, so a large output never queues hundreds of window messages ahead of the user's keys; while recording, each chunk is also written to the `.vt` file.
- UI thread: owns the parser, the screen and the `SessionModel`. A frame ends at `ESC[?25h` or after 100 ms without output; `Changed` applies the view edits with redraw suspended (`WM_SETREDRAW`) and restores the caret (§7.7).
- Writes: a queue drained on the UI thread with a delay after each write (30 ms between lines, 100 ms before `\r`), one pump timer in the console window; a restart stops it, so that no second pump runs on (two ran, halving the pacing, until 2026-10-23).
- The core (FR-15): on the UI thread alone, never nested. Every input goes to the end of one queue and one loop drains it; an input raised while a decision is carried out is only queued (`MainForm.EnqueueFlow`). The core has no timer and no clock: it asks to be woken, and the window's one timer sends a tick. The hooks' pipe and the session file's reader each get a thread of their own that never touches the window and posts once for a burst; a post from a Claude Code that is no longer the window's is dropped, and the UI thread never waits for either (`events-and-grounding.md` section 7.2).

### 7.4 PtyHost

The one ConPTY implementation: five kernel32 calls, the std-handle guard (FR-1.4), the graceful stop (FR-1.7; it runs on the UI thread and is bounded, 2 s for the exit and 1 s for each thread, since Claude exits within moments of its console closing and the window takes no input between a stop and the restart or close that follows) and `Kill`, the stop at once for a confirmed restart or close while Claude is busy, a reader thread that hands every chunk to the callback given to `Start` and a wait thread that reports the exit code the same way (both callbacks are in place before the threads start, so nothing the child prints first is missed); `ClaudeLauncher` builds the command line and the environment (FR-1.2, FR-1.3) and asks `claude --version` for the log (FR-13.2). `tools/PtyCapture` records through both, so a fixture shows what the app sees. The console size is fixed (D9).

### 7.5 VT parsing and the screen model

The stream is interpreted by a headless screen model, not stripped with regular expressions, because ConPTY expresses in-place rewrites and cursor parking with cursor movement and erase sequences. The model is deliberately small.

**Screen** = `rows × cols` cells, cursor, saved cursor, scroll region, pending-wrap flag, `Dirty` flag per row. Every row carries a stable **line identity** (a `Line` created the first time the row receives text). Scrolling moves rows up and appends a fresh row; the row that leaves the top is **committed**: classified by its text if the frame-end pass never saw it, and shown if it was chrome at the last frame end but holds other text now (the first rows of a reply longer than the screen land where the spinner and the mode line stood and scroll off inside the frame). Insert-line creates a row at the insertion point (its line goes before the displaced row's line) and discards the row pushed out of the region; delete-line removes the row's line. Erasing a row keeps its identity, so a cleared and overwritten dialog updates existing lines. Rows below the cursor row are not part of the transcript. `DetachRows` (a repaint from the top, §4.4; axTerminal's cls) commits every row's line with the text it had and starts the rows blank, so that what the program draws next is new lines and nothing of the old text is read again as new (2026-10-23); `RowOf` and `EnsureLine` let a model keep a row by its line (axTerminal AT-D10).

**Frames.** `ESC[?25h` ends a frame; a 100 ms quiet period also ends one. Chrome, finality and announcements are evaluated at frame end only.

Handled sequences (Appendix A): printable text with wcwidth-aware cell placement and deferred wrap; CR, LF, BS, TAB, BEL (event); CSI cursor moves, erase, insert/delete, scroll, scroll region, save/restore; `ESC[?25h` (frame end); OSC 0/2 title (event); OSC 133 marks (event; axClaude takes A, C and D as a turn's marks, FR-15); DCS/APC/PM/SOS skipped; `ESC c` and `ESC[!p` reset. Every other sequence, including SGR and the other private modes, is ignored.

**Row text.** At frame end `PullRowText` copies the trimmed text of every dirty row into its line. Rows Claude hard-wrapped are flagged after classification (`JoinWrappedRows`, FR-3.2a) and joined by the mirror.

**Finality.** A line is `Committed` once its row scrolled off or the screen was reset; until then it may be rewritten. Echo handling and speak-replies treat a line as settled when it is committed, followed by another visible line, or Claude is idle.

**Robustness.** The parser produces the same transcript wherever chunk boundaries fall (tested with random splits), ignores unknown sequences without desynchronising, and caps numeric parameters at 65535. Partial scroll regions have not been observed; rows they discard are dropped silently.

### 7.6 Transcript model and classification

`Line { Id; Text; Kind; HeadingLevel; JoinedToPrevious; Committed; Hidden }`. `LineKind`: `Plain`, `InputMarker`, `OutputMarker`, `System`, `UserMessage`, `Bookmark`, `UserEcho`, `ClaudeReply`, `Thinking`, `Tool`, `ToolError`, `Error`, `Warning`, `Prompt`, `PromptOption`, `TurnSummary`, `Question`, `SideQuestion` (the record of a `/btw` side question, D33), `AnswerRecord`.

Classification runs at frame end for every uncommitted line, on the trimmed text: `^you:` UserEcho; `^claude:` ClaudeReply; `^thinking:` Thinking; `^tool:` or `(ctrl+o to expand)$` Tool; `^tool error:` ToolError; `^error:` Error; `^warning:` Warning; `^Permission Required:`, `^Enter selection`, `^Enter y/n`, `^Select with numbers` Prompt; `^\d+\. ` or `^[yn]\. ` within 12 visible lines after a Prompt → PromptOption; `^\S+ for … · done ` TurnSummary; `^\[Screen Reader Mode:` System; `^●\s+User answered Claude's questions:$` AnswerRecord, and so the visible rows directly under such a row that start with `· ` or continue a row of the record wrapped at the console width (FR-7.4b; a row scrolled away within one frame is classified without the rows above it, so only the label is known there).

Headings are structural (§4.4 item 3): inside a reply (from a `claude:` row up to the next tool, summary or other labelled row), a row of 1 to 80 characters that follows a blank row or sits on the `claude:` label row, does not end in `.`, `,`, `;`, `:`, `?` or `!`, is not a list item, has at least one letter and is followed by a blank row, is level 2. Rows outside a reply, such as tool output, never qualify, and neither does the last line of a code block, which follows another code line. Screen reader mode strips the hashes, so every markdown heading level reads as level 2; a line that still begins with `#`s uses the `#` count anywhere. The markers are level 1 (FR-4.1). App lines (`Line.IsMarker`: the markers, the message, system lines, bookmarks, the `Question:` records) are never reclassified or hidden; Claude's own `[Screen Reader Mode: …]` row is classified System by its text and counts as one from then on.

### 7.7 TranscriptView and TranscriptMirror

`TranscriptMirror` (Core, unit tested) holds the visible lines as one text with their start offsets, separators (`\r\n`, or a space for a `JoinedToPrevious` line, nothing when it starts with one), display line numbers for `l`, and the search behind Ctrl+F. `Update(lines)` compares the new visible list with the old one by line identity and separator (common prefix and suffix; everything between is replaced as one block together with the separator in front of it; a prefix or suffix line whose text changed is replaced on its own) and returns `MirrorEdit`s from the end of the text to its start (of two with the same start, an empty line that got its text and what follows it, the one further on in the text first, FR-3.3a) plus `MapPosition(oldCaret)`: the same column of the same line when it is still shown, otherwise the start of the next line still shown, or of the replacement. A frame with no visible change returns at once; otherwise only the entries after the first changed line are recomputed, and the line lists are reused between frames, so a spinner tick allocates nothing and no 20 000-entry list goes to the large object heap. The update is valid until the next call. Reading breaks (FR-3.10) live here too: `BreakAtEnd(caretColumn)` records the last line and its length as heard, the rendering of that line then carries a `\r\n` at the resolved column (or the next joined line starts with `\r\n` instead of a space), start offsets and `MapPosition` count the extra characters, `RenderedColumn` maps a text column through them, `DisplayTextAt` and the display line numbers ignore them, and `ClearBreaks` takes them away. The view marks the end when the caret is on the last screen row of the edit control (`EM_GETLINECOUNT`, `EM_LINEFROMCHAR`) and clears once the caret's display line is not the one with the breaks.

The view applies the edits with `Select` + `SelectedText` (EM_SETSEL / EM_REPLACESEL), never `Text = …`, with redraw suspended, then restores the caret through `MapPosition`. Output within 250 ms of a key press in the focused view is held until the keys stop, because NVDA reads the caret line in several messages and text that shifts between them is read wrong; announcements and the status bar are not held. Without focus, the caret goes to the start of the last line and the view scrolls to it with `EM_SCROLLCARET` sent directly: WinForms' `ScrollToCaret` first copies the whole text. Edits land at the bottom of the text, which keeps the word-wrapped EDIT control cheap; an edit near the top re-wraps everything below it (about 0.7 s at 20 000 lines, so a trim, FR-3.6, is a rare one-off).

### 7.8 Announcer

`Announce(text, interrupt)` → `RaiseAutomationNotification(ActionCompleted, interrupt ? MostRecent : All, text)` (`AxKit.Forms.Announcer`) on the conversation, or on the notice's text or field while one shows. On `false`, the selection fallback (FR-7.6).

### 7.9 Settings and command line

`AppSettings` loads `axClaude.json` through the bundle's `SettingsFile` with `System.Text.Json` (reflection based; the app is not trimmed), sanitises ranges, writes via temp-file rename. `StartupOptions` is a hand-written parser: unknown options before `--` are errors; everything after `--` is opaque.

## 8. Design decisions

- **D1 WinForms, not WPF.** Real Win32 controls (EDIT, menus, status bar) with the most mature NVDA support; no custom UIA providers.
- **D2 A read-only multi-line `TextBox` for the transcript.** A `ListBox` has no partial selection, word wrap or character review and its type-ahead conflicts with quick keys; `RichTextBox` is slower and quirky; a custom control has a large accessibility surface. The plain EDIT control is what NVDA's own log viewer uses.
- **D3 ConPTY with screen reader mode, not `-p --output-format stream-json`.** The user wants the CLI's own interactive behaviour (slash commands, prompts, dialogs, modes) with the rendering Anthropic maintains. Stream-json drops interactive prompts unless the undocumented control protocol is implemented. It remains the fallback; the transcript and view layers would be reused.
- **D4 Own P/Invoke, no PTY package.** Five functions; the reference implementation already works.
- **D5 .NET 10 (LTS)**; `global.json` pins the SDK feature band; self-contained single-file publish.
- **D6 A screen model with diffing rather than escape stripping.** §4.2–4.4 show in-place redraws and cursor parking; stripping would duplicate or garble lines.
- **D7 App markers plus Claude's labels.** The markers are deterministic and immediate; the labels give the inner structure.
- **D8 UIA notifications for announcements.** They speak without stealing focus or moving the caret; NVDA supports them since 2018.3. Fallback: selection.
- **D9 A fixed, wide console (240 columns).** Claude hard-wraps at the console width; 240 keeps most paragraphs on one logical line and the EDIT control wraps visually. The window never resizes the console.
- **D10 No auto-speak by default; since 2026-11-21, replies are spoken by default.** The first decision: the point is a calm, navigable buffer; the bell announcement and Alt+3 are the fast path; auto-speak is an option. The maintainer changed the default on 2026-11-21, with the first testers in mind ("we must speak claude results on by default when we package and deploy. we should use my current options as defaults"): a new install speaks every line of a reply (`replySpeech` `all`), with the working music and the louder alert in the background on and questions waiting after what is read, as he runs it himself. The options are as they were, and a settings file that exists keeps what it holds.
- **D11 Enter sends, Shift+Enter is a new line (1.5.1).** What Claude Code and most chat apps do, and one rule for the bottom of the window, where a list of answers or a field for the user's own words can take the message field's place (D33): Enter acts. Until 1.5.1 Enter sent and Enter was a new line, to keep the field an ordinary multi-line edit.
- **D12 No send lock.** Claude Code queues or steers with a message sent while it works; the app keeps the markers honest (FR-4.7) and says "Queued".
- **D13 No history recall in the message field.** Claude's own recall draws on the hidden prompt row, so it is unusable through the app, and plain Up and Down never reach Claude. The app's own recall (Up on the first line, Down on the last; 1.0.0 to 1.0.2) was removed on 2026-09-19: earlier text appearing and being spoken in the field on an ordinary arrow key was confusing, and the messages are in the conversation anyway (`i`, and Enter copies a line back).
- **D14 Ctrl+O is guarded.** Until 1.2.0 the app sent Ctrl+O to Claude because the tool summaries advertise it, and Change folder moved to Ctrl+N (since 2026-09-19 Ctrl+N is New session, FR-8.6, and Change folder is a menu item without a key). In screen reader mode the key is harmful: on an idle prompt it hides the prompt (§4.4 item 17), and while Claude works it redraws the conversation from the first message on screen downwards, as its detailed transcript and then as plain text again (item 19), so the app's transcript gained a second copy of every message and Speak replies read old replies again. The app no longer sends it: Ctrl+O announces why and points at `--verbose` (FR-7.4, item 18), the menu item is gone, and the model's detection of the detailed view stays as a safety net, in which case Ctrl+O is sent once to close it.
- **D15 System.Text.Json for settings.** Ships with the runtime.
- **D16 A message sent while Claude works stays out of the conversation until Claude takes it up.** Claude Code owns the queue and draws the waiting message; the app only reports it and prints the block when the echo arrives. Placing the markers at once put them in the middle of the running reply and moved them later. Since 2026-11-17 "while Claude works" is the core's turn, open or ending (FR-4.7, `events-and-grounding.md` EG-6.4), not the screen's spinner: the screen can show no sign of work while a reply's last rows are still on their way, and a block placed in that moment stood in front of them.
- **D17 Wrapped rows are joined in the view, not in the model.** Each screen row keeps its `Line`, so rewrites and caret mapping keep working; only the separator changes. File-only switch.
- **D18 Installation is a script.** `install.ps1` does everything a per-user installer would with no dependency, no elevation and nothing to sign. `install.cmd` is how a person starts it: a downloaded `.ps1` is refused by the default execution policy and blocked as a file from the internet, and a batch file is not, so it runs `install.ps1` with `-ExecutionPolicy Bypass` for that one run. Next to `install.ps1` (the zip, the installed folder) it passes its arguments on; downloaded on its own (a release asset of its own) it fetches the latest release's zip from the GitHub API into `%TEMP%\AxKit-install` and runs the `install.ps1` in it. The updater (D25) still runs `install.ps1` itself. The install also writes the Apps entry (`HKCU\Software\Microsoft\Windows\CurrentVersion\Uninstall\AxKit`: name, version, publisher, icon, location, size, no modify or repair), so Settings, Apps and Add or remove programs list axKit; its uninstall command is `install.cmd -Uninstall` in the installed folder, which removes the entry with everything else. `install.cmd` is one parenthesised block that ends with `(goto) 2>nul`: cmd.exe reads a block whole before running it, and the uninstall deletes the folder the batch file is in, which otherwise ends in "The system cannot find the path specified." Every install first removes a previous installation completely, of any version (every installer since 1.0.0 used the same places; those before 1.5.0 wrote no Apps entry), and says what it found ("Removing axClaude 1.4.0 (installed by the earlier installer) before installing..."), then installs fresh; the settings and the log stay. The updater runs the same script, so an update is a clean reinstall. `Remove-Installation` is shared by that and by Uninstall. Uninstall does nothing while axClaude runs from the installed folder ("axClaude is still running, so nothing was removed. Close it and uninstall again."), so the Apps entry and `install.cmd` stay to try again; any error nothing handles is said and written to the update log (`trap`), since the updater runs the script without a window; a download install deletes `%TEMP%\AxKit-install` afterwards, and the updater keeps only the version it installs under `%LOCALAPPDATA%\AxKit\updates`.
- **D19 The user guide is one Markdown file**, embedded for Help → User guide; the zip's `README.md` is the bundle's `docs/axKit/README.md`.
- **D20 Escape is guarded in the message field.** Blind users press Escape by reflex, and an unguarded one interrupted the running turn. Ctrl+Escape was the first choice, but Windows opens the Start menu on it, and swallowing it needs a global keyboard hook, which must not be installed next to a screen reader.
- **D21 Quoting a conversation line is a literal text block.** No protocol, no hidden state; the user edits or deletes it like any text. The marker under the quote tells Claude where the user's own words begin.
- **D22 The app prints the message itself; Claude's echo is only hidden.** Moving two markers around the echo broke as soon as a message held a blank line. The exchange block is text the app owns, printed once; the echo is matched by text with whitespace ignored and hidden. Nothing moves afterwards.
- **D23 The app never opens a second window of its own.** A screen reader user loses popup windows: a dialog next to the main window is easy to leave behind when the screen reader's focus moves, and then both are stuck. Every dialog is a notice drawn inside the main window by `OverlayPanel` (Find, the shortcuts, the guide, About, errors, the crash report, Claude Code was not found, the close question, the restart question, New session, the update notices); what Claude waits on goes to the control area at the bottom of the window instead (D33). Callers pass only content, a `Notice` record (title, text, buttons, at most one of a text field and the New session controls, and whether the user opened it), to the one `AxKitForm.ShowNotice` (the window base's, AX-6.5), which adds what every notice shares: the notice chime (`Sounds.Notice`) for a notice the user did not open (errors, Claude Code was not found, the update offer at startup), the focus, the hidden conversation and field, and the blocked menu; the panel itself (`OverlayPanel.Populate`) adds the last line of the text, made from the buttons ("Enter: Close anyway. Escape: Keep working.", "Enter or Escape: Close." for a single button; no notice words its keys itself, and a notice with no words of its own shows the key line alone, so there is always text to land on), a one-second hold on Enter and Space for a notice the user did not open, and the bundle's page and paragraph keys in its text (AX-8.2). A change to how notices look, sound or behave is made there once. A button's action may open a notice of its own (I accept all terms, install and restart opens the progress notice, Restart now can open an error): that notice stays, and the place kept for a reader of the conversation carries over to it. The only separate windows are the standard folder, file and font pickers, and the `--help`, `--version` and bad-command-line message boxes shown before any window exists.
- **D24 Performance is measured, not assumed.** The per-frame path (parser, `EndFrame`, mirror update, EDIT control edits) was benchmarked at 20 000 lines (2026-09-19). Three wastes were found and removed: a closure allocated on every iteration of the echo loop (700 KB a frame), the mirror's full rebuild on every frame, and WinForms' `ScrollToCaret` copying the text. A frame end now costs 0.12 ms and allocates nothing at 18 000 lines, down from 0.54 ms. No further machinery (virtualised views, background parsing) is warranted.
- **D25 Updates come from GitHub releases, and the user chooses.** A release is a version tag: GitHub Actions builds the same zip that `publish.ps1` builds locally and attaches it (`.github/workflows/release.yml`, started by `release.ps1`). The app asks for the latest release once at startup (an opt-out setting) and installs only after Update now: no background downloads, no server of the app's own, no installer beyond `install.ps1`, which already exists. Handing over to the new version's own installer means the running executable is never overwritten while it runs, and a failed update leaves the installed version in place. A download counts as complete when it holds `install.ps1` and a program file of any name (1.7.0): the versions after 1.7.0 ship as `AxKit.exe`, the bundle axClaude is one app of, and their `install.ps1` keeps the hand-over parameters of this one.
- **D26 Go-to keys speak even when nothing moves.** Ctrl+Tab toggles, so a user who has lost track of the focus does not know where it will land. Alt+1 and Alt+2 name a destination, and when the focus is there already the app says the control's name (the same words NVDA uses for a real focus change): one key, one answer, whether or not the focus moved. This is on demand only (the user pressed the key), so it does not conflict with the rule that navigation never speaks by itself.
- **D27 The disclaimer is in the app and the guide, not a click-through.** The binding text is the licence (`LICENSE`, the GNU AGPL 3 since 2026-10-29, MIT before) with the terms and the disclaimer of `NOTICE.md`, both shipped in the zip. About, Licence shows `NOTICE.md`; the end of the user guide repeats the disclaimer, add that everything typed goes to Anthropic under Anthropic's terms, that Claude Code changes files and runs commands under the user's permissions, and that the project is independent of Anthropic. A first-run acceptance screen would be one more notice for a screen reader user to get through and would protect no better.
- **D28 The line being written is read in pieces.** In a word-wrapped edit control, Down Arrow on the last screen row leaves the caret where it is, and NVDA then reads that whole row again. While Claude writes, the row grows, so every Down Arrow repeated what had just been heard. Holding output back does not help (the row still grows), and announcing the new text over a notification does not either (NVDA still reads the row). - **D31 Sounds are generated, not shipped, and play through open devices.** Short sine tones, noise bursts for the ticks and a soft pad loop for the music (a plucked loop until 2026-11-15), built in code (`WaveTone`): no media files, no package, and they reach a Remote Desktop client like any other audio. ## 11. Risks

| Id | Risk | Mitigation |
| :-- | :-- | :-- |
| R1 | ConPTY emits an unexpected repaint pattern that the screen model turns into duplicated or lost lines. | Screen model plus fixtures; Record raw stream captures the stream when it happens. |
| R2 | NVDA does not speak UIA notifications on some machine. | Selection fallback (FR-7.6). |
| R3 | Enter in the same chunk, bracketed paste through ConPTY. | Resolved by the recordings (§4.4 items 1, 8, 14). |
| R4 | Claude Code changes its labels or rendering. | Fixtures pin the version (`tests/fixtures/README.md`); a new fixture is recorded when screen reader mode changes (the `record-fixture` skill), not per version; patterns live in one class. |
| R5 | The EDIT control slows down on very large transcripts. | The cap (FR-3.6); edits land at the bottom (§7.7). |
| R6 | Slash-command autocomplete needs a second Enter. | Enter on an empty field sends a bare Enter. |
| R7 | The user's `tui: fullscreen` setting. | Ignored in screen reader mode; `CLAUDE_CODE_DISABLE_ALTERNATE_SCREEN=1` as belt and braces. |
| R8 | The heading heuristic misses a heading or promotes a short line. | Conservative rule; `o`, `d` and `c` give reliable coarse navigation. |
| R9 | Tool detail rows collapse at the end of a turn. | Matches the terminal; Record raw stream keeps everything. |
| R10 | Claude changes how a waiting message is drawn. | The `steering` fixture pins it; a change degrades to a visible echo, not scrambled markers. |

## Appendix A — Control sequences the screen model handles

C0: BEL (event), BS, HT (next multiple of 8), LF/VT/FF (line feed), CR, ESC. Other C1 and control bytes are ignored.

ESC: `7` save cursor, `8` restore, `D` index, `E` next line, `M` reverse index, `c` reset; sequences with intermediates (charset designations) are ignored.

CSI (parameters default to 1 unless noted): `A` up, `B` down, `C` forward, `D` back, `E` next line, `F` previous line, `G` and `` ` `` column, `H`/`f` position, `d` row, `J` erase in display (0/1/2), `K` erase in line (0/1/2), `X` erase characters, `@` insert blanks, `P` delete characters, `L` insert lines, `M` delete lines, `S` scroll up, `T` scroll down, `r` scroll region, `s`/`u` save/restore, `! p` soft reset. `? 25 h` ends a frame; every other private mode, SGR (`m`) and every query is ignored.

OSC: `0`/`2` title (event); `133` shell integration marks (event, with the letter: A, C and D are a turn's marks for axClaude, `events-and-grounding.md` EG-1.1); others ignored. DCS, APC, PM, SOS: skipped to ST.

Cell width: `Wcwidth` returns 0 for combining marks and format characters, 2 for East Asian wide and emoji ranges, 1 otherwise. Continuation cells are skipped when a row is read.

## Appendix D — Glossary

- **ConPTY / pseudo console:** the Windows API that lets a program host a console application and exchange a VT byte stream with it.
- **VT sequence:** an escape sequence that moves the cursor, erases text or changes modes.
- **Screen reader mode:** Claude Code's `--ax-screen-reader` rendering.
- **Marker line:** a line the app inserts (`# Input n`, `# Output n Reply from Claude`, `System:`).
- **Exchange block:** the input marker, the message, a blank line, the output marker, a blank line (FR-4.1).
- **Bookmark:** an app line `Bookmark n` that the reader drops in front of a line with `m` and finds again with `k` (FR-3.9).
- **Conversation, transcript:** the conversation is the control the reader sees and the keys act in (FR-3, FR-5); the transcript is the model behind it (`SessionModel`, the `Line` list, `TranscriptMirror`).
- **Quick key:** a single-letter navigation command in the conversation, modelled on NVDA browse mode.
- **UIA notification:** a UI Automation event that asks screen readers to speak a string without changing focus.
