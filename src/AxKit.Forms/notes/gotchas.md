# AxKit.Forms: gotchas of the Windows controls and NVDA

What the windows of the bundle learned about Windows Forms, the Win32 controls under them and NVDA, which holds for every
window and not for one app. They were written in axClaude's window notes, where they were found, and moved here word for
word on 2026-11-25 (docs/axKit/repairs.json R-89); "the app" in them is axClaude, where each was met. Read this before
changing a control, a notice, a sound or an announcement of any window.

- `FindForm` is not a usable class name in a `Form`: it hides `Control.FindForm()`.
- `Control.Visible` is false for every child while the form itself is not shown, and `Button.PerformClick` does nothing then (`CanSelect` is false). The notice state is therefore a flag in the window base (`AxKitForm.NoticeOpen`), not the panel's `Visible`, and the off-screen probe reads each control's own state (`Control.GetState(States.Visible)` by reflection) and fires clicks through `OnClick`. The focus after a notice is the base's one rule (AX-6.5): the window only derives `KeepCaret` from the control the base remembered.
- The control area's lists are `ListBox` and `CheckedListBox`: NVDA announced a `ListView` in Details view as a table. An exception in an event handler of an off-screen probe opens WinForms' error dialog, which waits unseen and looks like a hang; run such probes inside a message loop (`Application.Run` with a timer) and suspect an exception first.
- A form's `AcceptButton` and `CancelButton` are the way to make Enter and Escape reach a notice's buttons from a read-only multi-line `TextBox` (`AcceptsReturn` off) and from the single-line field; Enter on a focused button presses that button, as in a real dialog. The window's own shortcuts and the menu's are skipped by returning from `ProcessCmdKey` without calling the base while a notice shows; Alt and F10 alone are `WM_SYSCOMMAND` `SC_KEYMENU` with a zero low word of `lParam`, swallowed in `WndProc`.
- Ctrl+Escape is a Windows system key (Start menu) and never reaches the app; Alt+Escape and Ctrl+Shift+Escape are taken too. The app's interrupt key is Ctrl+I (Shift+Escape until 2026-11-26), and plain Escape in the message field is a guard that only announces it (FR-2.3, D20).
- A `ToolStripStatusLabel` that does not fit the strip (or has `Spring`) is not exposed to UI Automation; `StatusLayout` gives both labels fixed widths when their texts do not fit.
- WinForms' `TextBoxBase.ScrollToCaret` (and every `Text` read) copies the whole edit-control text first: about 1 ms per call at 20 000 lines, on every frame while the message field has the focus. The view sends `EM_SCROLLCARET` itself. An edit near the top of a word-wrapped EDIT control re-wraps everything below it (0.7 s at 20 000 lines); streaming edits land at the bottom and cost nothing, so keep it that way and keep the transcript cap.
- `EM_SCROLLCARET` is ignored by an edit control that does not have the focus, so an off-screen probe cannot rely on it (nor can code that runs while the other control has the focus): scroll explicitly with `EM_LINESCROLL` against `EM_GETFIRSTVISIBLELINE`, as `EditKeys.Page` does. The native Page Down of a three-row field does nothing while the text fits it, which is why the field has the app's paging too.
- winmm `PlaySound` opens and closes the audio device on every call and backs up when called in quick succession: the ticks stuttered and were reported as clogged (1.2.1), and its `SND_NOSTOP` flag silenced them for good once the device never finished a sound (1.1.0). `Sounds` keeps one `waveOut` device open for the life of the process, prepares every sound's buffer once and plays it with a single `waveOutWrite`. A chime calls `waveOutReset` first (it replaces whatever plays); a tick is dropped while its own buffer is still queued (`WHDR_INQUEUE`), so a tick during a chime follows the chime and ticks never pile up. The wave data and the headers are pinned or unmanaged for the life of the process, since the device reads and writes them after the call returns. The working music (SPEC.md FR-7.9) loops as one buffer with `WHDR_BEGINLOOP | WHDR_ENDLOOP` and an endless `dwLoops`, set before each write (after `waveOutPrepareHeader`, which wants the flags clear), on a second device: on the chimes' device a chime's reset would cut it off and a tick would wait behind it for ever. The recurring chords of background work, 4.6 s each, have a third device for the same reasons, and are made at their first use off the UI thread (some tens of milliseconds each). All are one `Device` class inside `Sounds`; there is no second code path.
- UIA notifications raised back to back are not all spoken: NVDA read the first few of a burst of per-line notifications and dropped the rest. Claude prints a whole message in one frame in screen reader mode, so anything spoken per line must be joined into one notification per frame (`Arrivals` in Core, SPEC.md D32).
- The EDIT control's Ctrl+Up and Ctrl+Down scroll the view one row and leave the caret where it is, as Notepad's do; a screen reader hears nothing for them. `EditKeys.Paragraph` gives them Word's meaning with the `p` key's blank-line rule for a paragraph (SPEC.md FR-2.1, §6.4). Two other meanings were tried and dropped in 2.4.0: a paragraph as a whole logical line, and a step of one line keeping the column (that is what the plain arrows do by row). The rule the user settled on is "the first line after a blank line", the same in every edit control of the bundle.
