# AxKit.Forms: AI help, the AI tools and the automation channel

Part of the notes of `src/AxKit.Forms` (the index is `src/AxKit.Forms/CLAUDE.md`). One bullet per piece.

- `AutomationChannel` (docs/axKit/automation.md, 2026-10-23): a window's automation pipe, `axkit-auto-<process id>`, opened by the window base's `OnShown` only when `AXKIT_AUTOMATION` is set (the test runner `tools/AxAutomate` sets it, and `AXKIT_HOME` for the run's own files): keys posted to the focused control with the modifiers in the thread's keyboard state, characters, the focus, what was announced (`Announcer.Raised`), the window's state, a menu command by its palette name, close. Menu mode of the menu bar cannot be driven this way (it needs the foreground); `menu` runs the command instead.
- AI help (docs/axKit/ai-help.md, 2026-11-09): `AxKitForm.Ai.cs`, the window's part of the one shared service: `CreateClaudeMenu` (axKit, Claude ▸, AX-9.1: Use Claude in axKit, read as the menu opens; Ask about this window, Shift+F1; Folders Claude may read; Claude's working folder; the AI tools submenu), `ToggleAiHelp` and `TurnOnAi` (off at once, "Claude off"; on through the AX-11.4 consent, recorded under the app "AI help" through `HasConsent`'s app parameter and `ConsentTarget.AiHelp`, then "Claude on" and the ask that was in hand: whatever asks for Claude while it is off comes here, AH-1.3, 5.6.0), `AskAboutThisWindow` (AH-6: `AskText` for the question, the window's context from `AppTitle`, `Text`, `FocusDescription`, `Shortcuts`, the guide kept by `CreateHelpMenu` in `_userGuide`, and `Recent.Lines`, redacted), `AskClaude(prompt, extraFolders, resume, then)` (`AiReady`: off turns Claude on through `TurnOnAi` and asks again, Claude Code missing is a notice with Install it now, the consent; then the "Asking Claude" notice with Cancel, `AiRequest.AskAsync` awaited in `Do`, cancelled through one `CancellationTokenSource`), `ShowAnswer` ("Claude says": the text first through `Notice.FocusText`, the field "Ask more about this answer" whose Enter resumes the session, Copy, Close with the caller's action; an error as "Claude could not answer"), the folders notice with Add (the folder picker) and Remove (one button per folder), naming Claude's working folder, and `AiWorkingFolder` with `OpenAiWorkingFolder` (AH-2.1, AH-D6, 2026-11-09: `Documents\axKit Claude` made when missing, the one folder Claude Code starts in; the axKit menu's Claude, Claude's working folder item opens it in axFile). `WindowOwner.Describe(window)`: the program and the title of another program's window, for axHelp's and axDescribe's prompts.
- The AI tools (docs/axKit/mcp.md MC-6, 2026-10-24): `McpChannel`, a window's pipe `AxKit-mcp-<SID>-<random>` (one connection, one request: the client must run this very program file, the setting must be on, the key's challenge answered; then `hello`, `state`, `list`, `text`, `commands`, `said` or `pair`, read on the window's thread; none for axPass and axClip); `McpBroker`, `AxKit.exe mcp`, which the AI client starts (stdio, the rate, the pairing in the newest window, the tools, the audit line); `AxKitForm.Mcp.cs`, the window's part (the pipe started in `OnShown`, the axKit menu's AI tools submenu (`CreateMcpMenu`: on with one confirming notice, Add axKit to Claude Code through Claude Code's own `claude mcp add`, never in a test run; Forget; Read the log), `McpState`, the pairing notice with Deny as default, unprompted, the taskbar flashed). The runner drives it as a client (`tests/scripts/mcp`).
  Since 2026-11-11 (MC-7) the pipe's `run` request: the channel reads the sealed switch on its own thread and hands it to `AxKitForm.McpRunCommand` on the window's thread (the refusals, the user typing in the window in front among them through `GetLastInputInfo`; an act command asked of the user by `AskToRunMcp` through the interface of an offered command (MC-7.3, 2026-11-13: an `OfferedRequest`, the list's name, the explanation and the answers, shown by the virtual `ShowOfferedRequest`: over the whole window by default, the sections hidden through `HideForNotice` and kept hidden when the explanation's notice closes; at the bottom in `ConsoleForm` and `TextEditorForm` through `ShowOfferedRequestIn`, which plays `Sounds.Offer`, opens Explain as a notice and calls the answer once the list has gone; a notice only when the place is taken), naming the window's selection from the virtual `McpTarget` (axFile, axStart, axProcess, axGIT and `ItemForm` override it), whose Run is refused when that selection changed and reads the switch again through `Task.Run`; any other posted with a ticket, checked again by `WhyNotRunForMcp` and run by `RunForMcp`, which says "Claude ran ..." through `AnnounceBefore`, joined to the command's own words, chimes and flashes a window that is not in front, and clicks the item), the channel listening to what the window says until it is quiet, then `McpAfterRun(ticket)`, so that the answer says `ran` only for a command that ran; a run keeps the entry's name and menus and finds it again among the entries at the moment it runs (`ToolItem` over `CommandPalette.Find`), posted or after the user's Run, so that what is clicked is live, enabled and still what was named (docs/axKit/repairs.json R-08). The switch Let AI tools run commands is a plain item of the AI tools submenu, never a command of the list, so no client runs it.
  Since 2026-11-13 (MC-9) `axkit_offer_command`: the broker's `Offer` sends it to the axClaude window whose process is an ancestor of the broker's (`ThisProgram.ParentOf`; each window's `hello` carries its process id) or to the axClaude window the client names, as the pipe's `app` request; the window's own code asks the user.
  Since 2026-11-11 (MC-8) the typed data tools: the broker's `AppTool` sends `McpTools.AppTools`' tools to the newest window of their app as the pipe's `app` request (none open: the answer says to open one); the channel reads the switch on its thread and calls `AxKitForm.McpApp` on the window's thread, which refuses what every app refuses (axPass and axClip, another app's tool, for a change the switch and `McpChangeRefusal`: a notice, a dialog, the user typing in the window in front, shared with the run) and hands the rest to the window's `protected virtual McpAppRequest`, null for a tool it does not answer (axTask's `TaskForm.Mcp.cs` is the one override; an answer may be a `Task<object>` the pipe's thread waits for, for a long read off the window's thread); a request the window's thread has not taken up in 10 s is given up for good (a flag both threads swap), so a client told it failed never gets a second item, and one taken up is waited for to 20 s in all (MC-8.5); `ChimeForMcp` is the chime and flash of a window behind, shared with the run. No app is named here.
- `ThisProgram` (S-13; from `AppMessage` on its second use, the MCP pipes, 2026-10-24): whether a process runs this very program file, by its image path; `ParentId`, the broker's client. `UserPipe` (S-11; from the automation channel, the MCP pipes): the pipe access list for the user alone, the network denied, and the process at the other end. `WindowReading` (from the automation channel, the MCP pipes): a control's value as NVDA reads it, a hidden field as "protected", the first visible list or text of a window, the caret's line.
