# AxKit.Forms: AI help, the AI tools and the automation channel

Part of the notes of `src/AxKit.Forms` (the index is `src/AxKit.Forms/CLAUDE.md`). One bullet per piece.

- `AutomationChannel` (docs/axKit/automation.md, 2026-10-23): a window's automation pipe, `axkit-auto-<process id>`, opened by the window base's `OnShown` only when `AXKIT_AUTOMATION` is set (the test runner `tools/AxAutomate` sets it, and `AXKIT_HOME` for the run's own files): keys posted to the focused control with the modifiers in the thread's keyboard state, characters, the focus, what was announced (`Announcer.Raised`), the window's state, a menu command by its palette name, close. Menu mode of the menu bar cannot be driven this way (it needs the foreground); `menu` runs the command instead. `activate` (the NVDA tier) answers `ok`, whether the window is in front, and `menu`, whether its menu bar is in the keyboard's hands (`MenuBarActive`: an item selected or open with the mouse elsewhere), which the runner asks after it took the foreground with an Alt key press (2026-11-15).
  Since 2026-11-15 (docs/axKit/user-workflows.md WF-2.1 to WF-2.5, section 5.2) the window lists its commands as data, so that a script can name a command and never its key. A key's name in `keys` is one of `AxKit.Core/KeyChord`'s (the channel's own table of names until then; `ParseKey` asks `KeyChord.Code`). A menu item holds the key it shows as a value: `CommandPalette.Keyed(item, key)`, called by the base's `Item` for every command and every item it makes, and by hand for Send a report and Say the status, which set their own text from a bundle key; `CommandPalette.KeyOf` reads it, `MenuEntry.KeyData` gives it with the entry, and `BundleKeys.Chord` writes it in the vocabulary's words ("ctrl+shift+w"; empty for a key without a name). The text a menu shows is never parsed; an item whose text describes a place ("Alt+F4", "Enter in the message field") and the editor shell's Cut, Copy, Paste and Select all, whose keys are the edit control's own, have a key text and no key (WF-D-30). `AddKey` also keeps its command in `_keyOnly`, which tells a key with no menu item from a command's key. The request `commands data` answers `AxKitForm.CommandRows` (`AxKitForm.Commands.cs`): the entries of `CommandPalette.Entries` and every command with a key, each with whether its `When` holds now (none while a notice shows: the base's key handling runs no command then), made into rows by `AxKit.Core/CommandListing.Rows`, with the app's name and the open notice's title. `Execute` sends the text `CommandListing.Write` gave as it is, never through the serializer the other answers go through: serialized once more it is a JSON string, which `CommandListing.Read` takes for no listing. `commands` alone answers the palette's lines as before. The request `choose` with a JSON object of `label` and `menu` runs `AxKitForm.Choose`: the entry of exactly that name and those menus (`CommandPalette.Find`) clicked as the palette clicks it, a check item's new state said through `Announcer.Raise`; its refusal, "no menu item ... now", is the answer's error. No window's behaviour changed with this: the menus, the keys, the palette and the AI tools' list read what they read before.
- AI help (docs/axKit/ai-help.md, 2026-11-09): the window's part of the one shared service, in two files since 2026-11-14 (R-15). Settings changed outside axKit (AH-1.1a, the bundle's seal): `AiHelpFlow.ChangedOutside` saves them as now in use, shows the notice once and ends what was asked; the switch, a question and Folders Claude may read go through it. `AxKitForm.Ai.cs` keeps the menu, `CreateClaudeMenu` (axKit, Claude ▸, AX-9.1: Use Claude in axKit, read as the menu opens; Ask about this window, Shift+F1; Folders Claude may read; Claude's working folder; the AI tools submenu), `ContextOfThisWindow` (what the window knows about itself, with the guide kept in `_userGuide`) and the members a window calls (`AskAboutThisWindow`, `AskClaude`, `ShowAnswer`, `ShowAiFolders`, `AiWorkingFolder`, `OpenAiWorkingFolder`), each one line onto `AiHelpFlow`, the plain class the window holds, which has the question that waits (one `CancellationTokenSource`) and does the work: `ToggleAiHelp` and `TurnOnAi` (off at once, "Claude off"; on through the AX-11.4 consent, recorded under the app "AI help" through `HasConsent`'s app parameter and `ConsentTarget.AiHelp`, then "Claude on" and the ask that was in hand: whatever asks for Claude while it is off comes here, AH-1.3, 5.6.0), `AskAboutThisWindow` (AH-6: `AskText` for the question, the window's context from `AppTitle`, `Text`, `FocusDescription`, `Shortcuts`, the guide kept by `CreateHelpMenu` in `_userGuide`, and `Recent.Lines`, redacted), `AskClaude(prompt, extraFolders, resume, then)` (`AiReady`: off turns Claude on through `TurnOnAi` and asks again, Claude Code missing is a notice with Install it now, the consent; then the "Asking Claude" notice with Cancel, `AiRequest.AskAsync` awaited in `Do`, cancelled through one `CancellationTokenSource`), `ShowAnswer` ("Claude says": the text first through `Notice.FocusText`, the field "Ask more about this answer" whose Enter resumes the session, Copy, Close with the caller's action; an error as "Claude could not answer"), the folders notice with Add (the folder picker) and Remove (one button per folder), naming Claude's working folder, and `AiWorkingFolder` with `OpenAiWorkingFolder` (AH-2.1, AH-D6, 2026-11-09: `Documents\axKit Claude` made when missing, the one folder Claude Code starts in; the axKit menu's Claude, Claude's working folder item opens it in axFile; since 2026-11-15, AH-7, `AiWorkingFolder` also writes axKit's guides into it through `AiDocumentation.Write`, where missing and again by a new version, a failure logged and nothing more; the AI tools' rule file, `AxKit.Core/Ai/AiToolsRule`, AH-8, is one of those files). `WindowOwner.Describe(window)`: the program and the title of another program's window, for axHelp's and axDescribe's prompts.
- The AI tools (docs/axKit/mcp.md MC-6, 2026-10-24): `McpChannel`, a window's pipe `AxKit-mcp-<SID>-<random>` (one connection, one request: the client must run this very program file, the setting must be on, the key's challenge answered; then `hello`, `state`, `list`, `text`, `commands`, `said` or `pair`, read on the window's thread; none for axPass and axClip); `McpBroker`, `AxKit.exe mcp`, which the AI client starts (stdio, the rate, the pairing in the newest window, the tools, the audit line); `AxKitForm.Mcp.cs`, the window's part (the pipe started in `OnShown`, the axKit menu's AI tools submenu, `CreateMcpMenu`, `McpState`, `McpMainText`, the text `text` reads: the focused text, else the first of several lines, and the view of a `ConsoleForm` wherever the focus is, 2026-11-15, the focused field named beside it, and everything of a run, below); `AiToolsSetup` (out of the window base, 2026-11-14, R-15), the plain class the window holds for what the submenu's items do (on with one confirming notice, Add axKit to Claude Code through Claude Code's own `claude mcp add`, never in a test run; Forget; Read the log) and for the pairing notice with Deny as default, unprompted, the taskbar flashed (`AskToPairMcp`, `EndMcpPairing`, which the pipe reaches through the window's members of the same names); it keeps nothing itself, the sealed setting does. The runner drives it as a client (`tests/scripts/mcp`). Beside that registration for every folder, one conversation gets the tools by itself (MC-6.9, 2026-11-15): axClaude's `--ai-tools`, axHelp's, puts `--mcp-config` with `AppPaths.McpClaudeConfigFile` on Claude Code's line while the setting is on (`AxKit.Core/Mcp/McpClaudeCode.ConfigText`, `SessionArguments`, `WriteConfig`); nothing of it is here, and the consent is not touched by it.
  What did not move (R-15's note): the run (`McpRunCommand`, `AskToRunMcp`, `RunForMcp`, `McpAfterRun`, with the ticket, the minute after a Deny and the chime's time) and the request list (`ShowOfferedRequest`, `ShowOfferedRequestIn`) stay in the window base, since they read and set the window's notice, dialog, focus and menus in many places and call three hooks (`McpTarget`, `ShowOfferedRequest`, `NoticeChime`).
  Since 2026-11-11 (MC-7) the pipe's `run` request: the channel reads the sealed switch on its own thread and hands it to `AxKitForm.McpRunCommand` on the window's thread (the refusals, the user typing in the window in front among them through `GetLastInputInfo`; an act command asked of the user by `AskToRunMcp` through the interface of an offered command (MC-7.3, 2026-11-13: an `OfferedRequest`, the list's name, the explanation and the answers, shown by the virtual `ShowOfferedRequest`: over the whole window by default, the sections hidden through `HideForNotice` and kept hidden when the explanation's notice closes; at the bottom in `ConsoleForm` and `TextEditorForm` through `ShowOfferedRequestIn`, which plays `Sounds.Offer`, opens Explain as a notice and calls the answer once the list has gone; a notice only when the place is taken), naming the window's selection from the virtual `McpTarget` (axFile, axStart, axProcess, axGIT and `ItemForm` override it), whose Run is refused when that selection changed and reads the switch again through `Task.Run`; any other posted with a ticket, checked again by `WhyNotRunForMcp` and run by `RunForMcp`, which says "Claude ran ..." through `AnnounceBefore`, joined to the command's own words, chimes and flashes a window that is not in front, and clicks the item), the channel listening to what the window says until it is quiet, then `McpAfterRun(ticket)`, so that the answer says `ran` only for a command that ran; a run keeps the entry's name and menus and finds it again among the entries at the moment it runs (`ToolItem` over `CommandPalette.Find`), posted or after the user's Run, so that what is clicked is live, enabled and still what was named (docs/axKit/repairs.json R-08). The switch Let AI tools run commands is a plain item of the AI tools submenu, never a command of the list, so no client runs it.
  Since 2026-11-13 (MC-9) `axkit_offer_command`: the broker's `Offer` sends it to the axClaude window whose process is an ancestor of the broker's (`ThisProgram.ParentOf`; each window's `hello` carries its process id) or to the axClaude window the client names, as the pipe's `app` request; the window's own code asks the user.
  Since 2026-11-11 (MC-8) the typed data tools: the broker's `AppTool` sends `McpTools.AppTools`' tools to the newest window of their app as the pipe's `app` request (none open: the answer says to open one); the channel reads the switch on its thread and calls `AxKitForm.McpApp` on the window's thread, which refuses what every app refuses (axPass and axClip, another app's tool, for a change the switch and `McpChangeRefusal`: a notice, a dialog, the user typing in the window in front, shared with the run) and hands the rest to the window's `protected virtual McpAppRequest`, null for a tool it does not answer (axTask's `TaskForm.Mcp.cs` is the one override; an answer may be a `Task<object>` the pipe's thread waits for, for a long read off the window's thread); a request the window's thread has not taken up in 10 s is given up for good (a flag both threads swap), so a client told it failed never gets a second item, and one taken up is waited for to 20 s in all (MC-8.5); `ChimeForMcp` is the chime and flash of a window behind, shared with the run. No app is named here.
- `ThisProgram` (S-13; from `AppMessage` on its second use, the MCP pipes, 2026-10-24): whether a process runs this very program file, by its image path; `ParentId`, the broker's client. `UserPipe` (S-11; from the automation channel, the MCP pipes): the pipe access list for the user alone, the network denied, and the process at the other end. `WindowReading` (from the automation channel, the MCP pipes): a control's value as NVDA reads it, a hidden field as "protected", the first visible list or text of a window, the caret's line.
