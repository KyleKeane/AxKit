# AxClaude.Core: the stream

Notes of `src/AxClaude.Core/Streaming`, moved out of `src/AxClaude.Core/CLAUDE.md` word for word on 2026-11-17, when that file neared its limit; the rest of the pure code's notes are there. The specification is `docs/axClaude/stream-mode.md`; what the recordings of the real stream showed is `tests/fixtures/streams/README.md`.

- `Streaming/ClaudeCodeStream.cs` (2026-11-17; root rule 12, a place of Claude Code's beside `ClaudeCodeHooks` and `ClaudeCodeTranscript`): Claude Code's non-interactive stream, the options that start it, the lines a host writes (`UserLine`, `InterruptLine`, `ModeLine` for the permission mode, the permission tool's `AllowAnswer`, `AlwaysAnswer` (a rule of the session's alone, written to no file), `QuestionAnswer`, `DenyAnswer`) and a line of its output read down to a neutral `StreamLine` of `StreamPart`s (`Read`, tolerant: what is not understood is `StreamKind.Unknown`, never an exception; the start line also gives `Session`, an id that is never shown or logged, and `Commands`, the slash commands the run takes; a status note gives `Status`), with `ShapeOf`, a line's keys without a value. The window's stream source starts Claude Code with `StartArguments` (the stream's options, each message sent back, the relay's file and tool, the window's model, the user's own arguments last; no permission mode is ever named and the session is never kept out of the store), and it is what `tools/ClaudeProbe stream` measures with. `NextMode` is the round of the window's mode key: the three modes every run has, then each other mode the run was itself in, so that the key never reaches the mode that asks nothing unless the user started Claude Code with it. `Interrupted` tells the end line of a turn the user interrupted from a failure. The report is `docs/axClaude/stream.md`; `ClaudeCodeStreamTests`; `ClaudeCodePlacesTests` counts the file as a place. What a model needs of a line (2026-11-17, stage 2 of docs/axClaude/stream-mode.md): a message come back is a `StreamKind.Message` with its text, a slash command's print come back a `CommandOutput`; a call has its `Call` and what it is `About`; a failed result its first line, unless the words are meant for the model alone (`RefusedWords`, which a host's permission tool answers a refusal with); the note that lists the work in the background gives `Tasks` (`StreamTask`); an end line its `Turns`; `ModeWords` says a mode as the screen's mode line does; the notes a model acts on have names (`StatusNote`, `CompactedNote`, `ClearedNote`, `CompactingStatus`). `InitializeLine` is the request a host sends first, measured and not documented for the command line: its answer, a `StreamKind.Control` line, gives the permission mode in force and the version before any message (the fixture `start`); the account and the lists it also holds are never read.
- `Streaming/StreamModel.cs` (2026-11-17): the stream's model, the second on `ClaudeModel`: `Take` a line read down, `Send` a message the window writes, `Ask` and `Answered` for a question the relay passes on. It gives the conversation the screen's labels and markers (`ExchangeBlock` of the base, shared with `SessionModel`), and every line is final as it is added. Its rules are what the recordings in `tests/fixtures/streams` showed (their `README.md` says each), never the documentation alone: Claude works from a message written while idle, or a start line, until an end line that leaves no message of the window's still to come back (the end line's own count of waiting messages is wrong for a message written while a reply was being written); a message's block goes in at once when Claude was idle and else when its line comes back, also inside a running turn; a text is a slash command's print, and no reply, while a command the window sent has no end line yet and no message has come back; a start line with no message waiting and no command running is a turn Claude Code began by itself (`TurnSelfStarted`); a failed or refused call's line becomes `tool error:`; a question of Claude's is a call that gets no line; a subagent's own lines are left out; the end of a turn of the model's rings the bell (`LineStore.RaiseBell`), also when the turn failed, whose error line starts the response as the screen's error row does; an interrupted turn says Interrupted and rings none, and the end of a command Claude Code ran by itself, which counts no turn, rings none; a turn that began with a command awaited and no message is that command's (`_commandTurn`), whatever turns its end counts, so that a skill or a custom command, which runs the model, is no longer awaited after its turn. `StreamModelTests` replays every fixture through `StreamReplay` against its `expected.txt` (`AXCLAUDE_UPDATE_EXPECTED=1` writes them, to be read through) and says each rule in a test of its own. A new behaviour of the stream is recorded first (`tools/ClaudeProbe stream --record`), then the model is changed. The window's stream source feeds it (`src/AxClaude/MainForm.Stream.cs`): `WorksIn` is told the folder with every start, since a window keeps its model while its folder changes; `ModeName` and `ModesSeen` are Claude Code's own names, for the mode key; a turn the user interrupted adds the line `System: Interrupted` and says the word, since no Done follows.
- `Streaming/StreamHost.cs` (2026-11-17): a program as one process over three pipes, for the stream (`StreamHostOptions`: the `ProgramLine`, the folder, the environment whole). It knows no word of Claude Code's. Three background threads: the output line by line, the error output drained, and the input written from a queue, since a pipe's write waits while the program does not read; `lineReceived` and `exited` are called on those threads and only post. The end is reported once, after the error output was read to its end, with the exit code; `Write`, `CloseInput` (Claude Code ends when its input ends), `Kill` (the program with what it started). What the program writes as errors is kept in part (`ErrorTail`) for the user to be shown and is never logged. `End` closes the input, which is how a Claude Code that is idle is told to end, and ends the program after a grace when it has not ended, on a thread of the pool: the caller never waits. `StreamHostTests` runs it against Windows' own programs. The window's stream source runs Claude Code in it.
- `Streaming/AskRelay.cs` (2026-11-17, stage 3): the verb `AxKit.exe ask`, the permission tool of a Claude Code run over its stream, decided first in `Program.Main` as `HookRelay`'s verb is. `Serve` is the server's loop over two text streams (MCP's JSON-RPC, one object a line: `initialize`, `tools/list`, `tools/call`; the tool's input schema is `ClaudeCodeStream.PermissionToolInputSchema`, Claude Code's words); `Ask` passes one question to the window's pipe and reads the answer, both as frames of `HookFrame`, which serves a second kind of pipe through its overloads with a prefix (`PipePrefix`, `Variable`: the name and the secret come from the environment the window gives Claude Code, never from a file; a name of another pipe is refused); `ConfigText` is the configuration for `--mcp-config`, with the program and the verb and nothing of the pipe; `ToolName` is what `--permission-prompt-tool` is given. It holds no logic and fails closed: null from the window, an exception, a wrong secret, or a text that is no answer (`IsAnswer`: an object whose `behavior` is allow or deny) all become a no with `NoWindowWords`. It waits for the user without a limit. `AskRelayTests` (both sides stood in, and one real pipe); live, `tools/ClaudeProbe stream` plays three cases with the probe as the window's end (`relay`, `relay-refused`, `relay-gone`). `WriteConfig` writes the configuration's file when it is missing or names another program, whole or not at all. The window's stream source names the relay at every start of Claude Code and serves the pipe (`AskChannel` in `src/AxClaude/MainForm.Stream.cs`): the question's frame in, the answer's frame out when the user has answered.
- `Streaming/StreamAsking.cs` (2026-11-17, stage 5; docs/axClaude/stream-mode.md SM-7.4 to SM-7.6): one question of Claude Code's permission tool as the window asks it, pure. `ClaudeCodeStream.ReadAsk` reads the question down first (`StreamAsk`: the tool, the call, what it is about, the input as it came, and for Claude's own question tool the `AskQuestion`s with their `AskChoice`s). A tool call is one `Question` with no first, where a list starts (`RefuseKey`, then `OnceKey`, `AlwaysKey`, a rule of the session's alone, and `ExplainKey`, which answers nothing: `Explains`, `ExplainText`, everything Claude asks to do with the caution first); its title names who asks and for what, and its text is `AiCaution.Asked`, heard with the question every time (bundle rule 11; the words are `AxKit.Core/AiCaution`'s, `ToolCall` for the explanation). Claude's own questions are asked one after another (`Current`), each with its choices by number and Other last; Other sets `WordsPrompt`, the row Claude Code's screen shows for the user's own words (`ClaudeCodeTexts.TextPromptFor`), which the model hands the window as its `TextPrompt` (`StreamModel.AskWords`), so that the window's own field asks for them; `Answer` gives the relay's answer when the whole is answered, `Escape` goes back from the words to the list and else refuses the whole. Never add an answer that runs something in front of no, and never drop the caution from the question's text. `StreamAskingTests`, from the questions the recordings hold.
- Rules the audit of 2026-11-21 set (docs/axClaude/stream-mode.md section 13): a relay writes its secret only to a pipe this same program file serves (`ThisProgram.Serves`), never to a pipe known by its name alone; text of the stream is never put into a control as it came: what Claude asks goes through `StreamAsking.Shown` (hidden characters written out), a line of the conversation through `StreamModel.Printable` (control characters dropped), since a character of code 0 ends a text box's text; a title says Claude's own description as Claude's (`StreamAsk.AboutDescribes`) and says when the input holds more than it names (`AboutCut`, `HoldsMore`); the program runs in a `ChildJob`, so that it never outlives the window.
