# AxClaude.Core, the pure code

Everything of axClaude that does not need a window: the VT stream to transcript conversion, the model of what Claude waits on, and the ConPTY host. Unit tested in `tests/AxClaude.Tests` against recorded fixtures under `tests/fixtures` (the golden files show joined wrapped rows, as the reader sees them). The spec is `docs/axClaude/SPEC.md` ("SPEC.md" below); the catalogue of Claude's screens is `docs/axClaude/claude-screens.md`. The window is `src/AxClaude`, with its own `CLAUDE.md`. The bundle rules are in the root `CLAUDE.md`.

## Commands

```
dotnet test tests/AxClaude.Tests/AxClaude.Tests.csproj     # works while the app runs (this project is not locked)
AXCLAUDE_UPDATE_EXPECTED=1 dotnet test                      # regenerate tests/fixtures/*.expected.txt after a deliberate parser change; review the diff
dotnet run --project tools/PtyCapture -- --out session.vt --script demo.script -- claude --ax-screen-reader
dotnet run --project tools/PtyCapture -- --dump session.vt  # personal data replaced; --raw shows it, never print that into a session
```

New fixtures follow the `record-fixture` skill and are reviewed for personal data (account name, paths, session ids) before they are committed. When the conversion changes, add or update a fixture-based test.

## Gotchas already learned (do not rediscover)

- Clear this process's standard handles around `CreateProcess` when attaching a child to a pseudo console (see `PtyHost.Start`). Otherwise a child started from a process with redirected stdio inherits those pipes, sees no TTY, and Claude Code silently switches to non-interactive print mode.
- Strip every `CLAUDE*` environment variable but `CLAUDE_CONFIG_DIR` (the user's own folder for Claude Code, kept since 2026-11-15) from the child's environment so a nested Claude Code session is not detected, and set `TERM=xterm-256color`.
- Startup can show dialogs before the prompt (workspace trust, one-time onboarding questions). They are flat `y/n` or numbered prompts in screen reader mode; the app must simply show them and let the user answer.
- Frames are bracketed by `ESC[?25l` and `ESC[?25h`. Chrome, finality and announcements are evaluated at frame end. Rows below the cursor row are chrome (autocomplete list, dialog hints). Only the cursor row may be treated as the `$` prompt; reply and tool rows can start with `$ ` too. On a full screen Claude can park the cursor on the mode line in the bottom row while it works; that row is chrome too, or the spinner and mode line above it are spoken with the reply (FR-3.5).
- Screen reader mode emits no SGR styling. Markdown headings arrive as plain short rows, and the first block of a reply shares the `claude:` row. Heading detection is structural (SPEC.md §7.6).
- Claude echoes `you:` for messages and, since 2.1.281, for slash commands (`you: /model`), a row that repeats no sent text and is left as Claude's own, except `you: /clear` as the first row above the live block, which empties the conversation (SPEC.md FR-8.8, the `clear` fixture; in screen reader mode `/clear` prints nothing else); not for dialog answers. `BEL` and `ESC]133;C/D` arrive just before the final frame of a turn, so "Done" is announced after a short quiet period.
- A message sent while Claude works is drawn *inside* the working block as `you: …` over `ctrl+x ctrl+s to send now`, on rows that shift every frame; it is not the echo. The real echo is the `you:` row left behind when the hint disappears (see the `steering` fixture and SPEC.md FR-4.7). Never attach markers or hidden flags to rows inside the working block: the echo matcher skips chrome rows, and the markers of such a message wait for the echo (the user wants the message out of the conversation until Claude takes it up, SPEC.md D16).
- Claude hard-wraps long reply rows at the console width; the join rule (FR-3.2a) lives in `SessionModel.JoinWrappedRows` and the mirror renders the join. A labelled row (`claude:`, `tool:`) starts with a lowercase letter too, which is why only `Plain` rows inside a reply or echo block may join.
- The draft is printed without a cursor hide/show bracket; a lone `\n` write is Ctrl+J (newline in the draft), verified in the `steering` fixture. Text plus `\n` in one write is a paste.
- The default mode line is `manual mode on` with no `(shift+tab to cycle)` hint. Mode changes and similar confirmations appear for one frame as a bracketed row under the prompt (`[accept edits on]`) with the cursor parked on it; the app speaks those.
- A tool result, a replayed conversation or a slash command can print any row, including `you: …`, `Permission Required:`, `Enter y/n:` and `[Screen Reader Mode: …]`. Text alone never proves Claude's state: an echo must repeat a sent text, a question is pending only while the cursor sits on the prompt row, and the replay boundary of a restart is a remembered line, not a text match. Rows that scroll away inside one frame are classified when they are committed.
- `TranscriptMirror.Update` reuses its lists between frames: a frame that changes nothing visible (a spinner tick) must not allocate, and a 20 000-entry list goes to the large object heap. The update it returns is valid until the next call.
- `SessionModel.CompleteFrame` (called by `EndFrame` and by the screen's `FrameEnd` event) walks the whole transcript several times per frame. A lambda inside one of those loops that captures a local declared in the loop body makes the compiler allocate a closure on every iteration (that was 700 KB a frame in `HandleEchoes`); keep such work in a separate method called only for the rare line. The steady state is 0.12 ms and zero allocation at 18 000 lines; measure with a scratch console app against `AxClaude.Core` before and after touching that path.
- The record Claude Code prints in an answered question's place (`●  User answered Claude's questions:`, then `· <the whole question> → <answer>` for each question; a no-break space after the bullet) is not Claude's reply (SPEC.md FR-7.4b, 2026-11-14): its rows are `LineKind.AnswerRecord` (the label by text, the rows under it by `LineClassifier.ContinuesAnswerRecord` in `SessionModel.Classify`, since a reply's own row may start with the same mark), visible and exported as printed, skipped by `Arrivals` like a marker, and they neither end the reply block (`inReply` in `Arrivals`, `Classify` and `JoinWrappedRows`) nor join a wrapped row. As Plain rows of the reply they were spoken in *all lines*, the row with the old question seconds late, as the last visible line while Claude worked, into the next question. Keep a new row of Claude Code's own out of the reply the same way: a text in `ClaudeCodeTexts`, a kind, a skip in `Arrivals`.
- The chrome block above the cursor row is scanned from the bottom and closed by the first row that is not chrome (`SessionModel.ApplyChrome`, `blockOpen`), so one unknown row of Claude Code's own at the bottom leaves every known row above it (mode line, branch row) in the conversation, where *all lines* speaks them with the reply. That happened on 2026-11-15 with the row of a background agent after the turn has ended (`◯  general-purpose <description> running`, no time) under `Waiting for 2 background agents to finish`: both are `ClaudeCodeTexts` patterns now (`IdleAgentRow`, `BackgroundWait`), heard live and not yet recorded (docs/axClaude/claude-screens.md says what the fixture must confirm). The same day again with a dynamic workflow's live row, the lowest row under the spinner and the mode line (`   ◯  axkit-design-map-and-verify 14%  1/7 · 9m27s · ↓ 1.7m tokens · ⚠ Large workflow · /workflows to stop`, Claude Code 2.1.325): the spinner and the mode line stood in the conversation and, in all lines, every redraw of the row was spoken. The general rule since: every live progress row of background work is one class, the large circle and two spaces (`ClaudeCodeTexts.ProgressRow`, `LineClassifier.IsProgressRow`), read where its form is known (`AgentRow`, `IdleAgentRow`, `WorkflowRow`; the waiting row by its kind, `BackgroundWaitOf`) and otherwise counted as one thing of a kind not known (`SessionModel.BackgroundUnknown`), so that the next kind Claude Code invents is interface from the first day. The rows of the live block that are progress rows get `LineKind.Progress` from the model (`_progressLines` in `ApplyChrome`, set in `Classify`, never by text alone); with `ShowProgressRows` (the user's option) they stay visible while still closing nothing of the block, and `Arrivals` passes them like hidden lines. The scan was left as it is: letting an unknown row pass between known ones would hide a reply's last rows. When interface rows are spoken, look for the lowest row above the prompt that matches nothing. One known exception to the bottom-up rule: the last frame of `/exit` (Claude Code 2.1.319 and 2.1.332, the `clear` and `permissions-search` fixtures) leaves the spinner, the mode line and the prompt drawn and prints `Resume this session with:` and the `claude … --resume <id>` row under them, the cursor on the blank row below; those two rows matched nothing and closed the block, so the spinner and the mode line stood at the end of the conversation. `ApplyChrome` now reads the row above them as the cursor row (`ResumeRowsAbove`, `ClaudeCodeTexts.ResumeLabel` and `ResumeCommand`), and the two rows stay the conversation's.
- Events and the record (EG; measured 2026-11-15): a hook's process must exit 0 and print nothing whatever happens (`HookRelay.Run`), or Claude Code draws an error row into the conversation; an event is a signal, never run, typed or shown. The session file's order is file order, never its timestamps, which go backwards at times. Nothing of an event or an entry may reach a log: the records print as numbers and fixed words (`HookEvent`'s text, a `FlowInput`'s type name, a decision's `ToLine`), so keep it so in a new record. The core is fed in arrival order and accepts every order of its sources; a rule that needs one order is wrong (EG-11.2). The gate in three lines (EG-5): a proposed reply line counts only inside a turn; with a record it waits until an entry's key starts with its head's letters, and is dropped when none comes in time; without a record it is released after the old hold. Done after the last reply (EG-5.6) needed three rules the timelines showed, each with its fixture in `TimelineTests`: a frame after the bell that still shows work does not count as the one that added the reply's rows (it was cut mid-redraw, and the row is proposed a frame later); with a record Done waits, 500 ms at most, for the head of a reply the record holds and the screen has not proposed; and a turn ended without its bell stays ending for 600 ms, with no Done, since an interrupted reply's shown part is drawn after the end mark. When a rule of the core changes, replay every order before believing it.
- A hint row is one only when every part of it reads as keys, "to" and an action (`ClaudeCodeTexts.Hint`), and a screen under a tab row is a screen only down to such a row (`ScreenReader.Read`). So one new key in one part hides the whole screen, and nothing is said: Claude Code 2.1.327 named "/" on the permissions screen's row ("/ to search"), and `/permissions` showed nothing (the `permissions` fixture; found by the live scripts the day the version came). When a screen stops showing after a new version, dump a recording of it and read its hint row first. A key that opens a field of Claude Code's for typed text needs the field read too, or the cursor moves where no screen is read and the message field comes back over a field that takes the next message: the permissions screen's "/" (`ClaudeCodeTexts.KeySlash`) was read and given no key until 2026-11-25; now its search row is a screen of its own (`ClaudeScreen.Searching`, the search row under the cursor and a hint row whose Escape goes back or clears, the `permissions-search` fixture), shown by the window as a field while empty and as a list once a text is typed. Claude Code echoes the keys typed after the first onto the row without a frame, and never send Down or Enter there while nothing matches ("Nothing to select", which no reader knows).
- Claude Code draws the suggestions for a typed slash command above its prompt row and moves that row down (2.1.326 and 2.1.327, the `permissions` fixture): for the moment between the command's text and its Enter they are rows above the cursor that no pattern knows, so they are lines of the conversation until the next frame writes over them. Seen on 2026-11-17 and not repaired; the priorities list has it. A row that stood in the conversation at the last frame's end and was not written since is never the list's (`SessionModel.HideCompletionRows`, 2026-11-27: a reply's last rows of the list's shape were hidden for good with the list drawn under them).
- More than one mode line can stand on the screen (Claude Code 2.1.330, the timeline fixture `background-shells-330`, 2026-11-21): the session's first one stays where it was drawn, hidden by its remembered text, above the one Claude Code draws now. `ApplyChrome` reads the rows from the bottom, so only the first mode line it meets, the lowest, gives the mode, the background's counts, the drafts and whether Claude works; read after it, the old one took "1 shell" away again, and the status bar and the closing question knew of no background work (the maintainer's report of 2026-11-18).
