# axTask, the window

The WinForms side of axTask: the navigator and the detail pane, each the bundle's `AxKitList`, a status bar, the
bundle's notices. The pure code (the item format, the field values, the folder, the changes with their undo, the links,
the tasks and the smart lists, the settings) is `src/AxTask.Core`, with its own `CLAUDE.md`. The shared shape of the
item apps is `docs/axKit/item-apps.md` (IA-n.m); axTask's own spec is `docs/axTask/SPEC.md` ("SPEC.md" below); the guide
`docs/axTask/user-guide.md` is embedded by `AxTask.csproj`; the manual test plan is `docs/axTask/nvda-test-plan.md`.
The bundle rules are in the root `CLAUDE.md`.

## Commands

```
& '.\scripts to run-individual-apps\run-axTask.ps1' manual_tests\axTask\tasks   # build AxKit and start axTask on the test folder (run.ps1 -App task)
.\test.ps1 AxTask                            # the tests in Release, as CI runs them
```

## Where things are

- `AxTaskApp`: the entry point `Run`, one call into `AxKit.Forms/AppHost.Run` with the one folder or item file.
- The panes, the moves between levels, the shared keys and every field command are the item apps' shared window,
  `AxKit.Forms/ItemForm` (since axPass, its second use); `TaskForm` derives from it and fills in what is axTask's.
- `TaskForm.cs`: the menus (the bundle's eight through `PlaceMenuBar`, AX-9.1: Session; Actions; Navigation with All tasks, the search and the sections; Context over the List, Item and Field menus, never on the bar, from `ItemForm.CreateContextMenu`, AX-9.11; Options with Hide done tasks and Project folders first) with axTask's own keys as commands of the window's one command list (`Add`, each key's
  command at its first menu item; docs/axKit/app-kit.md AK-2), the levels of the folder (`Start`, `EnterList`,
  `LeaveList`, which goes straight back to the top, `ShowAllTasks`, `ReadLevel` with the rows' `Tag`: an `ItemFile`, a
  `SmartList`, a `SectionTag` (name, the user's own or not, level 1 to 3, the detail line when not the name's own) or a `ProjectSectionTag` on a heading, `ArchivedItemsTag`, a `ProjectTag`, or nothing for a list; the top level under three levels of headings is
  `ReadSections` with one row shape, `Heading`: "Smart lists, heading level 1, 3 smart lists", TK-3a, TK-D13; the smart and date lists over `GatheredItems`, the folder shown read now and the projects' as the last look read them, TK-5.6; the user's smart lists grouped by `SmartList.Grouped` under level-2 headings keyed "filters:", Tags with a level-3 heading per symbol keyed "symbol:", TK-5.2a, TK-5.5; Ctrl+1 to Ctrl+3 and with Shift, `JumpHeading` while `AtHeadings`, registered before the action keys, TK-D14, TK-D20) and the detail (`DetailOf`, with a `FileSource` to save to; a link read by `SpokenValue`).
- The selection of several items (SPEC.md TK-4.7, bundle AX-8.16, 2026-11-22) is the item window's (`ItemForm.Selection`, the bundle's `ListSelection`; the keys `AxKit.Forms/SelectionKeys`); axTask switches it on (`HasSelection`), says which rows are selected (`CanSelectRow`: an item, also one a search found; never a list, a project or a file that does not read) and why not (`NothingToSelect`), and gives its commands their targets: `Targets()` in `TaskForm.Commands.cs`, the selected items in the list's order, or the item you are on alone. On the targets: `ToggleDone` with `DoneForSelected` (Ctrl+Enter, the bundle's main action key, a command of the Item menu; Space did this until 2026-11-22), `DeleteRow` with `ArchiveSelected`, `MoveToList` (Ctrl+M on an item or with items selected, `OnItemsToMove`; on a list with nothing selected the key is `MoveToSection`, `OnListToMove`: one form with the lists and A new list, the new list made as the first part of the same step), and in `TaskForm.Actions.cs` a list's set and move actions (`RunAction`, `PerformAction`, `SetFields`, `MoveItems`, and `MoveItemsTo`, which Move to a list uses too). Enter, F2, the ways to open and an action that opens or runs stay on the item you are on. Several moves are one step through `CommitMoves`: each move's parts made from the disk as the one before left it and applied at once, a failure taking back what was applied. In the notes and the code "selected" means marked with Space; the item under the arrow keys is the one you are on (older text here says "the item selected" for it).
- `TaskForm.Commands.cs`: the commands and the one way a file changes: `Commit` (a `Step` applied, kept for Ctrl+Z,
  the panes filled, its words said; `Committed` is its second half, for a step already on disk), `CheckFresh` (the file still as shown, IA-5.5), `SaveFields` (the shared field
  commands' change, written: an item through `ItemFile.TextWith`, which writes only what changed; a list's details into its configuration), `MoveToSection` and `SetSection` (TK-3a.3), `NewList` in the selected row's section, the link's notice (`ChangeSpecial`). Rename and Archive add `Links.AfterMove`'s writes in the item's own folder of lists (`TopOf`: a project's for one of its items gathered into the user's smart lists, TK-5.6),
  so links follow what moved. The lists' configuration (docs/axTask/forms-framework.md sections 11 and 13, SPEC.md TK-4.0, 2026-11-21): `Changeable` (an item whose configuration is not there or does not read is not changed, and says why), `ConfigurationForChange` (the configuration a change goes by: the list's own, the one a list without a file gets, or none and the reason said when it does not read), `NewItemParts` (a new item, with the list's configuration before it when the list has none on disk), `SwitchList` (a checklist or a plain list, in the configuration alone), `EditConfiguration` (Ctrl+J on a list: the file written first when missing, then axJSON) with `OnActivated` and `ConfigurationChanged` (back from axJSON, the panes read again and one line said). `TaskForm.cs` has the detail's side: `DetailOfItem` (the kept line, `ReadKept`), `DetailOfList` with `DetailsDocument`.
- `TaskForm.ItemForm.cs` (AF-14.1, AF-14.2, SPEC.md TK-4.0a, 2026-11-21; the form itself the item window's since 2026-11-23, `AxKit.Forms/ItemForm.Form.cs`, the same as axTemplate's): `FormOf` gives an item's form (not in the search's level, not for an item whose configuration is not there; the links typed as the other item's title, the kept line as the note), `FormToday`, and `SaveItemForm` writes the changed document as one `Step` (`ItemChangeParts`: the file, and its rename with the links when the Title changed, which `RenameItem` uses too).
- `TaskForm.ManyFields.cs` (SPEC.md TK-4.7a, 2026-11-24): Context, Set fields and Clear fields on `Targets()`, all of one list (`ItemsForFields`): `SetFieldsOfItems` (a form from `AxTask.Core/ManyFields.Controls`, every control starting as "leave", a link typed as a title found in the item's folder of lists) and `ClearFieldsOfItems` (a check list of the fields); both write through `SetFields`, one step.
- `TaskForm.History.cs` (SPEC.md TK-4.11, 2026-11-24): a list's history of changes, off until its Options switch (`ToggleKeepHistory`) turns it on: `RecordHistory` adds a step's lines to the lists' `history.jsonl` from `Committed` and, as the change an undo makes, from `Undo` (never stops the step; a failure logged by its kind alone); Context, Item, History (`ShowItemHistory`) reads the item's lines off the UI thread into a notice. The rules are `AxTask.Core/ItemHistory`.
- `TaskForm.Order.cs` (SPEC.md TK-4.9, TK-4.10, 2026-11-24): the Item menu's Move up, Move down, Move to the top and Move to the bottom (`AxTaskKeys.MoveItemUp` and the rest, Ctrl+Shift with Up, Down, Home, End; `InOrderedList`), each a `Step` writing the list's configuration through `Commit`; Options, New items at the top of this list (`ToggleNewItemsAtTop`). `NewItemParts` puts a new item into the order, `ItemChangeParts` keeps a renamed one's place.
- `TaskForm.Conversion.cs` (AF-13.6): a list of the earlier format is not gone into (`EntryRefused`, which asks instead and returns an empty reason); `AskConversion` and `ConvertLists`: the copy into the Archive first (`AxKit.Core/Conversion/ListConversion`), then the plan as one `Step` through `Commit`, and what the conversion has to say in a notice after.
- `TaskForm.Actions.cs` (docs/axTask/forms-framework.md sections 2 to 7; SPEC.md TK-7a; 2026-11-21, in place of `TaskForm.ActionKeys.cs`): the actions of a list. `PlaceActionMenu` registers the eighteen keys (`AxTaskKeys.ActionKey`, "Action key 1" to "Action key Shift+9") and fills Context, Actions of this list, as it opens (`RefreshActionItems`: every action by its `Label` with its key, marked act, one with a hidden field withheld from the AI tools, then Read the last output). `RunActionKey` and `RunActionNamed` read the action from the file again and go through `RunAction` (not understood: said, never run; `ClickedForAiTool` taken along), `AskActionForm` (an action's form on `FormControls`, a hidden box emptied as it is read) and `PerformAction`: `SetFields`, `MoveItems` and `OpenTarget` through `Commit` and `ActionKeys.OpenRefusal`, a move or an open behind `AcceptedOrAsked` (said at the first press, done at the second, TK-7a.3; an acceptance of before 2026-11-21 still counts), and `StartRun`: the action filled (`ActionValues.Run`), its program found (`ActionProgram.Find`), the folder local, `SystemPrograms.LineFor`, then the question "Run <name>?" with everything that would run, Cancel the default, unless this very action was accepted (`ListActions.MarkText` under the settings' seal) and no AI tool asked. `RunNow` runs the program off the UI thread through `ProcessRun.RunAsync` in a `ChildJob`, one at a time, says how it started and ended, keeps its output in memory (`ReadLastOutput`), writes what its `then` sets as one step; `StopAction`; `OnFormClosed` ends what runs. While a program runs the status bar's place starts with "Running <name>." (`PlaceText`, set through the item window's `SetPlace`). `StartTerminal` is the `terminal` kind (AF-7.4): the command filled (`ActionValues.Terminal`), the folder local, the question "Put <name> into axTerminal?" as for a program, then a new axTerminal window through `WindowMenu.StartWith` with the folder, `--command` and each part as an argument of its own; axTerminal makes and quotes the line for its shell and never sends it (its SPEC AT-1.5a). Never join an item's value into a command line, never start a shell for an action, and never run an action that is not understood. axTask is local only (the user's decision, 2026-11-14, SPEC.md TK-7a.2): nothing in axTask makes a network request; what a program of an action reaches is that program's doing.
- `TaskForm.Projects.cs` (SPEC.md TK-7b, 2026-11-11): the project folders (Options, Add a project folder: `AddProjectFolder`, one `AskText` whose empty field opens the folder picker, and Remove a project folder made again as it opens, `FillProjectFolderItems`), `FindProjects` off the UI thread through `Do` (`_findRun` drops an older look's result; the level read again through `ItemForm.Refill` only when the projects changed, held in `_refillHeld` while a notice or a rename is open and done in `OnNoticeClosed`), the Projects heading's level-2 headings, one per project folder (`AddProjectSections`, `ProjectSectionTag`; the old Projects row and level are gone, TK-D13), the projects' items read by the same look (`_projectItems`, compared in `TakeLook`, a file the window changed read again by `PatchProjectItems` from `Commit`, `Undo` and `CheckFresh`, TK-5.6), the folder picker opened only once the notice has closed and its words said by `SayAfterDialog` (TK-D12), a project entered as the top (`_project`: `TopFolder` is the project while it is shown, so everything else works there unchanged), and the search (Ctrl+Shift+F: `FindEverywhere`, `RunSearch` ("Searching every list" at once; `_searchRun` and `Busy` drop a result that comes late), the level `_search` with its `FoundItem` rows read again on every fill, `OpenFound` on Right and Enter and `LeaveSearch` on Left and Escape, those keys registered before the shared ones). `Gathered` is the found level, where nothing is made or moved.
- `TaskForm.Mcp.cs` (SPEC.md TK-8, docs/axKit/mcp.md MC-8, 2026-11-11): the AI tools' `axkit_task_lists`, `axkit_task_items` and `axkit_task_add`, the override of the window base's `McpAppRequest` (the base has refused axPass, the switch, a notice, a dialog and the user typing first); `axkit_task_lists` reads its counts off the UI thread (a `Task<object>`, the folders taken first); the lists reached are `_settings.TopFolder`'s and `_projects`' (never a project shown as the top), an add goes through `Commit` with the words "Claude added X to List", selected only in the list shown, then `ChimeForMcp`; a rename open refuses it.
- `TaskForm.Approvals.cs` (SPEC.md TK-9, docs/axKit/outside-reports.md, 2026-11-21): the maintainer's approval of an outside report: the Item menu's Approve this report and Decline this report on an entry of the list `outside-reports` awaiting approval (`DecideReport`: a notice with the whole entry, the focus in its text first, and a hidden passphrase field; `SignEntry` signs off the UI thread with `AxTask.Core/Approvals` and writes State, Approval and Approved on through `Commit` after `CheckFresh`), and Options, Approval passphrase (`SetUpApprovalKey`: the key beside the list made, or its passphrase changed with the old key signing the new one, `approval-key-change.txt`, one change at a time; the key file written last and by a move). All three are withheld from the AI tools and marked act. The passphrase is read from the field, cleared there at once, and never kept, logged or said; never add a way to show or store it.
- `AxTaskKeys`: the window's keys, `AxKit.Forms/ItemKeys.All` and its own (`ActionKey(digit)` for Ctrl+1 to Ctrl+9, of which Ctrl+1 to Ctrl+3 are `NextHeading1` to `NextHeading3` at a top level, one table entry each, with `PreviousHeading1` to `PreviousHeading3` on Ctrl+Shift, named as axDown's; All tasks is Ctrl+0); `All` feeds the collision test and the F1 text names the same keys.
- `HelpText`: the F1 text and the embedded guide; About is the bundle's.

## Rules

1. Every change goes through `Commit` with a `Step`; nothing writes a file another way.
2. Never write a file without checking it is as it was shown (`CheckFresh`): axJSON or a sync may have changed it.
3. The detail pane says nothing when it fills; NVDA reads it when the focus goes there.
4. The window, the field notices and the format are shared with axPass (IA-D5): a change to them changes both apps;
   keep what is axTask's own (Done, Due, All tasks, smart lists, links, files) in `TaskForm`.
5. Run the `accessibility-review` skill on a change here before committing, and check it with NVDA following the test plan.

## Gotchas

- A row may be a file that does not read as an item (SPEC.md TK-4.6): its `Tag` is an `UnreadableTag` with the path, or without one on the gathering lists' last row that counts such files (`_unreadable`, set by `GatheredItems`). Enter on it is the command "Open the file in axJSON" (`OpenUnreadable`), registered before the shared keys; a command that falls through to "a list" for a row it does not know needs a case for this tag (`RenameRefused`, `DeleteRow`, `OpenInAxJson`, `ShowInAxFile`, `DetailOf` have one).
- The reads and writes run on the UI thread: items are small local files. All tasks reads every file under the top
  folder on each fill (TK-D3); a slow share would stall the window.
- Escape in the navigator has three commands, taken in the order they are registered: the search's "Back from the search" (only while nothing is selected), then the item window's "Deselect all" (only while something is). A new command on Escape there needs the same condition.
- Enter, Space, Delete, Escape, Backspace, Tab and the arrows reach `ProcessCmdKey` while a list has the focus; they are
  `ItemForm`'s commands with a `When` of the pane focused, and taking them keeps the list box from its own move and its
  ding. `ItemForm` registers the shared keys after the app's (`PlaceControls`), so that an app's key comes first; a
  command of axTask that acts anywhere has `When = NotRenaming`, so that the rename box keeps its keys.
