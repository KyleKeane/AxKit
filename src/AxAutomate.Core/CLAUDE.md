# AxAutomate.Core, the pure code and the engine

Everything of axAutomate that needs no window: the workflow format, and the runner's engine, which plays a workflow on a desktop of its own (SPEC.md AU-5.1). Unit tested in `tests/AxAutomate.Tests`. The spec is `docs/axAutomate/SPEC.md` ("SPEC.md" below); the window is `src/AxAutomate`, with its own `CLAUDE.md`. The bundle rules are in the root `CLAUDE.md`. The command line over the engine is `tools/AxAutomate` (project `AxAutomate.Runner`, program `AxAutomate.exe`), which `nvda-pass.ps1` and the assistant run; its header lists every step word.

## Commands

```
.\test.ps1 AxAutomate
dotnet build tools\AxAutomate\AxAutomate.Runner.csproj -c Release -o <scratch>   # the command line, then <scratch>\AxAutomate.exe <script> --exe <AxKit.exe>
```

## Where things are

- `Workflow`, `WorkflowStep`, `StepValue` (AU-3): a workflow and its steps as records; a note alone is a step with an empty `Do`.
- `ScriptReader` (AU-5.2): a runner's `.txt` script read as a workflow: a header line `# Workflow: <label>` is its title (AU-5.2a; `LabelOf`, every script has one, `tools/workflows.ps1` lists them in `docs/axKit/workflows.md`), the other header comments are `Covers`, later comment runs are notes, `try said` is `expect said` with `on failure` continue, the `iffound` lines its `Then`. A test reads every script of `tests/scripts` without a problem. Beside the steps, the script's sections (AU-5.2b, `docs/axKit/user-workflows.md` WF-3): `Goals` gives each `# Goal:` and `# Check:` line's section as a `Goal` (`Check` true for a check), to the next such line, with `Stable` from a `# Stable` line among its own comments; a script with neither is one goal, `Named` false, titled by its label. `GoalAt` finds a line's section (null in the setup); `Workflow.Needs` is the header's `# Needs:` line, which stays in `Covers`. A goal or check line ends the header (`HeaderLength`, the one rule) and is a note's text as before, so the window does not change. `IsInput` says whether a line is an input step (`do`, `keys`, `type`, `menu`, `start`, `launch`, `adopt`, `use`, `close`, `mcp call`, after any `iffound`).
- `GoalResults` (WF-3.9, WF-3.10): which sections passed, failed or were not run (`Of`: a failing step still stops the script; a failure after the steps fails every section that passed), the report's lines (`Heading` before a section's first step, `Lines` after the last, `Counts`). `ScriptRunner.Play` prints them only when given `PlayOptions` with a named section, as the command line does; `ScriptResult.Goals` holds the results. `WithFailed` fails one section alone after the steps: a stable section whose trace is not the kept one (WF-5.5), which the command line finds after the play.
- `ScriptApps.ByLine`: the app whose window each line of a script reaches, read off its `start`, `adopt` and `use` steps (a start by a verb of `Dispatch.Apps`; null where it cannot be read). For the checks and pages that name a command under its app (WF-2.11, WF-7.3).
- `CommandInventory` with `InventoryApp` (WF-2.6 to WF-2.11, format 5.3; `CommandInventoryTests`): the command inventory, `docs/axKit/window-commands.json`, pure: by app, the rows the windows listed (`ListedCommand` of `AxKit.Core`) without what is state (`Stored`: no `checked`, no `now`). `Read` and `Write` keep one order (the apps by name, an app's menu rows by menus and label, then its keys with no menu item; an app without rows is not written). `Kept` says which rows never enter: a numbered entry of a list, a row that names the run's folder or the profile folder; a rule for a name of the computer the run was made on (a program, a device, a shell) goes there as a named private method with its test. `Merge` puts a snapshot in (its rows replace the app's rows of the same label and menus; under a notice only its keys alone), `Rewritten` makes whole apps anew from a run's snapshots, `Stale` names what a live window lists differently, one line a row, and `Holds` says whether an app has rows at all; `Merge`, `Stale` and `Rewritten` take the run's root folder and the profile folder, for `Kept`. A command is found by `Resolve` (its name, through `CommandNames`; in one app, or app by app), `OfChord` (the one row of an app that holds a chord) and `OfMenuText` (the one row a `menu` step's text answers); all three pass over a row of keys alone whose label a menu row has.
- `Traces` with `TraceSection` and `TraceDifference` (WF-5, format 5.4; `TraceTests`): a run's trace, pure: `InputLine` (an input step's line, by `ScriptReader.IsInput`: a `do` with what it pressed, an `mcp call` without its arguments; null for a step that is no input and for a skipped `iffound`), `EventLine` (an event's line, with the window's number when the run has several), `Clean` (the run's folder as `{temp}`, the profile folder as `{home}`, then the redaction), `Stable` (the sections of the goals and checks marked stable), `Write` and `Read` (a script's kept file, at `PathFor` under `tests/traces`), `Compare` (for each section the first line that differs; line 0 for one with no kept trace) and `MayKeep` (never a script with a needs line, one outside `tests/scripts`, or one of the folders whose windows read the computer or the user's session). `Sections` makes a run's sections from the lines it played (`TracedLine`: a line's number, its input line, the events taken at its end; what the windows said between two sections is the earlier one's), and `Problem` words a difference as WF-5.5 does. The engine collects the lines (`ScriptRunner.Play` with `PlayOptions.Trace`, into `ScriptResult.Trace`); the command line decides for which scripts, compares and writes the kept files (`TraceRun` in `tools/AxAutomate`).
- `WorkflowRecord` with `RecordedGoal`, `RecordedTier` and `RecordedRun` (WF-6, format 5.5; `WorkflowRecordTests`): the workflow record, `docs/axKit/workflow-record.json`, pure: for each goal and check, known by its workflow's label and its title, and each tier it ran in (`Desktop`, `Nvda`, `AiTools`), the last result and the last pass. `Read`, `Write` (by the script's path, one entry a line), `With` (one run entered: a pass is the last pass too, another result keeps the pass it had) and `Pruned` (what no script has any more is dropped). It holds labels, titles, script paths, versions, commits and dates, nothing else. Nothing writes the file yet.
- `Reference` with `ReferenceScript` and `ReferencePage` (WF-7, formats 5.6; `ReferenceTests`): the pages for people, pure, from the scripts and the command inventory alone. `Pages` gives the index (`IndexPath`: by group, each workflow's label and under it its goals' titles), one page per group under `PagesFolder` (`Group`, `PageName`: an app's name, "ai-tools", "nvda-only") and the commands page (`CommandsPath`: one line a row), every line ended by a line feed; a script without a label is refused by name. `GoalLines` makes a goal's lines: each input step a numbered sentence ended by a full stop (`do` with the key and the menus of its row, "Press Ctrl+H (Heading; Navigation menu, Next)", or "Choose ... in the ... menu" for a row with no chord; `keys` in key words, naming the command when the line is one chord with Ctrl, Alt or a function key that one row of the app holds; `menu` with the answering row's menus and key; `start` as "Open axDown with find.md"; an `iffound` step after "If that came: "; the rest in `StepText.Sentence`'s words), and each expectation of speech a line of three spaces under the step before it ("You hear: ...", a sound, a focus move and a value by their marks, `try said` as "You may hear: ..."; `Heard`: the edge punctuation dropped, fewer than two words of an announcement left out). Every other step is left out, `{temp}` is never written, and a command is named with a key only from the inventory's rows of the step's app (for a window the lines do not name, only when every app that has the command reads the same). Only goals reach a page (WF-7.5): a check and a goal without an input step are on none, and neither is anything of a script's header or of a run; a script with no goal line has its steps under its workflow, after "Starts with:" and its opening window steps. `Counts` gives the workflows and the how-tos for the command line's line. The pages are what a blind user has read to him and what Claude in axHelp answers from: a changed sentence here is a change for both, and `ReferenceTests` pins the words.
- `WorkflowFile` (AU-3.1): a `.workflow.json` file; every key of a step other than do, on failure, report, note, then and otherwise is a value.
- `StepText` (AU-4.2, AU-D5): a step's sentence, its marks, the rows in run order with a block's steps after their step ("5.1 then: ..."), a step's detail lines.
- `WorkflowFolder` (AU-4.1): a folder's folders then its workflows, natural order, hidden and dot entries left out.
- `AutomateSettings`: the window base's settings and the folder opened last.
- The engine (AU-5.1, AU-D7), moved from `tools/AxAutomate`:
  - `ScriptLines`: a workflow as the lines the engine plays: a script's own lines, or a workflow file's steps written as lines; why a workflow cannot run (`Prepare`), and the operations the engine knows (`Known`).
  - `ScriptRunner.Play`: one workflow's lines played until one fails, every window closed, the report's log; a callback per line, and a stop asked between lines (Escape in the window).
  - `Run`: one step (`Step`), the expectations, the end (`Finish`) and what it ends (`Sweep`); `hosted` for a run inside axAutomate's window, which never hands the foreground right to its windows; `Abandon` for a window closed mid-run.
  - `DoStep` (`docs/axKit/user-workflows.md` WF-4): the step `do <name>` decided, pure and tested in `DoStepTests`. `Decide` takes the listing the window gave (`CommandListing.Read` of the channel's `commands data`, both of `AxKit.Core`) and the name, resolved by the one resolver (`CommandNames`), and says what the step comes to (`DoKind`): `Press` with the row's `now` chord, `Choose` for a menu item with no chord at all, or why it fails: `NoData` (a window from before the request), `Notice` (whatever the name), `Name` (unknown or ambiguous, with the resolver's refusal), `NoAct` (it has keys and none acts where the focus is). `Run` asks the window at the moment of the step, then presses the chord through its own `keys` step, so both tiers and the wait are that step's, or sends the channel's `choose` with the row's label and menus; a passed step's detail is "key ctrl+f" or "menu item". The key is never in the script.
  - The listings a run saw (WF-2.7): `Run` keeps the window's whole listing at every `check commands` step and the one resolved row at every `do` step, and `ScriptResult.Commands` hands them on after the run, for the command inventory (`CommandInventory.Merge`, `CommandInventory.Stale`).
  - The trace of a run (WF-5.1), only with `PlayOptions.Trace`: after each line `ScriptRunner.Play` takes the line's `Traces.InputLine` and `Run.TakeTraceEvents` (for each window in the run's order, the events of its timeline after the ones already taken, as `Traces.EventLine`), cleans each with the run's folder and the profile folder (`Traces.Clean`), and `ScriptResult.Trace` holds the sections, the setup among them, as far as the run got. The take only reads the timeline: what the expectations took and have yet to take is the same with it and without it. Without the option nothing of this runs, so axAutomate's window, the NVDA tier and a script that keeps no trace play as before.
  - `ScriptLines.CannotRun` reads no file (the window asks it per row); `BadNumber` refuses a step whose number is not one before a run, and `Run.Step` fails such a line (never throws) when the command line plays it unchecked. With `confined` (the window, AU-6b.8) it also refuses a `file`, `mkdir` or `silence` path outside the run's `{temp}` (`Outside`); `Commands` lists the `run` steps' command lines the window names before a run (AU-D11), filled by `Filled` (the engine's one filling of `{temp}` and the escapes) with `{temp}` as "the run's folder". The command line passes neither.
  - `Window`: one AxKit.exe of the run on its desktop (`Create`, with the run's variables in its own environment), its pipe and its timeline; `Event` and `Taken` in `RunEvent.cs`.
  - `RunSentences` (AU-6b): what the window says of a run: a failing step, a workflow's end, a folder's end, and the outcome its rows carry.
  - `ClipboardText`: the clipboard's text read and put back around a run of the command line (automation.md, "The user's clipboard kept").
  - `Front` with `FrontMove` (the NVDA tier, 2026-11-15, automation.md section 3): the rules of the foreground, pure and tested in `FrontTests`: `At` (the window asked first, then the runner takes the foreground itself, twice at most a step), `StopsRun` with `CannotTake` (the run's first shown window cannot come to the front: `Run.Stopped` is set and the command line runs no further script, exit 2) and `LeavesMenu`. `Run.InFront` and `Run.TakeFront` follow them; `Native.TakeForeground` is the one Alt key press, `Native.ShownWindow` the window of a process the run started.
  - `Speech`: NVDA's capture log (the NVDA tier); `Broker`: the run as an MCP client; `Native`: the P/Invoke the engine needs. The NVDA tier's keys take their codes from the one chord vocabulary, `KeyChord.Code` of `AxKit.Core` (WF-2.2), as the window's channel does: `Native` holds no table of key names, and `DoStepTests` reads its source to keep it so.

## Gotchas

- A new step word of the runner needs its value key in `ScriptReader.Values`, its sentence in `StepText.Sentence` and its name in `ScriptLines.Known`; without the last the window will not run a workflow that uses it. When the user would do it at the keyboard, or it opens, chooses or closes a window, it is also an input step in `ScriptReader.IsInput` (a goal must hold one, `GoalTests`); an input step is then a line of a trace (`Traces.InputLine`, held to the list of 5.4 by `TraceTests`) and a numbered sentence of the workflow pages, in `StepText.Sentence`'s words unless `Reference` words it itself, so its sentence must be one a user can follow.
- `do` presses what the window lists, at the moment of the step: a `do` line names a command and never a key, and its name is compared whole (`do Find` is not Find next). It fails by design where a user's key would do nothing: while a notice shows (the window lists no menu row then, and a notice's own keys are `keys` steps) and where the command's keys do not act with the focus as it is; it never falls back to the menu item of a command that has a key, since the keyboard path is what is checked. A command that closes the window is `close` or `keys alt+f4`, which tell the run that the end is meant. A key name new to the scripts must be one `KeyChord` holds: both tiers read it there.
- A trace's events are taken at the end of each line, so an event belongs to the last input before the take that fetched it: what a window says late (after the step that waited for something else has returned, or after a section's last step) can land under the next input or in the next section in one run and not in another. And a window puts a focus move and a value change on its timeline from a watch that looks every 50 ms (`AutomationChannel`), so a value that is gone before the next look is never there: a `type` step followed at once by the `keys enter` that closes its field gives its "· text" line under the `type` in one run, under the `keys` in the next and nowhere in a third (both goals of axDown's script 04 lost their marks to this on 2026-11-15, and no section is marked yet). A script whose section is marked `# Stable` therefore waits for what it caused (`expect said`, `expect focus` with the value) before its next input, and a section that still differs between runs loses its mark (WF-5.7); never loosen `Traces.Compare` for it. The take asks every window once more after each line: keep it behind `PlayOptions.Trace`.
- The run's secret and folder are never set on this process's environment (`Window.Create` hands them in the child's own block): the window that runs a workflow also starts the user's own windows, which must never get them (S-11).
- The NVDA tier sends a key only while a window of the run is in front (`Run.InFront` before every press), with one exception, the Alt key press of `Native.TakeForeground`. Nothing of it can be run while the user is at the keyboard: its rules are pure (`Front`) and the rest is checked by reading and by a pass.
- Every process start and pipe here carries its `Outside call, ...` comment (`tools/outside-calls.ps1`).
