# axKit, the executable

The one program file of the bundle (`docs/axKit/SPEC.md` AX-1, B-1, B-2). `Program.Main` takes a test run's variables out of the environment (S-11), takes the run's mark for the process (`RunMembership.Join`, in a test run only: the windows of a run find only each other, never the user's own, `AxKit.Forms/BundleWindows`), sets Windows' switch that keeps the current folder out of every program search by bare name, for this process and for every shell and program it starts (`SystemPrograms.KeepCurrentFolderOffSearches`, S-1), calls `ApplicationConfiguration.Initialize()`, asks `AxKit.Core/Dispatch` which app the command line means, sets the app's taskbar id and calls that app's `Run` (one `<Project>App.Run` per app of `Dispatch.Apps`; `tests/AxKit.Tests/InventoryTests` checks that every app of `Dispatch.Apps` has its call here and its places elsewhere). Everything after, including the crash handling and the log, belongs to the app. The icons live here; `tools/make-icon.ps1` draws them.

In the Store's copy, the MSIX package (`docs/axKit/store-distribution.md`), every app is an entry of the package running `AxKit.exe`; before deciding, `Program` puts the entry's verb first when the command line has none (`Dispatch.WithApplicationVerb` with `PackageIdentity.ApplicationId`), so a Start menu entry, a file opened with the app, its console alias and the startup tasks' hidden entries all reach the right app whether or not Windows passes the entry's parameters. The first start of any app of the Store's copy also starts the background apps hidden, once per install (`Program.StartBackgroundApps`, `AxKit.Core/StoreFirstStart`, AX-13.4a), since Windows runs their startup tasks only from the next sign-in. axTemplate's launcher has no entry and so no startup task (`App.InBackground`): the same place starts it also with the first start after an update and whenever a startup task starts its app hidden, unless its own Start with Windows is off (AX-13.4b). `publish.ps1 -Msix` builds the package; `tools/make-manifest.ps1` writes its manifest from the apps listing.

`<Version>` in `AxKit.csproj` is the bundle's version (`release.ps1` sets it); `AxKit.Core/BundleInfo.Version` reads it from the executable. The WinForms application settings (`ApplicationHighDpiMode`, visual styles, `InvariantGlobalization`) are here because only an executable project generates `ApplicationConfiguration`.

`AxKit.exe hook` is no app and is decided first, before the Open with links and the test run's variables: `Main`'s first statement hands it to `AxClaude.Core/Hooks/HookRelay.Run`, and everything else `Main` did is `Start`, called next (`docs/axClaude/events-and-grounding.md` EG-2.6, section 7.1). Claude Code starts the verb for each event of an axClaude session (the hooks of `claude-hooks.json`, `AppPaths.ClaudeHooksFile`): it reads the event from standard input, writes it as one frame to the window's pipe named in `AXKIT_HOOK_PIPE`, prints nothing, shows nothing and exits with 0 whatever happens, a watchdog ending it after 2 s, since Claude Code puts a failing hook's error on its screen. It is first so that its process loads nothing of WinForms or the apps (the JIT compiles `Start`, with its references to every app, only when it is called) and has nothing done to it that a window's start needs. It is not in `Dispatch.Apps` and never will be: no window, no entry, no usage line.

`AxKit.exe ask` is the second such verb, decided right after it and for the same reason (2026-11-17; `docs/axClaude/stream-mode.md` SM-7.3): `AxClaude.Core/Streaming/AskRelay.Run`, the permission tool of a Claude Code that axClaude runs over its stream. Claude Code starts it as the one server of the configuration it is given (`AskRelay.ConfigText`) and asks it before a tool call that needs the user's word, and for Claude's own questions. It passes each question as it came to the window that started that Claude Code, over the window's pipe named with its secret in `AXKIT_ASK_PIPE`, and the answer back as it came; where the window cannot be asked, or answers what is no answer, it answers no. It prints nothing but the protocol's own lines and lives until Claude Code ends it. No window starts it yet. Not in `Dispatch.Apps` either.

Started under any name but `AxKit.exe` (the installer's Open with links, `axDown.exe` and the like, hard links of `AxKit.exe`; bundle AX-2.3), `Program` first starts the `AxKit.exe` beside it with the same arguments and ends, so that every window runs as `AxKit.exe`: `ThisProgram`, the window lists and the AI tools tell this program by its path and name.

`Program` deletes any `*.old*.exe` next to the program file at startup: an update installed in place (`install.ps1 -InPlace`, bundle AX-2.8) renames the running program file to that, since a running file can be renamed but not overwritten or deleted. A running `AxKit.exe` locks `src/AxKit/bin`: a build over it stops in one line, before anything is compiled or copied (the build guard, a target in `AxKit.csproj` that tries to open the output's program file for writing), so build elsewhere to check a change (`dotnet build src/AxKit -o <scratch dir>`). The message boxes in `Program` and in `AxKit.Forms/AppHost` are the only ones allowed in the bundle: no window exists yet when they show (AX-7.2; `SecondWindowTests` holds the list of files).
