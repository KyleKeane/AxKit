# Security

## Reporting a problem

Please report a security problem privately, through GitHub: [report a vulnerability](https://github.com/KyleKeane/AxKit/security/advisories/new). Do not open a public issue for it. Say which app and version, what an attacker could do, and how to reproduce it; leave out personal data.

You will get an answer as soon as the maintainer can give one. A fix goes out as a new release, which installed copies offer through Check for updates, and the advisory is published with it.

## Supported versions

Only the latest release is supported. Installed copies check for it themselves (Help, Check for updates), so updating is one notice away; a copy from the Microsoft Store is updated by the Store itself.

## What axKit does that matters here

- The update check asks GitHub for the latest release of this repository and, when the user agrees, downloads and installs it for the user only, without administrator rights. It is the only network call a window makes on its own, and it can be turned off (Options, General); the updater takes a download only from this repository's release address, checked against GitHub's digest and the release key's signature. axKit's own code makes network requests in two places, over HTTPS to GitHub: the updater and the report sender. The report sender's is a report the user sends (F4; `docs/axKit/reports.md`): encrypted on the user's computer with the maintainer's public key (a fresh AES-256-GCM key per report, wrapped with RSA 3072 OAEP-SHA256; `ReportSeal`) and posted to GitHub as an issue of the private reports repository `KyleKeane/AxKit-reports`, as a reporter account of the maintainer's whose token ships in the release build and can reach that repository's issues alone. That token can be taken out of the program and can read those issues, which is why a report's content is sealed before it leaves the computer: the issue holds the encrypted report and, in the clear, a random id of the install, axKit's version and the report's kind; the private key is on the maintainer's computer, and its only other copy, a backup encrypted with a passphrase, lies beside that passphrase in the maintainer's private repository `KyleKeane/AxKit-keys`, which that token cannot reach (since 2026-11-15, `docs/axKit/reports-setup.md` section 5). The token is revoked and replaced at a release when it is abused, and a block list of random install ids and versions stops a blocked install or version: the sender reads it before it sends, without a token, from the public repository `KyleKeane/AxKit-blocklist`, which holds nothing else, and the reports repository's own workflow applies the same list to what arrives (`docs/axKit/reports.md` RP-6.4). So the report sender contacts two addresses of GitHub: the block list's file (`raw.githubusercontent.com`, a read) and the API that takes the sealed report (`api.github.com`). Copies up to 5.8.0 send their reports unencrypted and ask for the list at its old address in the reports repository, which answers "not found" now, so their own check finds an empty list; the workflow still closes what a blocked one sends. axTask is local only: it makes no network request and keeps no token (its GitHub lists were removed, `docs/axKit/reports.md` RP-7). The access layers (axClaude, axGIT, axTerminal, axPass) start Claude Code, git, the user's shell and KeePassXC's tool as child processes and talk to them through a pseudo console or pipes; those programs use the network as they would without axKit, on the user's command. Everything axKit contacts, and when, is [PRIVACY.md](PRIVACY.md); [docs/axKit/outside-calls.md](docs/axKit/outside-calls.md) lists every such call in the code, by what it reaches, with its file, line and purpose, written from the sources on every push and every release.
- Releases are built by GitHub Actions from this repository with GitHub's build attestation, and approved by the maintainer before they are published ([GOVERNANCE.md](GOVERNANCE.md)). The GitHub release's `AxKit.exe` carries no Windows (Authenticode) signature, and every release's notes say so; Windows' Smart App Control may refuse it, and an update it refuses stops without changing anything. The signed copy is the Microsoft Store's: an MSIX package the Store signs with Microsoft's certificate after its certification, installs and updates; that copy has no updater of its own, runs every program it starts (Claude Code, the shells, git, KeePassXC's tool, the installers) outside the package as Windows does by default, and keeps its own files in the package's private AppData ([docs/axKit/SPEC.md](docs/axKit/SPEC.md) AX-13). A signing service for the GitHub release was set up and retired, unused, in 2026-11 ([docs/axKit/code-signing.md](docs/axKit/code-signing.md)).
- axClaude runs the user's own Claude Code; axTerminal runs the user's own shells; axFile runs the programs the user chooses. None of them run anything the user did not ask for, with one case the user turns on: with axHelp's setting Options, Keep the conversation ready in the background, off at first, axHelp started in the background at sign-in starts the user's Claude Code hidden for its conversation, so that it is ready at the first key, and only after the user agreed to Claude Code in axClaude's reminder ([PRIVACY.md](PRIVACY.md)).
- axClaude's events from Claude Code (`docs/axClaude/events-and-grounding.md` EG-2, EG-10): with a start of the user's Claude Code, and only while the user has turned on Options, Developer, Events from Claude Code's hooks (off at first), axClaude passes a settings file of axKit's own (`--settings`, `%LOCALAPPDATA%\AxKit\claude-hooks.json`; never a settings file of the user's or a project's), so that Claude Code starts `AxKit.exe hook` for eight kinds of events of that session. That process reads the event from its standard input, writes it to the window's named pipe and ends; it starts nothing, prints nothing and ends with code 0 whatever happens. The pipe is the window's own, inbound only, with a new name and a new 256-bit secret for each start of Claude Code, open to this Windows account alone and refused over the network; a connection whose first line is not the secret is dropped. An event is a signal, no more trusted than a row on the screen: nothing it carries is run, typed, sent to Claude Code, shown as a question's text or written to a file, and the path it names for the session's file is used only when it lies in Claude Code's own projects folder. A hook returns nothing, so it allows, denies and changes nothing Claude Code does. Nothing an event carries enters a log, a report or the diagnostics. axKit listens on no port, on this computer or elsewhere.
- axClaude reads the session file Claude Code keeps for the conversation, in memory only, to check and order what it shows (`docs/axClaude/events-and-grounding.md` EG-3, EG-10.3): nothing of it enters a log, a report or the diagnostics.
- Files that Claude Code obeys in Claude's working folder (`docs/axKit/ai-help.md` AH-2.6, AH-7.8, `docs/axKit/repairs.md` R-54): a question of AI help (Shift+F1) runs Claude Code in print mode with `--strict-mcp-config` and a settings file of axKit's own that turns every hook off, so it connects no server of the folder's `.mcp.json` and runs no hook of its settings files. Before axHelp starts its conversation there, axKit lists the files that can make Claude Code run something by itself and that axKit did not write (`.mcp.json`, a `hooks` member in the folder's settings files, and the files under `.claude\skills`, `commands`, `output-styles`, `plugins`, `agents` and `rules` other than its own), and names every one the user has not accepted in a notice whose default is Cancel; the accepted list, with a SHA-256 of each, is under the settings' seal. The limits: `CLAUDE.md` is not on the list; an axClaude window the user starts in that folder is left to Claude Code's own trust question; a settings member other than `hooks` that names a command is not checked.
- Reports (`docs/axKit/reports.md` RP-6.9, R-57): the sender sends only the report files axKit's own report form saved, by a list of their names under the settings' seal; another file put into the reports folder is never sent, and the user is told how many there were.
- The settings that decide what is run or what Claude may read are sealed (`docs/axKit/SPEC.md` AX-5.6, `docs/axKit/repairs.md` R-53): axTerminal's shells and command lines, axGIT's trusted repositories (each trust bound to the programs the repository named when it was given), axMCP's servers, axFile's custom programs, the place of Claude Code, AI help's switch, folders and working folder, and the recorded agreements. Each file carries an HMAC-SHA256 over those fields under a key kept with Windows' protection for the user (DPAPI) in `%LOCALAPPDATA%\AxKit\settings-seal.key`; a field whose seal does not check is put to its default and not used, and the user is told once. The agreement for a custom shell is for its command line. The limit: a program running as the user can ask Windows for the same key; the seal holds against a file edited by another program or by hand, a profile copied or synced from elsewhere, and an AI tool writing files.
- Settings and logs stay in the user's profile (`%APPDATA%\AxKit`, `%LOCALAPPDATA%\AxKit`). Copy diagnostics puts the versions, paths and the log's end on the clipboard, with the account's name, paths, e-mail addresses and ids replaced, for the user to read before sharing.
- Releases are signed with a key that lives on the maintainer's computer, with a passphrase-encrypted backup beside its passphrase in his private repository `KyleKeane/AxKit-keys` since 2026-11-15, so that a stolen GitHub account of his could sign (`docs/axKit/security-audit-2026-10-24.md` S-27); the apps and `install.cmd` install nothing whose signature does not check (`docs/axKit/SPEC.md` AX-3.4).
- The audit of 2026-10-24 and the review of 3.7.x on 2026-10-25, `docs/axKit/security-audit-2026-10-24.md`, list every finding, what was done about it and what was accepted; the AI tools are specified with their protections in `docs/axKit/mcp.md`, and off until the user turns them on. Running a window's command for a paired AI tool (`axkit_window_run`, MC-7) has a second switch of its own, off by default and sealed with the first, is never offered in axPass or axClip, never while the window asks the user something or while the user types in it, and asks the user before any command that acts outside the window (a program started, a file opened in its program, the clipboard read among them; a test fails on a command without its mark). The typed tools over axTask's lists (MC-8) read through an open axTask window and add an item only behind the same switch, never changing or deleting one. Turning the access off and Forget AI tools turn it off too.
