# Security

## Reporting a problem

Please report a security problem privately, through GitHub: [report a vulnerability](https://github.com/KyleKeane/AxKit/security/advisories/new). Do not open a public issue for it. Say which app and version, what an attacker could do, and how to reproduce it; leave out personal data.

You will get an answer as soon as the maintainer can give one. A fix goes out as a new release, which installed copies offer through Check for updates, and the advisory is published with it.

## Supported versions

Only the latest release is supported. Installed copies check for it themselves (Help, Check for updates), so updating is one notice away; a copy from the Microsoft Store is updated by the Store itself.

## What axKit does that matters here

- The update check asks GitHub for the latest release of this repository and, when the user agrees, downloads and installs it for the user only, without administrator rights. It is the only network call a window makes on its own, and it can be turned off (Options, Check for updates at start); the updater takes a download only from this repository's release address, checked against GitHub's digest and the release key's signature. axKit's own code makes network requests in two places, over HTTPS to GitHub: the updater and the report sender. The report sender's is a report the user sends (F4; `docs/axKit/reports.md`): encrypted on the user's computer with the maintainer's public key (a fresh AES-256-GCM key per report, wrapped with RSA 3072 OAEP-SHA256; `ReportSeal`) and posted to GitHub as an issue of the private reports repository `KyleKeane/AxKit-reports`, as a reporter account of the maintainer's whose token ships in the release build and can reach that repository's issues alone. That token can be taken out of the program and can read those issues, which is why a report's content is sealed before it leaves the computer: the issue holds the encrypted report and, in the clear, a random id of the install, axKit's version and the report's kind; the private key is on the maintainer's computer, and its only other copy, a backup encrypted with a passphrase, lies beside that passphrase in the maintainer's private repository `KyleKeane/AxKit-keys`, which that token cannot reach (since 2026-11-15, `docs/axKit/reports-setup.md` section 5). The token is revoked and replaced at a release when it is abused, and a block list of random install ids and versions stops a blocked install or version: the sender reads it before it sends, without a token, from the public repository `KyleKeane/AxKit-blocklist`, which holds nothing else, and the reports repository's own workflow applies the same list to what arrives (`docs/axKit/reports.md` RP-6.4). So the report sender contacts two addresses of GitHub: the block list's file (`raw.githubusercontent.com`, a read) and the API that takes the sealed report (`api.github.com`). Copies up to 5.8.0 send their reports unencrypted and ask for the list at its old address in the reports repository, which answers "not found" now, so their own check finds an empty list; the workflow still closes what a blocked one sends. axTask is local only: it makes no network request and keeps no token (its GitHub lists were removed, `docs/axKit/reports.md` RP-7); a program that an action of a list starts (below) uses the network as it would from a terminal. The access layers (axClaude, axHelp, axGIT, axTerminal, axPass, axMCP) start Claude Code, git, the user's shell, KeePassXC's tool and the MCP servers the user chooses as child processes and talk to them through a pseudo console or pipes; those programs use the network as they would without axKit, on the user's command. Everything axKit contacts, and when, is [PRIVACY.md](PRIVACY.md); [docs/axKit/outside-calls.md](docs/axKit/outside-calls.md) lists every such call in the code, by what it reaches, with its file, the function it stands in and its purpose; the page is written from the sources by a script, the build of every push checks that it is current, and every release writes it again.
- Releases are built by GitHub Actions from this repository with GitHub's build attestation, and approved by the maintainer before they are published ([GOVERNANCE.md](GOVERNANCE.md)). The GitHub release's `AxKit.exe` carries no Windows (Authenticode) signature, and every release's notes say so; Windows' Smart App Control may refuse it, and an update it refuses stops without changing anything. The signed copy is the Microsoft Store's: an MSIX package the Store signs with Microsoft's certificate after its certification, installs and updates; that copy has no updater of its own, runs every program it starts (Claude Code, the shells, git, KeePassXC's tool, the installers) outside the package as Windows does by default, and keeps its own files in the package's private AppData ([docs/axKit/SPEC.md](docs/axKit/SPEC.md) AX-13). A signing service for the GitHub release was set up and retired, unused, in 2026-11 (the record of it is in the git history).
- axClaude runs the user's own Claude Code; axTerminal runs the user's own shells; axFile runs the programs the user chooses. None of them run anything the user did not ask for, with one case the user turns on: with axHelp's setting Options, Keep the conversation ready in the background, off at first, axHelp started in the background at sign-in starts the user's Claude Code hidden for its conversation, so that it is ready at the first key, and only after the user agreed to Claude Code in axClaude's reminder ([PRIVACY.md](PRIVACY.md)).
- The actions of an axTask list (`docs/axTask/forms-framework.md` sections 3, 4 and 7): a list's configuration file, `list.json`, can declare actions, and an action of the kind `run` names a program that axTask starts on the selected item when the user chooses the action. The file may come from elsewhere (a shared or synced folder, a cloned repository, an AI that wrote it), so: the program is fixed in the file, holds no placeholder, and is found on the search path or by its full path, never in the list's own folder and never off a drive of this computer; what the item holds reaches the program only as single arguments, each one text whatever it contains, or as its input, and axTask never joins a command line, splits one or starts a shell for it; a value with a line break is refused as an argument; an action that is not understood is never run. Before an action's first run on this computer, and again after any change to the action in the file, a notice carries the AI caution, in its name and as the first part of its text (who wrote the action is not known: the user, another program or an AI; it can be wrong; axKit checked none of it; running it is the user's own act), and then names where the action is written, what it does, the program by its full path and every argument as it is for the item, with hidden characters written out, and says that axKit does not know what the program does; Cancel is the default answer. The acceptance is a seal over the list's folder and the whole action, kept with the settings' seal, so a line written into the settings accepts nothing. A request of an AI tool to run such an action is asked about every time, whatever was accepted, and an action with a field typed unseen is never offered to the AI tools. The program runs without a window, under a time limit, in a Windows job that ends with the axTask window; nothing of its output is logged. An action of the kind `terminal` runs nothing: after the same question it starts a new axTerminal window with the command's parts as the arguments of that process, one each; axTerminal makes one line of them for its shell, each part quoted by that shell's rule so that it stays one part (PowerShell: single quotes; Command Prompt: a part with a character cmd.exe acts on is refused; a shell without a rule gets no line; a line break is refused for every shell), puts the line into its command field, says that another program put it there and that it was not sent, and never sends it: the user reads it and presses Enter (`docs/axTerminal/SPEC.md` AT-1.5a). The log holds the number of the command's parts, never the parts. Any program running as the user can start axTerminal this way; it gains nothing by it that it could not do itself. The limits: axKit does not know what a program the user accepted does, and a program found on the search path is whichever one the search path of the user's session gives.
- axClaude's events from Claude Code (`docs/axClaude/events-and-grounding.md` EG-2, EG-10): with a start of the user's Claude Code, and only while the user has turned on Options, Developer, Events from Claude Code's hooks (off at first), axClaude passes a settings file of axKit's own (`--settings`, `%LOCALAPPDATA%\AxKit\claude-hooks.json`; never a settings file of the user's or a project's), so that Claude Code starts `AxKit.exe hook` for eight kinds of events of that session. That process reads the event from its standard input, writes it to the window's named pipe and ends; it starts nothing, prints nothing and ends with code 0 whatever happens. The pipe is the window's own, inbound only, with a new name and a new 256-bit secret for each start of Claude Code, open to this Windows account alone and refused over the network; a connection whose first line is not the secret is dropped. An event is a signal, no more trusted than a row on the screen: nothing it carries is run, typed, sent to Claude Code, shown as a question's text or written to a file, and the path it names for the session's file is used only when it lies in Claude Code's own projects folder. A hook returns nothing, so it allows, denies and changes nothing Claude Code does. Nothing an event carries enters a log, a report or the diagnostics. axKit listens on no port, on this computer or elsewhere.
- axClaude over Claude Code's stream (`docs/axClaude/stream-mode.md` SM-7; being built, and off unless the user turns on Options, Developer, Feed the next window from Claude Code's stream): Claude Code is started as one process over pipes, with no option of axKit's that asks less than the user's own Claude Code would (no permission mode is named). Claude Code does not ask before it works in a folder this way, so axClaude asks whether the folder is trusted before the first start there, with no as the default. With that start axClaude passes a file of axKit's own (`--mcp-config`, `%LOCALAPPDATA%\AxKit\claude-ask.json`; never a settings file of the user's or a project's) and names its one tool as Claude Code's permission tool, so that Claude Code starts `AxKit.exe ask` and asks it before every tool call that needs the user's word and for Claude's own questions. That process holds no logic: it passes the question to the window's named pipe and the user's answer back. The pipe is the window's own, with a new name and a new 256-bit secret for each start of Claude Code, which reach the process through Claude Code's environment and are written to no file; it is open to this Windows account alone and refused over the network, and a connection whose first line is not the secret is dropped. It fails closed: a window that is not there, a pipe that breaks, a wrong secret, an answer that is none, or Claude Code stopped while a question waits all become a no. In the window the question names who asks and for what, carries the AI caution every time it is read, and starts on No; an answer that allows a tool for the rest of the session is a rule of that session alone, written to no settings file. Nothing of a question or an answer enters a log, a report or the diagnostics. A limit that is not closed: the pipe's name and secret are in the environment of everything Claude Code starts, so a program it runs (a command the user allowed, or anything that command starts) can start `AxKit.exe ask` itself, with that environment, and write it a question, which the window cannot tell from one of Claude Code's (the window takes a question only from a process of this same program file, and this is one). What such a program can do: put a question of its own wording to the user under Claude's name, learn the answer, and the words the user types with it; the conversation can then hold a line of the window's own about that answer (that a tool was allowed for the session, or what the user told Claude), about something Claude Code never asked. What it cannot do: the answer goes back to the program that asked and never to Claude Code, so it allows no tool call, adds no rule to the session and runs nothing. Checking that the asking process was started by the Claude Code this window started was looked at (2026-11-27) and not built: how Claude Code starts its permission tool (directly, or through a shell of its own) is not something axKit controls, and a check that guessed wrong would turn every question into a no. The copy from the Microsoft Store does not start Claude Code this way.
- axClaude reads the session file Claude Code keeps for the conversation, in memory only, to check and order what it shows (`docs/axClaude/events-and-grounding.md` EG-3, EG-10.3): nothing of it enters a log, a report or the diagnostics.
- Files that Claude Code obeys in Claude's working folder (`docs/axKit/ai-help.md` AH-2.6, AH-7.8, `docs/axKit/repairs.md` R-54): a question of AI help (Shift+F1) runs Claude Code in print mode with `--strict-mcp-config` and a settings file of axKit's own that turns every hook off, so it connects no server of the folder's `.mcp.json` and runs no hook of its settings files. Before axHelp starts its conversation there, axKit lists the files that can make Claude Code run something by itself and that axKit did not write (`.mcp.json`, a `hooks` member in the folder's settings files, and the files under `.claude\skills`, `commands`, `output-styles`, `plugins`, `agents` and `rules` other than its own), and names every one the user has not accepted in a notice whose default is Cancel; the accepted list, with a SHA-256 of each, is under the settings' seal. The limits: `CLAUDE.md` is not on the list; an axClaude window the user starts in that folder is left to Claude Code's own trust question; a settings member other than `hooks` that names a command is not checked.
- A repository's own settings and hooks (`docs/axGIT/SPEC.md` AG-1.6 to AG-1.6c, AG-5.4 to AG-5.4c): a repository that comes in an archive or from a share brings settings and hooks git obeys. Since the review's fourth pass (2026-11-28), before the user trusts a repository, axGIT runs no git command in it at all: setting programs aside by name had failed three times (a repository's own `core.unsetenvvars` cleared what axGIT gave a submodule's run; a push into a folder ran another repository's hooks; a legacy remotes file; an include on a share). Since the sixth pass (2026-11-28) every repository is asked about once, also one where the check found nothing: each round had found a form of git's files the check read otherwise than git (a split index, version 4's byte prefixes, a submodule's `core.worktree`, a byte order mark before HEAD, an include's leading space, a `.git` file in an untracked folder), and a repository it found nothing in had been trusted without asking. axGIT reads the repository's files in its own code (its `.git` entry, `commondir`, every entry of its `.git` folder for a link, the alternates, the legacy `remotes` and `branches` files, its hooks folders, its index, and the repositories inside it that git enters: the gitlinks of each index, the paths of `.gitmodules` and those under `.git/modules`), and its settings files through git as a parser of one file given by its path, with no repository, which runs nothing. Since the fifth pass (2026-11-28) a path the repository names is read only when it is a plain path on a drive of this computer, or lies under the repository's own folder, with no link on the way; a share in any spelling, a device path, a stream or a junction is named and never touched. A folder whose `.git` git would not take for a repository is not one for axGIT, and a repository whose `.git` is a link or names another computer is not opened; every run of git names the git folder that was read and the root as the work tree, without git's variables for other folders, so that git works on no other repository; the first time a repository is trusted, git is asked once, finding it itself, whether it opens it, so that git's own ownership check (`safe.directory`) still holds. The check reads strictly and fails closed: HEAD, `commondir` and a `.git` file as bytes by git's rule, the index by a strict reading of its format (an entry with an empty name, a length that does not match, or a path git's own check would refuse makes it one axGIT does not read), every path in a setting as git reads it or named, a submodule's `core.worktree` a risk unless it is the gitlink's own folder, and the folder git finds itself at the first trust compared with the one read. Only a setting whose name is in its table of harmless ones is passed over; every other, every hook, every link, alternate object store and legacy remotes file, and every value that names a place on another computer (a share, a device path, a network drive) is named in the notice, and until the user trusts the repository nothing runs in it: Keep it off closes it. The check is made again before and after every command that changes the repository (one that no longer holds before it refuses the command), failed or not, before every fetch, pull and push, after the user trusts a repository (a trust holds only for what the notice showed), and at a refresh; a trust is bound to the risks, the values of the settings that are not harmless and the content of every hook and of every file such a setting names, so that a changed hook is asked about again. In a trusted repository whose hooks folder or a program lies in its work tree, the changing commands run without them, since a switch or a pull could change them while git runs. git's automatic maintenance, its fetch of a partial clone's missing objects and Git LFS's transfers never run through axGIT, and every run gives git's own `core.unsetenvvars` default on its command line. A fetch, pull or push names its remote, its remote's own programs as git's, and its own lines (a fetch's and a pull's with an empty refmap, so that no configured or legacy line applies), and follows no http redirect, also where a setting for its own address says to; a push names its branch on both sides and goes only to a server, never into a folder, a share or the repository itself; an address is read only in a strict form, and nothing runs when it is not; a push in a repository whose pre-push hook is Git LFS's does not start. Not covered, and said in the notice every time: until the user trusts a repository, axGIT runs no git in it and reaches nothing; once trusted, git works in it as git does: it runs the programs and hooks the repository's settings name, whatever they run in turn (a program a setting names is a command line, which may run files of the work tree), and axGIT sets aside only those whose path is in the work tree, on the commands that change the repository; and git reads the files and places those settings and its index name, which can be on another computer (a status reads an untracked folder's `.git` file and what it names, which the check does not read). Also not covered, since each needs a program writing in the repository at the same moment: a file changed between a check and git's start, or a link put on a path between the check and its opening, is seen at the next check; and a settings file swapped and swapped back between the two reads of its content that keep its parse is not seen.
- Reports (`docs/axKit/reports.md` RP-6.9, R-57): the sender sends only the report files axKit's own report form saved, by a list of their names under the settings' seal; another file put into the reports folder is never sent, and the user is told how many there were.
- The settings that decide what is run or what Claude may read are sealed (`docs/axKit/SPEC.md` AX-5.6, `docs/axKit/repairs.md` R-53): axTerminal's shells and command lines, axGIT's trusted repositories (each trust bound to what the repository held when it was given, its hooks' and named files' content among it), axMCP's servers, axFile's custom programs, the place of Claude Code, AI help's switch, folders and working folder, and the recorded agreements. Each file carries an HMAC-SHA256 over those fields under a key kept with Windows' protection for the user (DPAPI) in `%LOCALAPPDATA%\AxKit\settings-seal.key`; a field whose seal does not check is put to its default and not used, and the user is told once. The agreement for a custom shell is for its command line. The limit: a program running as the user can ask Windows for the same key; the seal holds against a file edited by another program or by hand, a profile copied or synced from elsewhere, and an AI tool writing files.
- Settings and logs stay in the user's profile (`%APPDATA%\AxKit`, `%LOCALAPPDATA%\AxKit`). Copy diagnostics puts the versions, paths and the log's end on the clipboard, with the account's name, paths, e-mail addresses and ids replaced, for the user to read before sharing.
- Releases are signed with a key that lives on the maintainer's computer, with a passphrase-encrypted backup beside its passphrase in his private repository `KyleKeane/AxKit-keys` since 2026-11-15, so that a stolen GitHub account of his could sign (the security audit of 2026-10-24 S-27); the apps and `install.cmd` install nothing whose signature does not check (`docs/axKit/SPEC.md` AX-3.4).
- The security audit of 2026-10-24 and the review of 3.7.x on 2026-10-25 listed every finding, what was done about it and what was accepted; the fixes are in the code, which names each finding by its number (S-1 to S-33), and the audit itself is in the repository's history (the file `docs/axKit/security-audit-2026-10-24.md` at commit ab8cf1b1); the AI tools are specified with their protections in `docs/axKit/mcp.md`, and off until the user turns them on. Running a window's command for a paired AI tool (`axkit_window_run`, MC-7) has a second switch of its own, off by default and sealed with the first, is never offered in axPass or axClip, never while the window asks the user something or while the user types in it, and asks the user before any command that acts outside the window (a program started, a file opened in its program, the clipboard read among them; a test fails on a command without its mark). The typed tools over axTask's lists (MC-8) read through an open axTask window and add an item only behind the same switch, never changing or deleting one. Turning the access off and Forget AI tools turn it off too.
