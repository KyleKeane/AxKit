# axKit

axKit is a bundle of accessible Windows apps for a blind developer who uses the NVDA screen reader, shipped as one self-contained executable, `AxKit.exe`. Each app is a window that NVDA reads reliably and that works wholly from the keyboard. Some are standalone (a file manager, editors, a task list, a calculator); some are access layers over a program axKit does not include (axClaude over Claude Code, axGIT over Git, axTerminal over a shell, axPass over KeePassXC). Releases go from `main`; larger work runs on a branch and merges when its checks have passed.

## Where things are

- **The apps**: `docs/axKit/apps.md`, written from `Dispatch.Apps` (`src/AxKit.Core/Dispatch.cs`), lists every app with its command, its code, its tests, its documents and its automated checks. The list of apps is written nowhere else by hand.
- **One app** is `src/Ax<Name>` (the window, with a `CLAUDE.md` of notes), `src/Ax<Name>.Core` (pure code, with its own notes), `tests/Ax<Name>.Tests` and `docs/ax<Name>/` (`SPEC.md`, `user-guide.md`, `nvda-test-plan.md`). In an app's code and documents, "SPEC.md" means that app's own specification.
- **The shared pieces**: `src/AxKit.Core` (pure code) and `src/AxKit.Forms` (the window base `AxKitForm` and the shared controls), each with its notes; `src/AxKit` is the executable. The kinds of window: the text editor shell (axDown, axJSON, axPreview), the console window (axClaude, axTerminal), the item window `ItemForm` (axTask, axPass, axMCP, axAutomate) and the hotkey window `HotkeyForm` (axStart, axClip, axHelp).
- **The documents**: `docs/axKit/documents.md` says where each thing is written. **The commands**: `docs/axKit/commands.md`.
- **Open work**: the priorities list (rule 9). **What the audits found and what became of it**: `docs/axKit/repairs.md`, written from `docs/axKit/repairs.json`. **Apps asked for and not built**: `docs/axKit/plan.md`, "Still to come".

Specifications are the source of truth: `docs/axKit/SPEC.md` for the bundle and `docs/ax<Name>/SPEC.md` for each app. A behaviour change updates the spec in the same commit.

## Stack and constraints

- .NET 10 (LTS), C#, WinForms. WinForms is deliberate: native Win32 controls (EDIT, menus, status bar, ListBox) that NVDA reads reliably. No WPF, Avalonia or web view.
- Zero third-party runtime dependencies, no NuGet packages. Windows APIs are called through P/Invoke.
- Plain code (SPEC B-10): plain classes, static methods, records for data, one obvious way to do each thing. No dependency injection, no interfaces with one implementation, no reflection beyond what WinForms needs, no clever generics. A smaller model must be able to change one app with only that app's folders, spec and notes in context.
- Everything that does not need a window lives in a `.Core` project and is unit tested; recorded fixtures live under `tests/fixtures`.

## Commands

The ones used every day; all of them, with their options, are in `docs/axKit/commands.md`.

- `.\test.ps1 [<App>]`: every test project (or one) in Release, one by one, then the checks of the generated pages. Run it before a commit. Never `dotnet test AxKit.sln` while axKit runs.
- `.\run.ps1 [-App <verb>] [<path>]`, or `.\run-ax<Name>.ps1`: build and start one app.
- `dotnet run --project tools\AxAutomate -c Release -- tests\scripts\<app> --build`: the app's automated window checks, on a desktop of their own (`docs/axKit/automation.md`). They never run in CI: run them after a change to a window.
- `.\nvda-pass.ps1 [<app>]`: the same checks with NVDA listening. It takes the keyboard: only after the user has stepped away.
- The generated pages (`outside-calls.md`, `workflows.md`, `repairs.md`, `apps.md` in `docs/axKit`) are each written by a script in `tools` and never by hand; `test.ps1` says which script to run when one is stale.
- `.\tools\upstream.ps1` at the start of a session: when it says an outside program changed, run it with `-Verify` before other work and fix what fails in that program's one place (rule 12).
- After a bare `dotnet build` or `dotnet test`, run `dotnet build-server shutdown`: the development computer has 7 GB.
- `.\release.ps1 <version>` only at the maintainer's word.

## Rules of the bundle

1. Accessibility first (SPEC AX-7). Every control gets an `AccessibleName`; every list the user moves through is `AxKit.Forms/AxKitList` (type-to-find and the edge earcon built in, AX-8.6; `ListTests` enforces it); every action works without a mouse; the caret moves only on the user's own command; results of navigation are announced through one UI Automation notification.
2. No second window of an app's own (AX-7.2): questions, errors and help texts are notices inside the window (`OverlayPanel`), what an app waits on goes in place of its input field (`ControlArea`); never a `Form` or a `MessageBox` once a window exists. The Windows folder, file and font pickers, and the shell's own dialogs and menu an app hands an entry to (axFile's Open with, Properties and Windows menu), are the only separate windows. An app that keeps one window (axMedia, axPreview) takes what a second start brings through `AppMessage`, a window message, and the second process ends.
3. Never block the UI thread on I/O; background reads are marshalled to the UI thread and batched.
4. Modularity (SPEC 5.3): one app, one set of folders; references point one way (an app never references another app; shared projects never reference an app; `LayoutTests` enforces it); shared code moves on the second use, unchanged, one piece per commit; notes next to the code; one version, one changelog with app prefixes (`axClaude:`, `axDown:`, `axKit:`). A new app follows `docs/axKit/adding-an-app.md`.
5. Keys (SPEC AX-8): every key is either bundle-wide (`AxKit.Forms/BundleKeys`, the same in every window) or window-specific (one table per window); a key is changed in its table and nowhere else; a test fails on a collision.
6. Personal data never enters the repository or a session's output: only the licence identity (Dr. Kyle Keane, www.kylekeane.com) appears; `PrivacyTests` fails on an e-mail address or an account path; recordings are read through PtyCapture's redacting `--dump`, never `--raw`, `cat` or `type`.
7. Git hygiene: small commits with imperative subject lines; never commit `bin/`, `obj/`, ad-hoc captures or `.claude/settings.local.json`. Every commit builds and passes the tests; `main` is always releasable. Fetch before building on the repository: `git fetch origin` and `tools/sync-repos.ps1` at the start of a session and before its first commit, and bring in anything `origin/main` has gained (`git pull --ff-only` on `main`, a merge or rebase on a branch) before new work stacks on a stale base. `release.ps1` fetches and refuses a `main` that is behind `origin/main`; git itself only rejects the push, after local commits have piled up. Every push of this repository also syncs the two repositories beside it through the pre-push hook (`tools/sync-repos.ps1`), so the reports clone and the management lists never wait on anyone's memory; `release.ps1` refuses to run until the hook is installed.
8. Local first (SPEC G6, B-15, AX-11.11): every standalone app keeps its full utility with the network off; an access layer reaches the network only through the program it runs as a child process on a pseudo console or pipes (Claude Code talks to Anthropic, git reaches a remote on fetch, pull and push alone, the shell's commands reach what they reach, KeePassXC's tool nothing); axKit's own code makes network requests in three places, over HTTPS to GitHub: the updater (the update check, a setting, and the download the user chooses), the report sender (`docs/axKit/reports.md`, only when the user sends a report, F4, the report saved on the computer first) and axTask's GitHub lists (`docs/axKit/reports.md` RP-7, only when the user opens or refreshes such a list, which reads the issues of the list's repository, or acts on one of its items, which is sent with the user's own token); AI help is one shared, optional service that no app's feature depends on, never a feature built into one app. `PRIVACY.md`, `README.md`, `docs/axKit/README.md` and `SECURITY.md` state this in these terms and change in the same commit as any new network contact. Every network request, program start or pipe in `src` carries an `Outside call, <kind>, <what is reached>:` comment on the line above it or at its end, and `tools/outside-calls.ps1` writes `docs/axKit/outside-calls.md` from them (B-17); a new kind of call or a new program joins the script's tables in the same commit.
9. Open work has one place: the `priorities` list of the private management repository beside this one (`..\axkit-management\priorities`, axTask's top folder, one JSON item per piece of work with Done, Priority, App, Due, Where it is written and Notes). Intake is the public reports repository `KyleKeane/AxKit-reports` (F4 from any window; `..\axkit-management\issues` shows its open issues in axTask), and the documents keep their own open items where they are (`docs/axKit/plan.md` "Still to come", the Owed sections of `docs/axKit/nvda-test-record.md`, `docs/axClaude/SPEC.md` section 12, `docs/axKit/inventory-2026-10-24.md` section 3, `docs/axKit/store-distribution.md` section 5). Whenever work is found, asked for, deferred or finished (a report read, an NVDA pass owed, a decision left to the user, a leftover seen in the code), the assistant writes or updates its item there in the same turn: the title names the app and the thing, Where it is written points at the report or the document section, Notes hold the scope (what it touches, what it waits on, how big it is) and the reason for the proposed Priority, which the user changes in axTask; a finished item is marked Done, never deleted. The commit does the marking (the user's wish of 2026-11-13, so that it never depends on memory): every commit message names its item on a line of its own, `Item: <words of the item's title>` for work on it, `Item done: <words>` for the commit that finishes it, or `Item: none, <the reason>` for upkeep that belongs to no item; the commit-msg hook (`tools/hooks/commit-msg`, `tools/item-of-commit.ps1`) refuses a message without such a line or with words that name no item or several, and writes today's date into the item's Started field, or checks its Done. So the item is written before the first commit of its work. The pre-push hook pushes the lists with the next push of the code, so nothing of this lives in a session or a memory.
10. axKit is the tool both of us use to work together (the user's word, 2026-11-12). The assistant uses what Anthropic gives it as that grows, and also builds and uses axKit's own access layer for our coordination: the AI tools (MCP, `docs/axKit/mcp.md`), the axTask lists, plain data structures and automations, with tests and checks like every release's. When a piece of our coordination is done by hand more than once, propose the tool for it. Above all of this: stable, the screen reader user in full control, the simplest flow, no interaction that is not needed.
11. What an AI wrote or asks for says so, and code most of all (SPEC AX-11.12; the user's decision, 2026-11-13). Any place that shows text an AI wrote for the user to act on, or lets something an AI asked for happen (a command to run, a window command run for an AI tool, an answer of AI help, anything of the kind built later), states in plain words who wrote it, that it can be wrong, that axKit checked nothing of it, and that acting on it is the user's own choice; the words come from `AxKit.Core/AiCaution`, never written afresh. Code and commands get special care: the caution is heard with the question every time and is the first thing in the explanation; it says that a command may be offered because the AI's own permission or safety checks refused it, to run it with care and to read every detail first; running is never the default answer or where a list starts; the AI's own explanation is labelled as the AI's. A feature of this kind is designed with its caution from the start, and the spec section, the user guide and AX-11.12's list change in the same commit.

12. An access layer holds the user's experience still (the user's direction, 2026-11-14). axKit is a self-contained system on its own console pieces (the ones axTerminal runs on) and its own small window framework. The programs under an access layer (Claude Code, Git, a shell, KeePassXC, others later) change their output, their signals and their options whenever their makers choose. Everything read from such a program or sent to it goes through one place of axKit's own per program: its launcher, its parser, the table of its screen texts and keys, its protocol, each tested from recordings. When the program changes, that place is adjusted, and what the user hears and presses stays as it was; a window never reads a program's text itself. New work is built so that a second program of the same kind (a second agent beside Claude Code) fills the same places and gets the same window.

## Environment gotchas (bundle-wide)

- A running app locks its `bin` folder. Build somewhere else to check a change (`dotnet build <project> -o <scratch dir>`) and ask the user to restart the app for a real run. Dialogs and menus can be checked off screen from a small probe project that references the scratch build; never activate windows or send keys while the user is working. A probe started from this session is a child of the user's foreground app and may take the foreground, so a probe is a `WinExe` (no console window) that writes its output to a file, shows its own forms with `ShowWithoutActivation` and the app's windows with `ShowWindow(SW_SHOWNOACTIVATE)`, `SetActiveWindow` (the thread's own active window, so that controls can take the focus) and `OnShown` by reflection, never calls `Show()`, `Activate()` or `SetForegroundWindow`, plays silent media, and checks `GetForegroundWindow()` right before and right after showing (the user lost the keyboard to probe windows on 2026-10-21). Verified for axFile's window: the foreground stays. Not for axClaude's: `SetActiveWindow` on `MainForm` made it the foreground window in the probe process, cause not yet found, so a probe of axClaude's window is not run while the user works until it is. Menu mode of a menu bar cannot be driven this way at all: WinForms enters it only in the foreground window.
- The Bash tool mangles backslashes inside heredocs: use the Write tool for source files. A PowerShell one-liner sent through the Bash tool loses its backticks to command substitution; `-replace` is case-insensitive, so a mangled pattern once turned every capital N of a file into n. Run PowerShell through the PowerShell tool.
- Windows PowerShell 5.1: `$PSScriptRoot` was once seen empty while parameter defaults were evaluated (`tools/make-icon.ps1` and two others read `$MyInvocation.MyCommand.Path` instead; a scratch script on 2026-11-09 could not reproduce it, so the case is unknown and the workarounds stay), and a function that returns a byte array unrolls it unless written `return , $bytes`.
- PowerShell variable names are case-insensitive and a script's parameters are variables: a local `$msix` is the `-Msix` switch, and a local `$apps` is the `[string]$Apps` parameter, which turns the array assigned to it into one string (publish.ps1 and tools/make-manifest.ps1, 2026-11-08). Name every local unlike every parameter.
- Windows PowerShell 5.1 reads a script without a byte order mark as ANSI, and the repository's scripts carry no mark: a script stays ASCII, since a non-ASCII character becomes several (an ellipsis in a script for the Store, since removed, made the release notes three characters too long, 2026-11-09). Write `...`, not the one-character ellipsis.

## Manual verification

Any change to focus handling, key handling, announcements or an edit control is checked with NVDA running, following the app's test plan (`docs/<app>/nvda-test-plan.md`) on the files of `manual_tests/<app>`. Every pass is written down in `docs/axKit/nvda-test-record.md`, by step, with the version and the commit, newest first: when a bug comes up, it says when its step last passed. The assistant runs these passes itself: `.\nvda-pass.ps1 [<app>]` runs the app's scripts with NVDA listening (every expected announcement must also be spoken by NVDA, read from the `axkitCapture` add-on) plus `tests/nvda-scripts`, after asking the user through the question tool to step away; it takes the keyboard, and Windows' voice repeats the warning until it is over (`docs/axKit/automation.md` section 3). Ask the user for a pass by ear only for what it cannot hear: sound and video quality, the Start menu and Explorer, and how a change feels.
